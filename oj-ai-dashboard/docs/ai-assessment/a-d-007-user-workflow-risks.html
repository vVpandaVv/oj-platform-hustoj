사용자 업무 흐름과 위험

교사의 활동지 제작·자체 평가·발행·배포·제출 관리·AI 평가·검토·공개·출력과 학생의 조회·작성·저장·제출·피드백 흐름을 실제 화면 명령부터 저장소까지 추적했다. 정상 흐름뿐 아니라 빈 상태, 오류, 브라우저 중단, 재실행과 수동 복구가 가능한지도 함께 판정한다.

조사일 2026-08-10 상태 사용자 확인·기준선 확정 관리 화면 11개 활동지 로컬 단계 4개 학생 목록 기본 50개·후보 150개 자동 저장 1.5초 자동 제출 5분·회당 100과제 제출 상태 7개 교사→학생 전체 E2E 0개 실행 코드 변경 0건

한 줄 판정

현재 구현에는 제작, 배포, 제출, 평가, 보고서 기능이 각각 존재하지만 하나의 책임 있는 업무 흐름으로 이어지지 않는다. 발행 snapshot과 시간 관문이 없고 저장 충돌·부분 업로드·브라우저 중단을 사용자가 복구할 수 없으며, 일괄 AI 평가와 PDF 생성도 요청 수명 안에서 실행된다. 기존 화면을 그대로 연결하기보다 불변 revision, 서버 상태 전이, 지속 작업함과 명시적 복구 명령을 중심으로 사용자 여정을 다시 설계해야 한다.

가장 큰 사용자 위험: 학생은 마감 뒤에도 현재 활동지를 열고 저장·제출할 수 있지만, 자동 제출은 이미 초안을 만든 학생만 처리한다. 저장 충돌 응답에는 서버 최신 답안이 들어 있어도 화면은 이를 보여 주거나 병합하지 않아 이후 저장이 계속 충돌할 수 있다.

단계현재 동작완료로 보이는 신호사용자 위험
1. context 준비학사 상태·그룹 200·학생 500을 동시에 조회드롭다운과 학생 목록 표시각 조회 오류를 빈 객체·빈 목록으로 바꾸므로 실제 빈 학급과 연결 장애를 구분할 수 없음
2. 활동지 제작Plate 편집 후 제목·status·rubric mode와 schema 저장공용 메시지에 저장 성공unsaved 표시·로컬 복구·이탈 경고가 없고 malformed hidden JSON은 기본 문서로 대체될 수 있음
3. 자체 평가화면·명령 없음없음활동지의 명확성·정답성·난이도·안전·루브릭 정합성을 AI로 검사할 수 없음
4. 발행draft|active|archived를 저장 폼에서 직접 선택active 문자열review·publish 명령, 불변 revision, 학생/PDF preview와 발행 전 관문이 없음
5. 배포template·학년·반·그룹·학생·시작·마감을 입력하고 즉시 assigned 저장“배포되었습니다” 메시지대상 수·제외자·중복·시간대·발행 revision 확인 없이 mutable template를 바로 배포
6. 모니터링제출 화면에서 과제·학년·반·상태로 현재 submission 행 조회제출 행 목록한 번도 시작하지 않은 학생은 submission 행이 없어 기대 명단과 실제 제출을 같은 화면에서 안정적으로 비교하지 못함
7. 평가별도 평가 화면에서 계획 저장·preflight 후 제출을 다시 불러와 순차 채점현재 화면의 요약 카드계획과 실행이 서버에서 연결되지 않고 브라우저 이탈 시 남은 작업과 선택이 사라짐
8. 검토·공개결과 승인·반려, 재평가 검토, 피드백 생성·공개현재 메모리의 result·feedback 상태accepted 점수와 학생 공개가 분리되지 않으며 reload 뒤 기존 피드백 일괄 공개가 현재 state에서 복구되지 않음
9. 출력제출 PDF 또는 일괄 PDF 버튼으로 보고서 생성다운로드 링크정확한 발행·제출 revision이 아니라 현재 조회를 동기 출력하고 실패 작업을 다시 여는 목록이 없음

현재 제작·배포의 상태 전이

Plate 편집 중 메모리
  → 저장 클릭
  → mutable template update
  → status를 draft/active/archived 중 직접 저장
  → 배포 폼에서 현재 template ID 선택
  → assignment status=assigned 즉시 저장
  → 학생 상세 요청 때마다 현재 teacher template 재조회·학생 projection

누락: draft revision → 자체 평가 → 교사 해결 → preview → publish snapshot
누락: target preview → 확인 → scheduled/open → server-time close
발행 뒤 변경 위험: 과제는 published snapshot이 아니라 template ID를 보유하고 학생 상세와 제출 grading schema가 현재 template을 다시 읽는다. 교사가 나중에 template을 수정·보관·삭제하면 이미 배포한 학생 화면과 채점 기준도 달라지거나 열리지 않을 수 있다.

현재 학생 업무 흐름

단계현재 정상 흐름빈 상태·오류중단·복구
1. 발견/student/assignments?limit=50 목록 조회0건이면 “활동지 없음”, 오류면 공용 오류 메시지전역 후보 150개를 먼저 제한해 오래되거나 뒤쪽인 본인 과제가 누락될 수 있음
2. 열기assigned 또는 closed 과제의 현재 학생 projection과 현재 submission 조회403·404를 일반 “열지 못했습니다”로 표시starts_at·due_at을 서버 접근 관문으로 사용하지 않아 예정·마감 의미가 불일치
3. 작성응답 input마다 답안을 메모리에 모으고 1.5초 뒤 자동 저장필수·형식·선택지·표 구조 검증 없음로컬 영속 draft, offline 감지, 이탈 경고와 재전송 queue 없음
4. 첨부파일을 하나씩 먼저 업로드한 뒤 답안에 URL을 넣어 자동 저장중간 파일 실패 시 일반 오류앞서 성공한 파일은 orphan이 될 수 있고 삭제·재시도·scan 진행 상태가 없음
5. 저장 충돌base_revision이 같으면 새 revision 저장다르면 서버가 409와 latest_content 반환클라이언트가 최신 내용을 사용하지 않아 base가 계속 오래된 채로 남고 반복 저장도 충돌 가능
6. 제출현재 답안을 한 번 더 저장한 뒤 submitted·locked 처리사전 검증·문항 누락 요약 없이 요청 오류만 표시서버 저장 뒤 응답이 끊기면 새 idempotency key로 재시도해 결과 확인 대신 충돌할 수 있음
7. 마감WP-Cron이 기존 draft/conflict 행을 자동 제출미작성 학생은 행이 없어 처리되지 않음마감 뒤에도 과제가 assigned/closed이면 학생이 새 답안을 시작·제출할 수 있음
8. 결과제출 상태는 잠기며 별도 대시보드가 accepted 점수·feedback 상태를 조회피드백 본문과 결과물 PDF 화면 없음재개방 이유·새 마감·교정 공지와 공식 공개 revision을 학생이 확인할 수 없음

현재 자동 저장과 충돌

답안 변경
  → 1.5초 debounce
  → client_revision + 1
  → idempotency_key = session + revision + Date.now()
  → POST autosave(base_revision)

성공: server_revision 갱신
응답 유실: 서버는 저장했지만 클라이언트는 이전 base 유지
재시도: 새 idempotency key + 이전 base → 409 conflict
409 응답: server_revision + latest_content 포함
현재 UI: 메시지만 표시, 비교·병합·서버본 열기·내 사본 다운로드 없음

현재 마감과 자동 제출

assignment.starts_at / due_at
  → 목록 표시용 데이터
  → student_can_access: status assigned|closed + 대상 여부만 검사

5분 WP-Cron
  → due_at 지난 assigned 과제 최대 100개
  → auto_submit_enabled 검사
  → 이미 존재하는 draft|autosave_conflict submission만 auto_submitted
  → assignment는 assigned로 남아 다음 cron에서도 다시 후보

결과: 미시작 학생은 자동 제출되지 않고, 서버 마감도 강제되지 않음

submission revision·접수 시각·상태·첨부 개수와 PDF 준비 상태를 보여 주며 새로고침 뒤에도 같은 영수증을 조회한다.
재개방·교정
교사가 재개방하면 이유·새 마감·기존 공식 결과 영향을 알리고 새 draft revision에서 다시 작성한다.
결과와 피드백
교사가 공개한 release만 점수·문항별 feedback·종합 feedback으로 보여 주고 변경·철회 알림과 활동지/제출 결과물 PDF를 제공한다.

확인할 목표 결정

  1. 교사 기능은 OJ Console의 학습 공간 > AI 활동지에서 활동지 생명주기 작업대로 통합한다. 제작·자체 평가·발행·배포·제출·평가·공개·출력 탭이 worksheet/assignment context를 유지하고, 학생 기능은 별도 PublicUI 학습 > 활동지에 둔다.
  2. 활동지는 자동 복구 가능한 draft revision으로 작성하고, 특정 revision의 활동지 자체 AI 평가·교사 해결·학생/교사/PDF 미리보기를 거친 뒤에만 불변 published snapshot을 만든다. AI는 활동지를 자동 수정하거나 발행하지 않는다.
  3. 배포는 published snapshot만 선택하고 OJ Platform의 수업 context·roster를 원장으로 target snapshot을 만든다. 대상 수·제외·중복·변경·시간대를 preflight와 확인 화면에서 검토한 뒤 scheduled|open으로 전환한다.
  4. 시작·마감·grace·재개방은 서버 시각과 command policy로 강제한다. 대상 학생 전원을 not_started부터 추적하고 자동 제출은 지속 worker가 기대 명단 전체를 대상으로 idempotent하게 처리한다.
  5. 학생 작성은 로컬 recovery draft와 서버 revision을 함께 사용한다. operation 동안 같은 idempotency key를 유지하고 저장 영수증, offline queue, 충돌 비교·병합, 제출 전 schema 검증과 제출 영수증을 제공한다.
  6. 첨부는 private quarantine에서 파일별 upload·scan·extraction·ready/failed 상태를 관리한다. 학생은 실패 재시도·삭제가 가능하고, 정책상 준비되지 않은 첨부를 포함한 제출은 명확히 차단하거나 검토 상태로 분리한다.
  7. 활동지·제출 AI 평가는 ready plan revision에서 애드온 batch를 enqueue한다. 작업함이 item 진행률·attempt·partial failure·pause·resume·cancel·실패만 재시도를 제공하며 브라우저 반복을 실행환경으로 사용하지 않는다.
  8. AI 결과 검토, 공식 점수 확정, 점수 공개, feedback 승인, feedback 공개를 분리한다. 재평가 교체는 기존 공식 결과를 유지한 채 원자적으로 수행하고 관련 release를 stale·withdrawn으로 명시해 학생에게 교정을 알린다.
  9. 재개방·대리 제출·결시·ZIP·자동 제출·export는 지속 작업 또는 보호된 command로 만들고 대상·영향·사유·실행자·시각·idempotency·복구 결과를 감사한다. 부분 성공은 성공으로 뭉개지 않고 항목별 재개가 가능해야 한다.
  10. 모든 화면은 loading·empty·error·partial·conflict·offline·stale·permission·success·destructive 상태 계약을 공유하고 객체 scope·접근성·반응형·역할 기반 E2E로 검증한다. 애드온은 플랫폼 파일을 수정하지 않고 모든 애드온 물리 테이블에 oj_ai_* 무접두어 규칙을 유지한다.
