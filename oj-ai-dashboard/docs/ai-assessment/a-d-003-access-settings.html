한 줄 판정

기능 단위 capability는 비교적 세분되어 있지만, 별도 애드온 역할이 OJ Console 접근권한과 연결되지 않고 화면 권한과 화면 안 작업 권한도 일치하지 않는다. REST는 capability를 검사해도 대부분의 교사 작업에서 학급·배정·결과 소유 범위를 재검사하지 않으며, 브라우저가 발급하는 nonce와 서버가 검증하는 nonce action이 달라 현재 쓰기 요청이 정상적으로 통과할 수 없다.

설계 기준: capability 보유는 기능 종류에 대한 허용일 뿐 특정 학급·학생·배정·평가 결과에 대한 접근 허용이 아니다. 목표 모델은 shell 접근 + 기능 capability + 객체 scope + 요청 무결성을 모든 메뉴, 직접 URL, REST, Jobs, 보고서에서 같은 순서로 검사해야 한다.

애드온 재검증기본 action oj_ai_dashboard같은 nonce 문자열을 다른 action으로 검증해 실패
GET 재사용/submissions, /submissions/{id}조회도 쓰기용 manage_submissions callback을 사용해 nonce를 요구
목표 규칙: 브라우저 cookie REST는 WordPress의 wp_rest 계약 하나를 사용한다. capability와 객체 scope는 permission callback에서 계속 검사하되 같은 header를 다른 action으로 중복 검증하지 않는다. 비브라우저 호출이 필요하면 별도의 명시적 인증 방식을 설계하고 nonce와 섞지 않는다.

A-D-003 확정 결정

  1. 신규 설치에서는 애드온 전용 교사·학생·보조교사 역할을 만들지 않고, 플랫폼의 역할·사용자 권한 관리에서 애드온 capability를 배정한다.
  2. Console Route는 플랫폼 shell 접근과 애드온 capability를 모두 요구하고, PublicUI Route는 로그인·학습자 사용 capability·해당 배정 scope를 모두 요구한다.
  3. 교사 객체 범위는 애드온 로컬 학급 표가 아니라 플랫폼 context authorization gateway를 기준으로 한다.
  4. 활동지 자체 평가 실행과 학생 제출 평가 실행 capability를 분리하고, 검토·승인·공개도 독립 capability로 유지한다.
  5. 브라우저 REST는 wp_rest nonce 계약 하나만 사용하며 모든 읽기·쓰기에서 capability와 객체 scope를 별도로 검사한다.
  6. C-28 보완은 플랫폼 코드 변경 전에 플랫폼 개발 문서에 계약·거부 조건·테스트 기준을 먼저 반영하고 같은 구현 작업에서 동기화한다.
