신규 설치 절차

1 · 정적 사전 검사
WordPress·PHP·extension·단일 사이트·플랫폼 상수와 Addon API 범위를 확인한다.
2 · 이름·소유 검사
45개 exact 이름을 조회하고 동명 table과 과거 source를 구분한다. 하나라도 소유 불명이면 쓰지 않는다. 단, exact·empty bootstrap owner table 하나는 0.1.5 제한 복구로 잠금 전후 재검증한다.
3 · DB lock
oj_ai_dashboard_schema named lock 하나를 획득하고 설치 correlation을 만든다.
4 · 원장 bootstrap
installation·schema migration 원장을 먼저 만들고 owner marker를 기록한다.
5 · Immutable delta
정렬된 migration을 한 번씩 적용하고 DDL·checksum·postcondition을 기록한다.
6 · 전수 검산
45개 table·owner 10개·index·column·FK·schema fingerprint를 다시 계산한다.
7 · 등록 대기
설치는 registration_pending으로 끝나며 다음 정상 boot의 Manifest 승인을 미리 성공으로 간주하지 않는다.
8 · Runtime 준비
accepted onReady()에서 schema를 읽기 전용 검산하고 Bridge를 원자 연결한다. DDL은 실행하지 않는다.

WordPress activation hook이 실패하면 안정 code와 짧은 조치만 표시한다. DDL은 auto-commit될 수 있으므로 일부 적용이 발생하면 원장과 postcondition으로 maintenance_required를 남기고 다음 시도는 완료된 checksum을 검산한 뒤 forward repair만 수행한다.

부분 실패·보상·재실행

  • 각 item은 source type·key·checksum과 생성한 target type·public ID를 기록한다. 같은 source checksum 재실행은 기존 성공 item을 중복 생성하지 않는다.
  • 한 batch는 owner aggregate 단위 transaction으로 처리한다. 다른 batch 실패가 이미 검증된 aggregate를 암묵적으로 rollback하지 않는다.
  • C63은 DB 전체 rollback이 아니라 이 run이 만든 target만 역의존 순서로 보상한다. 이후 사용자가 수정·배포·제출한 target은 자동 삭제하지 않고 수동 해결로 남긴다.
  • 원본 source와 package는 수정하지 않는다. 실패 항목을 고친 새 mapping은 새 plan hash와 새 run을 사용한다.
  • 보상 완료 뒤에도 import run·item과 감사 사건은 남기며 원본 삭제를 성공 조건으로 삼지 않는다.
