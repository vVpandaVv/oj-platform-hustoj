한 줄 판정

물리 테이블 이름은 모두 요구대로 oj_ai_*이며 $wpdb->prefix를 사용하지 않는다. 그러나 플랫폼 원장과 중복되는 학사 테이블 6개, 제출물에만 묶인 평가 구조, 활동지 발행 revision 부재, 변경 가능한 과거 migration, 공개 URL 파일과 보존·삭제 정책 부재 때문에 현재 35개를 그대로 목표 스키마로 채택할 수 없다.

활동지 자체 평가 기준: AI가 평가할 활동지는 편집 중인 최신 template가 아니라 특정 worksheet revision 또는 발행 snapshot이어야 한다. 이 평가는 submission_id가 필요한 학생 제출 평가와 별도 subject·입력 snapshot·결과·검토 이력을 가져야 한다.

현재 문제영향목표 관문
두 과거 migration이 모두 현재 Schema::sql() 호출Schema 변경 시 과거 설치 경로의 의미도 바뀜migration별 SQL·postcondition·checksum immutable
두 번째 migration도 전체 테이블 반복실제 delta와 migration ID가 일치하지 않음한 migration은 한 목적의 delta만 소유
dbDelta 결과·DDL 상태 미검증일부 테이블 실패 뒤에도 완료로 기록될 수 있음예상 table·column·index·constraint 전수 postcondition
lock·동시 실행·repair checkpoint 없음활성화 요청이 겹치면 이력·schema가 어긋날 수 있음단일 lock, timeout, 실패 상태, 재시작과 운영자 repair 절차
동명 무접두어 table owner 확인 없음다른 설치의 oj_ai_*를 오인·변경할 수 있음owner marker와 schema fingerprint가 없거나 다르면 설치 중단, 자동 adoption 금지
Multisite 사전 차단 없음tenant_context=default로 사이트 간 충돌필수 OJ Platform과 같은 방식으로 Multisite 설치 거부
0.1.5 제한 복구 보정: 자동 adoption 금지 원칙은 유지한다. 예외는 첫 CREATE 뒤 중단된 oj_ai_installations 하나만 존재하고 0행이며 immutable baseline과 exact 일치하는 경우다. 잠금 전후와 기록 직전에 다시 확인해 누락된 addon owner row만 복원하고, 행 존재·복수 table·drift는 쓰기 전에 차단한다.
0.1.6 DB metadata 호환: MariaDB가 nullable 열의 SQL NULL을 문자열 NULL로 전달하는 차이만 의미 기준으로 정규화한다. quoted literal 'NULL'과 실제 column·index·FK·engine·collation drift는 계속 구분하고 차단한다.
DDL 현실성: MySQL DDL 전체를 하나의 transaction으로 되돌릴 수 있다고 가정하지 않는다. 각 migration을 재실행 가능하게 만들고 실행 전후 schema postcondition과 repair checkpoint로 복구한다. 데이터 backfill은 작은 batch·checkpoint·검산 합계로 별도 수행한다.

A-D-004 확정 결정

  1. 목표 물리 테이블은 계속 고정 oj_ai_*를 사용하고, OJ Platform과 동일하게 Multisite를 거부하며 동명 table owner·schema preflight가 실패하면 설치를 중단한다.
  2. 로컬 학사 원장 6개와 roster import를 제거하고 플랫폼 user·class·group stable ID와 context authorization snapshot만 참조한다.
  3. 활동지는 immutable revision·발행 snapshot을 도입하고, 활동지 자체 평가와 학생 제출 평가는 별도 subject·입력·결과를 저장하되 실행·검토 공통 계약만 공유한다.
  4. 학생 첨부·ZIP·내보내기는 private storage와 권한 streaming만 허용하고, JSON·AI raw 데이터·파일의 schema version·redaction·보존·cleanup 정책을 필수화한다.
  5. Migration은 immutable delta·checksum·lock·postcondition·repair checkpoint를 사용하며 legacy import는 preview·명시 승인·idempotency·batch rollback 또는 보상 절차를 갖춘다.
  6. 비활성화는 데이터를 보존한다. uninstall도 기본 보존하며, 관리자에게 범위·수량을 보여 주는 별도 2단계 삭제 승인을 받은 경우에만 애드온 table·option·private blob을 purge한다.
