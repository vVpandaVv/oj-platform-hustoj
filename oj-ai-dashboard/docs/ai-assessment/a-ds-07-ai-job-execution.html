A-DS-07 · AI Job Orchestration Contract

AI 작업 실행·큐

OJ Platform은 승인된 AI task의 연결·routing·동기 실행만 담당한다. AI 평가 애드온은 작업 등록, lease, 재시도, 취소, 멱등성, 결과 검증과 공식 저장을 소유하며 브라우저 요청 안에서 장기 AI 호출을 완료하지 않는다.

작성일 2026-08-13 A-DS-06 사용자 확정·동결 상태 사용자 확인·동결 확정일 2026-08-13 상세 설계 8/17 Manifest AI Task 정확히 2개 플랫폼 인수 기록 AJ01~AJ08 Runtime 변경 0건

한 줄 결론

AddonRuntimeContextV1::aiTasks()는 worker가 실제 AI를 호출하는 동기 Port다. 애드온의 oj_ai_evaluation_runs와 oj_ai_evaluation_attempts가 비동기 실행 정본이며, 외부 호출은 중복될 수 있어도 lease token·멱등 key·조건부 commit으로 공식 결과는 정확히 한 번만 생성한다.

실행 경로: 화면·REST는 enqueue와 상태 조회만 수행한다. 플랫폼 내부 Jobs 모듈, provider client, WordPress AI filter, 직접 HTTP 호출, 요청 반복 loop를 worker 대체 수단으로 사용하지 않는다.

Preflight·enqueue·일괄 실행

  1. 현재 actor의 capability, platform Context, assignment·worksheet·submission 객체와 허용 상태를 검증한다.
  2. 활동지 revision 또는 공식 submission revision과 canonical hash를 고정한다.
  3. subject별 active policy·rubric·review rule·prompt descriptor·schema hash를 고정한다.
  4. canRoute()와 snapshot()이 같은 routing revision을 가리키는지 확인한다.
  5. redaction·artifact extraction을 끝낸 canonical input을 만들고 1MiB 공개 상한보다 작은 task별 상한을 적용한다.
  6. evaluation root, immutable input, queued run, audit·outbox를 owner transaction으로 저장한다.
  7. transaction이 끝난 뒤 scheduler를 깨우고 evaluation public ID·상태만 반환한다.
여러 학생 평가: 별도 batch master table을 만들지 않는다. 한 번의 교사 명령을 제출 revision별 독립 evaluation으로 확장하고 assignment별 projection에서 전체·대기·진행·확인 필요·완료 수를 집계한다. 중간 중단 뒤 같은 명령을 다시 실행해도 item별 멱등 key가 이미 만들어진 평가를 재사용하고 누락 item만 보완한다.
외부 호출과 transaction: Context Gateway와 AI Gateway 호출을 DB transaction 안에서 수행하지 않는다. preflight 결과를 고정한 뒤 worker가 시작·commit 시점에 다시 검사한다.

현재 플랫폼은 DTO의 idempotency key를 검증하지만 실제 provider 중복 억제에는 사용하지 않는다. 따라서 외부 AI 호출은 worker crash 경계에서 두 번 발생할 수 있다. 애드온은 “외부 호출 exactly-once”를 주장하지 않고 “공식 result exactly-once”만 보장한다.

Worker lease와 실행 순서

  1. due index에서 한 run을 고르고 lock version·현재 state 조건으로 queued|retry_wait → leased와 300초 lease token을 원자 적용한다.
  2. evaluation·immutable input·source·configuration hash를 읽고 현재 Context와 객체 권한을 재인가한다.
  3. task routing snapshot을 다시 읽어 고정 revision·fingerprint와 비교한다.
  4. run을 running으로 바꾸고 append-only attempt를 started로 기록한 뒤 lease를 다시 300초로 갱신한다.
  5. 고정 contract와 같은 idempotency key로 플랫폼 execute()를 한 번 호출한다.
  6. Gateway 결과의 correlation ID·실행에 사용된 routing snapshot과 output digest를 수집하고 raw response는 저장하지 않는다.
  7. task별 byte·schema·근거·점수·forbidden-key 검증과 canonical normalization을 수행한다.
  8. snapshot(taskKey)을 새로 호출해 plan·결과 snapshot·postflight 현재 revision과 fingerprint를 모두 비교한다. 조회 실패나 불일치이면 output을 폐기한다.
  9. Context·source 상태를 commit 직전에 다시 확인한다.
  10. run state·lease token·lock version이 그대로일 때만 attempt, result, evaluation state, audit·outbox를 한 transaction으로 commit한다.
Lease 회수: lease가 만료된 run은 원 worker가 죽었다고 단정하지 않는다. 현재 token을 바꾼 회수 worker만 이후 commit할 수 있으며 이전 worker가 늦게 돌아오면 결과를 버린다. 현재 플랫폼 provider timeout 최대 120초를 기준으로 300초 lease를 잡되, 이 상한이 바뀌면 플랫폼 인수 검사에서 설계를 다시 확인한다.

플랫폼은 timeout·rate limit·일시 provider 장애를 모두 안전한 실패와 retryable로 축약할 수 있다. 애드온은 숨은 provider 원인을 추측하지 않고 같은 bounded backoff를 적용한다.

취소는 비용이 아직 발생하지 않았음을 보장하지 않는다. 실행 중 provider call의 원격 취소 API가 공개되지 않았으므로 사용자 화면에는 “중지됨, 진행 중이던 요청은 반영하지 않음”으로 표시한다.

Routing drift·fallback

  1. enqueue의 snapshot() 결과 중 routing revision·profile fingerprint를 run에 고정한다.
  2. worker 시작 전 현재 snapshot과 두 값을 모두 비교한다.
  3. execute() 결과 snapshot을 run 계획과 비교해 실제 실행에 사용된 배정을 확인한다.
  4. 성공 직후 snapshot(taskKey)을 다시 호출해 현재 postflight revision·fingerprint를 읽고 plan·결과 snapshot과 함께 비교한다.
  5. postflight 조회가 실패하거나 세 값이 다르면 output이 구조적으로 정상이어도 공식 result를 만들지 않고 routing_changed_during_execute로 닫는다.
  6. provider·model은 fallback 때문에 preflight primary와 달라질 수 있으므로 반환된 실제 값을 attempt/run에 기록한다.
API 공백 보상: 실행 요청에는 expected routing revision이 없고 결과 snapshot은 응답 반환 시점의 현재 배정이 아니라 실행에 사용한 배정이다. 따라서 성공 뒤 fresh snapshot()을 별도로 호출한다. 이 비교는 잘못된 공식 결과를 막지만 변경된 route로 이미 한 번 호출되는 비용까지 막지는 못한다. 이를 완전히 막으려면 별도 플랫폼 API 변경 승인이 필요하다.
