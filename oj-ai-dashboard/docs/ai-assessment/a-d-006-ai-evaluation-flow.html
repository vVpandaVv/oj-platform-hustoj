평가와 AI 실행 흐름

활동지 자체 평가와 학생 제출 평가가 현재 어디서 시작되고, 어떤 입력·provider·normalizer·저장·검토·공개 경로를 거치는지 코드에서 역추적했다. 이 문서는 AI라는 이름과 실제 실행을 구분하고, OJ Platform의 AI 연결 경로와 애드온 평가 실행환경을 결합하는 목표 기준선이다.

한 줄 판정

현재 애드온에는 실제 AI provider 호출도 활동지 자체 평가도 없다. 학생 제출의 “AI 채점”은 요청자가 보낸 결과, 수동 점수, WordPress filter, 정답 문자열 일치 규칙을 같은 AI 결과로 저장하는 동기식 경로이며, 평가 계획의 준비 완료 상태와도 연결되지 않는다. 기존 흐름을 확장하기보다 출처를 분리하고 플랫폼 gateway를 사용하는 비동기 평가 실행으로 교체해야 한다.

실행환경 판정: 평가 화면, queue·worker, 입력·출력 schema, 정책, 결과 이력과 교사 검토는 AI 평가 애드온이 소유한다. OJ Platform의 운영 > AI 작업 배정은 provider profile·model·주/대체 routing을 선택하는 설정이며 평가 화면이 아니다. 실제 provider 접근만 플랫폼 AddonAiTaskGatewayV1을 통과한다.

현재 “AI 채점” 흐름

교사 score 클릭
  --> model_key = "manual-or-filtered-ai"
  --> policy_version = "score-v1"
  --> 현재 submission + assignment + attachment metadata 조회
  --> grading input·rubric hash·fingerprint 생성
  --> assessment_run을 곧바로 running으로 생성
  --> Ai_Scoring_Service::score()
       1. request payload.ai_result 그대로 반환
       2. manual_items/items를 AI 응답 형태로 변환
       3. oj_ai_dashboard_ai_score_result filter 반환
       4. 정답 문자열 완전 일치면 만점, 아니면 0점
  --> Scoring_Normalizer가 문항 점수 clamp·합계 계산
  --> raw_ai_response + normalized_result + grading_items 저장
  --> run succeeded
  --> 교사 accept 또는 regrade review
우선순위실제 출처현재 저장 표기판정
1REST 요청의 임의 ai_resultraw_ai_responseAI 아님·주입 가능
2교사가 입력한 rubric click·수동 점수같은 run·result·raw 필드human 출처 혼합
3WordPress filter callback같은 run·result·raw 필드provider 증거 없음
4정답과 답안의 문자열 완전 일치 규칙같은 run·result·raw 필드rule을 AI로 오표기
재현성 오류: ai_result는 grading fingerprint에 포함되지 않는다. 같은 기본 입력에 서로 다른 요청 결과를 보내도 먼저 저장된 결과가 재사용될 수 있다. 반대로 수동 점수는 fingerprint에 추가되지만 출처 유형 자체를 별도 aggregate로 보존하지 않는다.

확정한 목표 결정

  1. 활동지 자체 평가와 학생 제출 평가를 서로 다른 first-class subject·input builder·output schema·normalizer·result aggregate로 구현한다. 활동지 자체 평가는 특정 immutable worksheet revision 전체를 실제 AI가 평가할 수 있어야 한다.
  2. 플랫폼 manifest에는 C28에서 정한 worksheet_quality_assessment와 student_submission_assessment task 2종만 등록한다. OJ Platform은 연결·model routing만, 애드온은 queue·worker·평가·검토 화면과 데이터를 소유한다.
  3. 실제 AI 결과는 플랫폼 AddonAiTaskGatewayV1 성공 응답만 인정한다. request ai_result, WordPress AI filter, direct provider 호출, 정답 규칙·Faker fallback을 AI 성공으로 저장하지 않고 gateway 부재·실패 시 미확정으로 닫는다.
  4. ai, human, rule 평가 출처와 provenance를 분리한다. 공통 review UI에서 비교할 수 있지만 raw 응답·fingerprint·실행 상태를 혼합하지 않는다.
  5. 모든 실행은 immutable subject, input·policy·rubric·prompt·output schema, projector·extractor와 platform routing snapshot의 ID·version·hash를 고정하고 결정적 idempotency key를 사용한다.
  6. REST는 평가를 enqueue하고 애드온 job worker가 lease·attempt·retry·cancel·timeout·rate limit·비용을 관리한다. 브라우저 순차 반복이나 장기 HTTP 요청을 실행환경으로 사용하지 않는다.
  7. AI 출력은 versioned JSON schema로 먼저 검증하고 evidence·confidence·abstain·safety flag를 요구한다. 점수는 canonical 배점으로 서버가 다시 계산하며 schema 오류를 0점으로 바꾸지 않는다.
  8. 평가 계획을 불변 batch definition으로 바꾸고 ready plan revision만 실행한다. platform context·canRoute, published/submission snapshot, 정책·rubric, 첨부 추출, 비용 한도와 공개 정책을 preflight에서 확인한다.
  9. 교사 검토·공식 확정·학생 공개를 분리한다. 재평가는 기존 공식 결과를 유지한 채 원자 교체하고, 연결된 feedback은 stale·recall·재승인을 명시적으로 처리한다. AI가 활동지를 자동 수정·발행하거나 점수·피드백을 자동 공개하지 않는다.
  10. 학생 task의 score, feedback_draft, special_note_draft는 각각 별도 job·output schema·검토 상태를 사용하되 플랫폼 routing 행은 1개를 공유한다. 직접 학생 ID·public file URL·비밀값은 AI payload에 넣지 않는다.
