# Oracle MySQL 8 동시 수집·부하 검증

검증일: 2026-10-28 (한국 시간). 운영 서버와 분리한 로컬 시험이며, 이전 MariaDB 검사를 Oracle MySQL 검사로 대신 표시하지 않습니다.

## 환경과 판정 기준

Oracle 공식 CDN의 ZIP과 공식 MD5 파일을 대조하고 실행 서버의 `VERSION()`·공급자 문자열을 확인합니다. Windows Oracle 실행기의 한글 경로 제약은 전용 폴더를 가리키는 임시 영문 드라이브 별칭으로 해결하며, 기존 DB·시스템 서비스·운영 파일은 사용하지 않습니다. 테스트 계정 암호·토큰·SQL 원문·행 원문은 공개 보고서에서 제외합니다.

학생 전체가 두 페이지를 미리 연 다음 실제 교사의 쿠키·nonce로 일정을 만듭니다. 초기 실행은 실제 그룹·시간 UI, 후속 실행은 메모리 절약을 위해 같은 교사의 API를 사용합니다. 시작 준비와 정상 활동 구간을 분리합니다. 서로 겹친 활동과 다른 그룹의 활동을 함께 만들고, 동시 기록 중 기간 단축·조기 종료를 실행합니다. 실제 제품의 5초 승인 확인·10초 승인 기한과 이벤트 전송·문항 정책은 완화하지 않습니다.

정상 활동·전송 마무리 구간의 5xx·429·요청 시간 초과는 0건, gate p99는 제품의 5초 fetch 기한보다 짧아야 합니다. 1초는 추가 참고 목표입니다. 의도한 권한·개인정보 거부와 페이지 이동에 따른 취소는 별도로 셉니다. ACK된 허용 기록의 손실·중복·그룹 밖 및 종료 경계 밖 저장은 0건이어야 하며, 실제 SQL 자료와 전송 ledger·일별/주간/월간 통계를 대조합니다. p50·p95·p99, 요청 수·오류·취소·재시도도 함께 기록합니다.

부하 브라우저는 headless Chromium의 실제 visibility/focus 값을 그대로 관측합니다. DOM 속성이나 응답을 바꾸지 않고, 학생 모두가 동시에 실제 전경 상태라고 가정하지 않습니다. 실제 OS가 숨긴 탭·휴대전화 절전의 검증과 이 네트워크/저장 부하 검증은 구분합니다. 메모리 여유가 2GiB보다 작으면 새 시험 클라이언트 생성을 중단하고 자원 경계를 실패/제한 결과로 기록합니다.

## 수정 전 재현과 수정 방향

공식 1.1.0에서 서로 다른 학생의 새 세션 INSERT 직전만 동기화한 실제 MySQL 트랜잭션 검사로 교착을 재현했습니다. 두 요청 중 하나는 200, 다른 하나는 503 뒤 재시도로 200이었고, 최종 손실·중복은 없었지만 `lock_deadlocks`가 0에서 1로 증가해 실패로 판정했습니다. 동기화는 WordPress의 query 필터로 실행 순서만 제어하며 SQL·응답을 바꾸지 않습니다. 별도의 일반 다중 학생 실행에서도 503 재시도가 발생해 강제 재현만의 현상이 아님을 확인했습니다.

원인은 새 source prefix에 대한 `SELECT ... FOR UPDATE`의 빈 인덱스 구간 잠금입니다. 서로 다른 학생이 같은 물리적 gap을 읽고 나서 INSERT하면 순환 대기가 생길 수 있습니다. 학생별 개인정보 잠금과 잠금 획득 후의 새 RR snapshot으로 같은 학생의 기록을 직렬화하므로, 이 prefix 조회의 불필요한 범위 잠금을 제거합니다. 소유자·페이지 서명·개인 삭제 경계·활동 시간 재검증과 이벤트 중복 방지는 유지합니다.

이벤트 중복 확인·집계의 잠금 조회에서도 실제 `events.PRIMARY`의 INSERT-intention 대기 cycle을 관측했습니다. 해당 범위 조회는 일반 읽기로 바꾸고, 이미 존재하는 세션만 ID 오름차순의 `WHERE id = ... FOR UPDATE` 기본키 단건 잠금으로 다시 읽습니다. 보관 정리와 경합할 때는 최신 만료 메타데이터를 확인하며, 원시 기록이 만료된 대상 구간은 재생성하지 않고 정책 처리합니다. 같은 페이지의 다른 새 수업 구간은 계속 기록합니다.

정리 작업이 오래된 세션 후보를 읽은 직후 새 heartbeat가 도착하는 경쟁 조건도 재현했습니다. 실제 UPDATE에서 오래된 heartbeat 조건을 다시 확인해 갱신된 세션을 timeout으로 닫지 않도록 수정했습니다. 수정 전 실패와 수정 후 소스 회귀 106개 통과는 별도 로그에 보관합니다.

두 활동이 같은 대기 문항을 지지할 때 동시에 단축하거나 하나를 단축하고 다른 하나를 삭제하면, 실제 활동 둘이 모두 끝난 뒤에도 문항이 pending으로 남는 문제도 실제 Oracle에서 재현했습니다. 기존 DB 버전 행의 정확한 행 잠금으로 교사 일정 변경끼리만 직렬화하고 그 뒤 최신 문맥을 읽도록 수정했습니다. 새 테이블이나 옵션을 추가하지 않습니다. 동일한 세 사례(삭제 둘·단축 둘·단축 후 삭제)는 수정 후 모두 invalidated가 됐습니다. 검증 도구는 실제 PFS 잠금 대기 쌍을 확인하며 단순히 늦게 부팅된 것을 직렬화 성공으로 간주하지 않습니다.

한 학생의 개인정보 삭제에 쓰는 점수 조건도 Oracle `EXPLAIN`으로 조사했습니다. 점수 105행 중 대상은 1행인데 인덱스 없이 전체 스캔을 수행했습니다. 점수표에 `user_id`가 선두인 보조 인덱스를 추가하며, 수정 후 실제 쿼리 계획과 점수·개인 삭제 회귀를 함께 확인합니다.

자동 문항의 첫 발급도 별도로 조사했습니다. 만료된 문항이 없는 학생에게 실행한 범위 UPDATE가 빈 인덱스 gap을 잠근 뒤 새로운 문항 INSERT와 충돌했습니다. 서로 다른 학생 두 명의 실제 `/checks/next`에서 교착을 재현하고, 만료 후보를 먼저 일반 읽기로 찾은 뒤 존재하는 문항 ID만 조건부 UPDATE하도록 수정했습니다. 같은 학생의 quota·발급·응답은 기존 학생 잠금으로 보호합니다. 수정 후 같은 강제 경합은 교착·타학생 직렬화 없이 통과했습니다.

첫 대량 재검사에서는 추가 교착이 남아 전체 통과로 판정하지 않고 실행을 중단했습니다. 이미 저장된 실제 이벤트 네 개와 시작·종료 제어 두 개를 모두 `ON DUPLICATE KEY UPDATE id=id`로 재전송하는 경로였습니다. 값이 바뀌지 않아도 MySQL의 중복 키 쓰기는 잠금을 취합니다. 실제 서로 다른 두 학생이 `events.PRIMARY`의 supremum과 INSERT-intention을 서로 기다리는 cycle을 확인했습니다. 이미 저장한 실제 순번과 제어 순번은 INSERT에 보내지 않고 패킷 내부 중복도 제거하도록 수정했습니다. 전체 재전송이어도 새 종료 플래그·시간 상한·활동 연결은 갱신하며, 시간 수정으로 옮겨진 구간에 빈 행을 만드는 일은 막습니다. 수정 전·후의 짧은 동일 조건 재현과 마지막 전체 재검사는 분리해 보관합니다.

수정본에서 학생 60명의 실제 문항 next 120회, 응답 100회, 종료 뒤 next 60회를 280개 독립 PHP 프로세스로 실행했습니다. 같은 학생의 두 요청은 동일한 한 문항·일일 발급 한 건으로 유지됐고, 응답 재전송은 멱등 처리됐습니다. 답하지 않은 열 명의 문항은 활동 종료로 취소되고 종료 뒤에는 새 문항을 발급하지 않았습니다. 비공개 정답 미노출·오답의 집중 점수 비반영과 원시 활동 불변, 교착 0건도 확인했습니다. 이 검사는 내부 REST이며 아래 브라우저·HTTP 부하와 구분합니다.

최종 전체 실행 중 UTC 02:02:40~02:04:40의 별도 120초 읽기 전용 관측에서 전역 교착 증가는 0이었습니다. 잠금 표본 238개, 전역 행 잠금 대기 404회·누적 18,994ms는 남아 있으며, 포착한 대기 표본 42건은 모두 옵션 테이블이었습니다. 이벤트 테이블 대기는 이 표본에서 관측되지 않았습니다. 이후 관측 도구의 동일 fingerprint 중복 slot 집계 누락을 발견해 기존 statement 호출 수·누적 SQL 시간의 정밀 주장은 철회합니다. 그 오류는 전역 교착·행 잠금 수치와 실제 이벤트 SQL 대조를 바꾸지 않습니다. 전체 실행의 최종 판정과 이 표본은 구분합니다.

최종 전체 실행은 학생 60명·학생당 두 탭 패킷·두 라운드의 독립 PHP 작업 1,047개를 끝까지 실행하고 44개 조건을 통과했습니다. 최종 교착 증가도 0건이었습니다. 동일 순번 재전송·추가 기록·교사 점수/월간 조회와 시간 수정·조기 종료·개인정보 삭제·보관 정리·계정 삭제를 겹쳤습니다. 이벤트 순번·내용·리비전, 그룹 분리, 삭제한 자료의 재생성 방지·다른 학생 보존, 보관 집계와 누적 시간 합집합을 실제 SQL로 대조했습니다. PHP 부팅 뒤의 내부 REST 검사이며 실제 HTTP 지연과 구분합니다.

내부 REST는 1,085회, 직접 개인정보·정리 작업은 7회였습니다. 503은 0건이며 일반 수집 960작업과 교사의 시간 수정·조기 종료는 재시도 0회였습니다. 개인정보 삭제 중 의도적으로 보낸 요청 14회는 정상 보호 응답 423을 받고 이후 재시도했습니다. 삭제 중 차단을 서버 오류나 무손실 수집 성공으로 바꿔 세지 않습니다. 기존 월간 활성 90,000ms에 새 독립 합집합 60,000ms를 더한 150,000ms를 대조했습니다.

## 실제 HTTP·브라우저 준비 결과

처음 실제 Chrome 10명 단계를 준비할 때 PHP 12개 환경은 브라우저 실행 전 가용 메모리 2,340MiB에서 교사 로그인 뒤 1,910MiB로 줄어 학생을 추가하지 못했습니다. PHP 4개 환경은 2,484MiB에서 교사 로그인 뒤 2,083MiB, 학생 한 명의 두 페이지 준비 뒤 1,780MiB가 되어 그 학생 context를 즉시 닫았습니다. 두 시도 모두 확정 학생 0명·활동 생성 0·기록 수집 0이며 부하 통과가 아닙니다. 각 시도의 교착·SQL 오류 증가는 0이지만 수집 부하 성공의 근거로 사용하지 않습니다. 다른 사용자의 앱을 닫거나 메모리 안전선을 낮추지 않았습니다.

첫 HTTP 준비 시도는 학생 네 명의 실제 로그인·자료 페이지 200을 확인한 뒤 그룹 제출 화면 400으로 중단했습니다. `/submit/{id}` 자체는 정식 경로지만 이 설치에는 그룹 제출의 Blockly 문맥 provider가 없어 플랫폼이 “수업·대회·그룹 Blockly 설정을 확인할 수 없습니다.”로 거부했습니다. URL 모양만 바꿔도 같은 결과였습니다. 같은 그룹의 공개 문제 상세 화면은 200·정확한 학생·서명·문제 분류를 반환했습니다. 두 번째 채널을 이 지원 화면으로 바꾸고 실제 Chrome도 HTTP 200을 확인하도록 시험 도구를 수정했습니다. 임시 MU 도구는 SQL 원문을 내보내지 않고 WordPress의 query 개수·시간 합과 hook 경과 시간만 집계했습니다. 단일 요청은 PHP 진입 후 297.659ms 중 SQL 41개·20.972ms였고, plugin main 파일 로드 뒤 `plugins_loaded` callback 구간이 180.982ms였습니다. 120파형의 PHP 요청 경과 시간 합은 86,392ms, query 합은 4,139ms(약 4.8%), 같은 callback 구간 합은 61,457ms였습니다. 각 요청은 파일 1,793개를 포함했습니다. 이 구간에는 여러 플러그인의 callback이 있어 한 함수나 Focus만의 비용으로 단정하지 않습니다. 진단이 끝난 뒤 임시 SAVEQUERIES 설정과 MU 파일을 제거하고 `wp-config.php` 원본 SHA-256 복원을 확인했습니다. 실제 교사의 쿠키로 진단 일정 두 개만 삭제하고 다른 활동 목록을 보존했습니다. 정상 부하 검사는 이 계측을 끈 구성에서만 실행합니다.
