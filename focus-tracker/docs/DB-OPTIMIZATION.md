# DB 조회·갱신 최적화 — 1.1.2

검증일: 2026-10-28. 공식 1.1.1 ZIP과 개선 소스를 같은 전용 WordPress 7.1·PHP 8.3.33·Oracle MySQL Community 8.0.46에서 비교했습니다. OJ Platform은 2.5.5입니다. SQL 절감과 30~60명 HTTP 부하 통과는 다른 판정입니다.

## 원인과 측정 결과

앞선 HTTP 시험의 주된 비용 범위는 PHP 초기화·실행과 upstream 대기였습니다. 단일 요청의 PHP 구간 297.659ms 중 SQL은 20.972ms였고, 120개 단발 요청에서도 SQL 합은 PHP 경과 시간 합의 약 4.8%였습니다. 계측 자체의 비용과 다른 플러그인 초기화도 포함돼 DB만의 문제나 Focus만의 비용으로 단정하지 않습니다.

다만 불필요한 반복 조회·저장도 확인돼 다음과 같이 줄였습니다.

| 실제 Oracle의 동일 작업 | 1.1.1 SQL | 1.1.2 SQL |
|---|---:|---:|
| 그룹 페이지 승인 확인 | 6 | 4 |
| 학급 페이지 승인 확인 | 6 | 5 |
| 일반 페이지 승인 확인 | 6 | 6 |
| 60명 과거 활동 강제 점수 계산 | 431 | 195 |
| 60명 과거 활동 캐시 점수 조회 | 307 | 130 |
| 진행 중 자료 없음 60명 점수 조회 | 367 | 130 |
| 한 학생 월간·이전 기간 통계 최초/반복 | 287 | 47 |

표는 WordPress가 부팅된 뒤 내부 REST 처리의 SQL 개수입니다. 부팅 SQL 20개와 계정 로딩은 별도이며 전체 HTTP 요청 개수가 아닙니다. 최종 소스 38조건과 원본 업무 결과 SHA 8개가 일치했습니다. 승인 비교는 분당 진단 옵션을 동일하게 예열했습니다. 진행 중 점수는 불필요한 UPSERT 60회가 없어졌습니다.

재전송의 원시 프로필은 31→22 SQL이었고, 별도 예열한 개선본은 18 SQL이었습니다. 그 예열 결과에서 이벤트·참여·활동 연결·점수표 쓰기는 0회이며, 개인정보 보호와 요청 한도에 필요한 옵션 쓰기 두 번은 유지했습니다. 예열 상태가 다른 숫자로 지연 개선율을 계산하지 않습니다.

과거 일정 10,000개를 넣은 실제 일정 조회는 table scan 10,003행에서 `context_end_window` range scan 2행으로 바뀌었고, 반환한 활동 ID가 같았습니다. 개선본 계획의 해당 구간은 약 0.0245ms였으며 전체 요청 시간이 아닙니다.

## 변경한 방식

- 서명된 그룹 화면은 그룹 소속만, 학급 화면은 학급 소속만 조회합니다. 일반 화면은 둘 다 확인하고 소속은 매 요청 새로 읽습니다.
- 승인된 명단의 참여·점수 캐시를 100명씩 읽습니다. 계산이 필요한 이벤트만 묶으며 리비전 기준 예상 10,000행 예산을 넘는 학생과 이전 리비전 0 기록은 단건 처리합니다. 수동 DB 변조까지 막는 절대 행수 상한은 아닙니다.
- 재사용하지 않는 진행 중 점수는 반환만 합니다. 최종 점수와 보관 작업의 스냅샷은 저장 성공을 계속 확인합니다.
- 점수와 타임라인이 같은 요청의 참여·이벤트 원본을 공유합니다. 표시할 WordPress 사용자 정보도 승인된 명단만 묶어 읽습니다.
- 통계 메타데이터는 한 요청·개인정보 트랜잭션 안에서 최대 7일씩 읽습니다. 원시 이벤트는 기존 일별 조회 범위를 유지합니다.
- 새 계산 결과·원본 서명·보관 상태가 모두 같을 때만 일별 UPSERT를 생략합니다. 문항 상태가 바뀌면 같은 이벤트 서명이어도 반영하며, 서명만으로 진행 통계를 캐시하지 않습니다.
- 수집의 종료·heartbeat·리비전·누락 표식은 변경된 필드만 한 UPDATE로 저장합니다. 재전송이어도 새 final 플래그와 바뀐 시간표는 처리하고 기존 활동 연결은 다시 INSERT하지 않습니다.
- 실제 변경이 있는 활동만 모아 기존 점수 PK를 읽고 그 PK만 삭제합니다. 빈 범위 DELETE와 원시 만료 스냅샷 삭제를 피합니다.
- `(context_type, context_id, ends_at, starts_at)` 인덱스를 추가합니다. 기존 시작 시각 인덱스는 유지하고 저장소 건강 검사가 새 인덱스까지 확인합니다.

권한·일정의 장기 캐시, 승인 기한 연장, 이벤트 표본 수집은 추가하지 않습니다. 개인정보 잠금 획득 전 RR snapshot을 여는 최적화도 하지 않습니다.

## 검증 범위

별도 SQLite의 61일 자료·문항 fixture에서는 월간+이전 월이 최초 488→182 SQL, 동일 반복 488→121 SQL이었습니다. 반복 일별 UPSERT는 61→0, 원시 이벤트 조회는 61회를 유지하고 응답 전체 SHA가 같았습니다. 문항 `pending`→`correct` 변경도 같은 이벤트 서명에서 해당 날짜만 다시 저장했습니다. 이 fixture와 위 Oracle 자료는 양이 달라 서로 같은 작업으로 비교하지 않습니다.

실제 Oracle에서 개인정보 삭제 후 옛 outbox 차단·새 기록 허용, 일정 변경 사이의 유효 기록 저장·시간 밖 정책 처리를 21조건으로 확인했습니다. 별도 repository 경합 17조건에서는 빈 점수 무효화가 다른 학생의 직접 최종 캐시 INSERT를 막지 않고, 기존 PK만 삭제하며 다른 학생·보관 자료를 보존했습니다. 추가 두 번째 개인정보 잠금 구성은 timeout을 만나 이 17조건의 증명에서 제외했습니다. 이 검사는 repository 범위이며 교사 HTTP 동접 성공이 아닙니다.

새 회귀는 재전송의 학습 표 쓰기 0, 단일 메타데이터 UPDATE, final-only 재전송, 기간 단축, 실패 시 전체 rollback, 개인정보 기준값의 새 조회·오류 차단을 확인합니다. 인덱스 생성에 실패하면 DB 버전을 올리지 않고 API를 중단합니다.

30~60명·학생당 여러 탭의 전체 수업 성능은 운영과 같은 PHP-FPM·OPcache·하드웨어에서 다시 측정해야 합니다. 이번 SQL·스캔 행수 개선은 그 시험을 대신하지 않습니다. 원시 이벤트의 증분 집계나 플랫폼 초기화 축소는 별도 설계 범위입니다.
