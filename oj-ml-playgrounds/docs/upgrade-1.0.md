# 기존 버전에서 1.0.0으로 업데이트

rc.1/rc.2의 스키마 3에서 업데이트할 때에는 DB 업데이트가 필요합니다. 스키마 4는 평가의 항목별 스냅샷 저장 컬럼을 추가하며 기존 평가·제출물을 유지합니다. **이미 스키마 4인 rc.3~rc.6에서 1.0.0으로 업데이트할 때에는 추가 DB 변경이 없습니다.** 정식 1.0.0은 RC6의 실행 코드·내장 번들을 유지하는 메타데이터·문서 승격입니다. 페이지 내 삭제 확인·취소, 지속되는 결과 안내, 단일 삭제 응답 처리와 다중 탭 잠금 순서, OJ 개인정보 URL 상속을 유지합니다. rc.5의 영수증 UTC ISO 8601 반환과 서버 횟수 재조회도 유지하며 기존 시도 차감 정책은 변경하지 않습니다. [rc.3 기능 안내](workflow-rc3.md)에 양식·루브릭·CSV와 명시적 반려 재검토 절차가 있으며, 화면 확장은 [화면 모드 안내](display-modes.md)를 참고하세요. 기존 반려 제출을 업데이트만으로 자동 재검사하지 않습니다.

운영자와 합의한 시간에 교체하고 설치 버전·스키마·운영 진단과 기존 기록을 확인합니다. 서버 관리·로그·백업·복원은 운영자 직접 수행으로 인계했으며 아래 일반 절차는 관리 경로나 백업 위치 제출을 다시 요구하지 않습니다. 합의한 기관용 기술 인수는 통과했고 정확한 범위·한계는 [기술 승인 기록](release-1.0.md)을 따릅니다.
내장 실습 앱의 업스트림 기준은 **ML Playgrounds 0.12.1+OJ 패치**, 플러그인 DB 버전은 **4**입니다. PHP 8.3 이상을 사용합니다. RC6 검증 번들을 1.0.0에 유지하며 RC5 이하의 구번들과 혼합하지 않습니다.

승인 기준 시험 서버 **OJ dev.107 / ML RC6 / 스키마 4**에서 G1 실제 삭제·다중 탭 종료·재로그인 후 미노출·서버 자료 보존을 통과했습니다. 이 문서는 정식 패키징 시점의 기록이며 실제 1.0.0 설치 결과와 최신 서버 상태는 배포 폴더의 외부 검증 기록을 따릅니다. 새 ZIP의 SHA-256은 함께 제공되는 **1.0.0 `.sha256` 및 검증 기록**과 대조합니다. 기존 RC4·RC5·RC6 동결 ZIP은 재포장하지 않으며 이전 후보의 해시를 1.0.0 검증 값으로 사용하지 않습니다.

## 업데이트 순서

1. 수업 외 시간을 잡고 학생에게 제출·로컬 데이터 정리를 안내합니다.
2. 웹 요청을 점검 페이지로 전환하고 실행 중인 제출·평가가 끝날 때까지 기다립니다. WP-Cron, 시스템 cron과 별도 복구 작업도 중지합니다.
3. WordPress DB 전체와 비공개 제출물, wp-config.php의 설정·인증 SALT, 기존 플러그인 ZIP을 같은 시점으로 백업합니다. 백업은 웹 루트 밖에 보관합니다.
4. 기존 8개 oj_ml_* 테이블이 InnoDB인지, 단일 WordPress 설치만 이 DB를 쓰는지 확인합니다. 기존 자료에는 처음 업그레이드하는 사이트의 테이블 prefix가 소유자로 기록됩니다. 공유 DB에서 먼저 실행하여 소유권을 선점하지 마세요.
5. WordPress의 플러그인 업로드 교체 기능으로 `oj-ml-playgrounds-1.0.0.zip` 전체를 교체합니다. 폴더명은 반드시 `oj-ml-playgrounds`입니다. 전달받은 ZIP의 SHA-256을 1.0.0 `.sha256` 및 검증 기록과 먼저 대조합니다. 교체 직후 PHP-FPM/OPcache와 WordPress·프록시·CDN·브라우저 캐시를 비우고 작업을 보존한 기존 실습 탭을 모두 닫은 뒤 새로 엽니다. 부모 JavaScript만 바꾸거나 구버전 내장 앱을 남겨 두지 않습니다.
6. OJ 콘솔 **교사 메뉴 › ML 실습 › 설정**의 서버 상태에서 DB 스키마를 확인합니다(1.1.0부터 WordPress 도구 메뉴의 운영 화면은 없습니다). 스키마가 4보다 낮을 때만 **DB 업데이트 및 검증**을 실행합니다. rc.3~rc.6에서 이미 스키마 4라면 1.0.0 설치를 위한 추가 DB 업데이트는 없으며, 상태 검사와 대조만 수행합니다. WordPress 루트의 CLI에서는 다음 명령을 사용합니다.

```bash
# 스키마가 4보다 낮을 때만 실행
sudo -u www-data wp oj-ml migrate

# 스키마 4에서도 상태와 파일 대조를 위해 실행
sudo -u www-data wp oj-ml doctor
sudo -u www-data wp oj-ml reconcile
```

7. OJ Console → ML 실습 설정에서 용량과 개인정보 URL을 확인합니다. 별도 ML 주소가 비어 있으면 정상 연결된 OJ Platform `/privacy`를 이어받으며 기존 유효한 기관 필터·별도 주소의 우선순위는 유지합니다. 링크 상속이 문서를 새로 게시하거나 보존 정책을 동기화하지는 않습니다. 현재 서버의 `/privacy` 게시 문서 없음 관찰도 RC6 설치만으로 해소되지 않습니다. 기존 과제의 100 MiB 정책이 있어도 운영 한도가 기본 25 MiB이므로, 더 큰 제출을 계속 받으려면 운영 한도와 PHP·Nginx를 함께 조정하세요.
8. 플러그인 버전 1.0.0과 관련 자산의 갱신을 확인합니다. PHP와 프런트 자산이 섞여 있으면 시험을 진행하지 말고 전체 ZIP·캐시 상태를 다시 확인합니다.
9. 학생·교사 테스트 계정으로 직접 제출, 전체 이력, 안전 바로보기, 평가 비공개/공개, 개인 연장과 과제 재개를 시험합니다. 같은 제출의 영수증 시각과 결과 화면 시각, 새 시도 생성·직접/파일 제출 성공 뒤 서버와 일치하는 최대·사용 횟수, 동일 iframe 유지도 확인합니다.
10. 새 환경이나 삭제 관련 변경이 있으면 아래 삭제 검사를 합성 자료로 수행하고 결과를 기록합니다. 점검 페이지와 cron 중지는 운영자 절차에 따라 해제합니다. 현재 사이트의 합의 범위 기술 인수 통과와 새 환경의 검수는 구분하며, 제외한 수업 규모·운영 복원 검사를 통과로 표시하지 않습니다.

### 설치 환경의 삭제 유지 검사

1. 시험 계정·로컬 프로젝트·기존 서버 제출을 식별하고 같은 계정으로 실습 탭 두 개를 엽니다. 페이지 내 삭제 확인창에서 먼저 **취소**하여 프로젝트 보존과 삭제 미실행을 확인합니다.
2. 대상을 다시 확인한 뒤 **로컬 데이터 삭제**를 명시적으로 누릅니다. 실제 성공 응답 뒤 성공 안내가 유지되고 자동 새로고침이나 오류 문구로의 교대가 없어야 합니다.
3. 다른 탭의 이전 프로젝트 저장이 중단되고, 새로고침·재로그인 뒤 삭제한 프로젝트가 재노출되지 않는지 확인합니다. 서버의 접수 사본·평가, 다른 계정 자료와 다운로드 파일은 유지돼야 합니다.
4. 잠금·DB 연결 때문에 삭제가 막히거나 시간이 초과되면 삭제 결과 미확인으로 남깁니다. 구현은 배타 잠금 요청 대기 → 저장 권한 폐기 → 기존 공유 잠금 해제 → 삭제 순서를 사용하며, 이미 시작한 IndexedDB 요청은 완료 전 잠금을 조기에 놓지 않습니다. UI 시간 초과를 DB 삭제 취소 또는 완료로 해석하지 않습니다.

이 목록은 새 환경의 검사 절차입니다. 현재 사이트에서는 RC6의 식별된 빈 시험 프로젝트로 취소 보존·명시 삭제·두 탭 종료·재로그인 후 미노출과 기존 서버 자료 보존을 실제 확인했습니다. 정식 1.0.0은 같은 실행 코드·번들을 유지하지만 모든 데이터 크기·환경의 시험을 대신하지는 않습니다.

## 마이그레이션 특성

- 1/2/3 → 4는 컬럼·인덱스 추가 방식이며 원본 제출물과 평가를 지우지 않습니다.
- 스키마 4 설치 → 1.0.0은 스키마 변경이 없으므로 버전 4를 다시 설치하기 위한 DDL이 필요하지 않습니다.
- DB advisory lock으로 중복 업데이트를 거부합니다.
- 테이블 엔진, 필수 열·핵심 인덱스를 확인한 뒤에만 버전 4를 기록합니다.
- 업데이트가 중단되면 같은 명령을 다시 실행할 수 있습니다. 실패 원인을 확인하기 전에 버전 옵션을 손으로 4로 올리지 마세요.
- 일반 학생 요청은 DDL을 실행하지 않고 업데이트가 필요하다고 응답합니다.
- 멀티사이트 또는 다른 설치가 소유한 DB에서는 동작을 차단합니다.
- 마이그레이션 전 MyISAM 테이블을 발견하면 자동 변환하지 않습니다. 먼저 DB 관리자와 백업·변환 작업을 진행합니다.

## 1.0 이후 백업과 복원

운영 설정의 **실습 점검 모드**는 새 시도·제출·평가와 자동 검사를 중지합니다. 브라우저의 로컬 학습은 계속될 수 있고 실행 중인 PHP 요청까지 즉시 취소하지는 않습니다.

1. 점검 모드를 켜고 실행 중인 요청이 끝났는지 확인합니다. 동시에 관리자 설정 변경·개인정보 삭제·CLI 정리도 하지 않습니다.
2. `wp oj-ml manifest`로 보관 파일의 크기·SHA-256 목록을 비공개 exports 폴더에 만듭니다.
3. DB 전체와 비공개 디렉터리를 함께 백업합니다. 인증 SALT도 별도 안전한 장소에 보존합니다. 한쪽만 백업하면 정상 복원을 보장할 수 없습니다.
4. 격리된 복구 사이트에 DB·파일·동일 버전 코드를 복원합니다.
5. `wp oj-ml doctor`와 `wp oj-ml reconcile`을 실행해 missing/corrupt가 0인지 확인하고, 파일 manifest와 학생·교사 결과를 대조합니다.
6. 점검 모드를 해제하고 학생 제출을 재개합니다. 자체적으로 생성한 exports 사본과 오래된 백업은 기관 정책에 따라 별도 정리합니다.

DB 덤프에는 WordPress 사용자·비밀 설정도 포함될 수 있으므로 공개 다운로드 링크나 이메일 첨부로 배포하지 않습니다.

## 롤백

코드만 0.2.9로 덮어쓰지 마세요. 새 기능의 데이터가 구버전과 일치하지 않을 수 있습니다.

- 점검 상태에서 업데이트 직전의 **DB·비공개 파일·플러그인 코드 세트**를 함께 복원합니다.
- 업데이트 이후 새로 받은 제출은 기존 백업에 없습니다. 별도 보존·정합성 확인 없이 삭제하거나 덮어쓰지 않습니다.
- OPcache와 프록시 캐시를 비우고 학생별 제출 수·SHA-256·공개 점수를 대조한 후 서비스를 엽니다.

## 설치 파일이 없다는 오류

ZIP 내부가 `oj-ml-playgrounds/oj-ml-playgrounds.php`인지 확인합니다.
`oj-ml-playgrounds-1.0.0/oj-ml-playgrounds/`처럼 중첩되거나 버전명이 설치 폴더에 붙으면 안 됩니다.
기존 폴더를 수동 삭제하기 전에 DB와 비공개 저장소를 백업하고 WordPress의 ZIP 교체 절차를 사용하세요.

## 검증 기록 구분

RC6의 소스·번들·패키지 검증과 이후 실제 서버 G1 인수는 각각의 검증 기록을 따릅니다. 1.0.0은 실행 코드·번들을 유지하며 최종 소스·패키지·실제 설치 결과는 배포 폴더의 외부 검증 기록으로 구분합니다. 아래 RC4·RC5 기록은 당시의 역사적 증거이며 새로운 시험이나 현재 승인 조건으로 확대하지 않습니다.

동결 rc.4 ZIP 추출본은 WordPress 7.1 + PHP 8.3.33 + MariaDB 11.4.10 신규 격리 DB에서 통합 검사 123/123을 통과했습니다. 이는 신규 스키마와 스키마 3 형태의 fixture 업데이트를 확인한 로컬 기술 증거입니다. 실제 기관 DB와 비공개 저장소의 백업·업데이트·롤백·복원 성공을 뜻하지 않습니다.

9월 9일 초대 접근 장애는 9월 10일 오전 dev.102 확인 후 두 시험 계정의 수락으로 해소했습니다. 저녁 실제 사이트의 ML rc.4에서는 직접 제출·재제출·교사 안전 보기·평가 공개·학생 확인과 타 학생 차단을 확인했습니다. 다만 저녁 시험 내내 OJ 플랫폼 빌드를 고정 확인한 것은 아닙니다. 20:23 KST에는 서버가 dev.103을 표시했으며 전환시각은 미확인입니다.

rc.5 발행 당시 로컬 회귀 34개와 dev.102 공개 API 계약 검사는 통과했습니다. 이후 dev.103 고정 ZIP을 확보했지만 서버 설치 파일 전체와의 바이트 대조는 수행하지 않았습니다. 당시에는 ML rc.5 설치와 현장 재시험이 남아 있었고 운영 백업 복원·36명 시험을 승인 조건으로 논의했습니다. 이후 RC5 설치 및 dev.107 서버 확인과 승인 범위 조정이 있었으므로, 과거의 미설치 표현이나 넓은 승인 조건을 현재 요구로 사용하지 않습니다. 자세한 시점별 증거는 RC5 외부 검증 기록, 최신 인계 범위는 [기술 승인 기록](release-1.0.md)을 따릅니다.
