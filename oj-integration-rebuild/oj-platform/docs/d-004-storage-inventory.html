OJ Platform 재정비 기준 · D-004

데이터 저장소 재정비

이 문서는 저장 위치를 나열하는 데 그치지 않고, 테이블 이름·기능별 소유권·설정 저장 위치·데이터 이전 절차를 재정비하기 위한 기준서다. 실제 변경은 운영 DB 읽기 전용 보고서와 백업·복구 시험을 승인한 뒤 실행한다.

핵심 결론: 플랫폼 DB 모듈과 Judge DB 모듈은 코드상 분리됐지만 데이터 구조 정리는 아직 끝나지 않았다. 플랫폼 테이블 31개에는 여전히 WordPress 접두어와 oj_가 붙고, 사용자 데이터는 WordPress·플랫폼 사용자 테이블·사용자 메타·Judge 사용자 사이에 중복되어 있다.

재정비 기준이 되는 실제 저장 위치

모듈 분리는 별도 데이터베이스 생성을 뜻하지 않는다.

연결 구조 확인
1 · WordPress 연결

$wpdb

WordPress 핵심 테이블, 플랫폼 전용 테이블 32개, 옵션, 사용자 메타, 게시판·공지와 첨부파일 메타를 저장한다.

2 · Judge 연결

같은 DB 또는 외부 DB

mode=same이면 WordPress 연결을 공유하고, mode=external이면 별도 접속 정보로 Judge DB에 연결한다.

3 · 파일 저장

WordPress 업로드·Judge 경로

AI 지침, Blockly 자원, 오류 로그는 업로드 경로를 사용하고 문제 테스트데이터는 설정된 Judge 데이터 경로를 사용한다.

외부 Judge DB 이름이 jol이고 WordPress가 다른 DB를 사용한다면 jol에 WordPress 테이블이 보이지 않는 것이 정상이다. 플랫폼 전용 테이블은 항상 WordPress 연결 쪽에 설치되고 Judge DB에는 자동 설치되지 않는다.

재정비 대상 비테이블 저장소

옵션, 메타와 파일도 데이터 소유권에 포함한다.

저장 방식 분류
기능 설정 옵션 16개

사이트·홈·DB·가입·메일·제출·AI·게시판·Blockly·시스템·이전·공개 메뉴 설정이다. 현재 기본값과 정규화가 모두 Settings_Repository에 모여 있다.

운영 상태 옵션

기능 플래그, 경로 서명, 모듈별 활성 스키마 맵과 버전, 역할 버전, 설치 상태, DB 상태, 이전 상태, 암호화 비밀값과 오류 상태를 WordPress 옵션에 저장한다. 스키마 맵은 사용자 식별자 매핑이 아니라 각 소유 모듈의 Repository가 사용할 물리 스키마 버전만 기록한다.

WordPress 사용자·메타

wp_users.ID와 함께 oj_user_id, 소속, 닉네임, 생년월일, 제출·정답 수가 사용자 메타에도 중복 저장된다.

글·댓글·미디어

oj_board_post와 oj_notice 글 유형, 글·댓글 메타, WordPress 미디어 첨부를 Board가 소유한다.

AI·Blockly 파일

AI 지침과 변경 기록은 uploads/oj-platform, Blockly 자원은 uploads/oj-platform/blockly에 저장된다.

문제 테스트데이터·오류 로그

테스트데이터는 설정된 Judge 경로를 사용하고 오류 로그는 업로드 경로의 oj-platform-fatal.log에 기록될 수 있다.

테이블의 접두어 제거 원칙은 플랫폼 전용 물리 테이블에 적용한다. WordPress 옵션·메타·글 유형과 capability·액션·훅은 전역 이름 충돌을 막기 위해 기존 oj_platform_ 또는 oj_ 네임스페이스를 유지한다. 플러그인 슬러그·PHP 네임스페이스와 관리자 경로 /oj-console도 유지한다.

저장소 재정비 선결 과제

코드에서 확인된 사실을 위험도 순으로 정리했다.

8개

  1. D4-F01 · 플랫폼 테이블 명명 불일치

    높음

    31개 테이블이 아직 WordPress 접두어와 oj_를 사용한다. 단순 매핑 변경은 새 빈 테이블을 만들 수 있으므로 데이터 복사·검증·전환 절차가 먼저 필요하다.

  2. D4-F02 · 사용자 단일 ID 전환 미구현

    높음

    oj_user_id는 테스트를 제외한 운영 PHP 41개 파일의 662개 행에서 확인되고 플랫폼 스키마에는 해당 열이 8개 남아 있다. 테스트 계약 파일 1개·1개 행은 운영 참조 수에서 제외한다. 같은 행의 중복 출현을 포함한 단순 문자열 출현 수가 아니라 일치 행 수를 기준선으로 사용한다. wp_user_id와 문자열 로그인 ID가 함께 사용되어 WordPress ID 단일화는 아직 적용되지 않았다.

  3. D4-F03 · 사용자 원본 중복

    높음

    현재 oj_users가 로그인 ID, 이메일, 비밀번호, 닉네임까지 보관하고 같은 값 일부를 WordPress 사용자 메타에도 복제한다. 목표 구조인 user_profiles와 다르다.

  4. D4-F04 · 스키마 설치 책임 과밀

    중간

    하나의 설치기가 32개 테이블 생성과 기존 열·테이블 이전을 모두 실행한다. 기능 소유자, 테이블별 버전과 선택 기능 상태가 스키마 계약에 기록되지 않는다.

  5. D4-F05 · 이전 실패 판정과 복구 부족

    높음

    일부 이전이 실패해도 전체 상태를 성공으로 기록하고 스키마 버전을 올릴 수 있다. 여러 저장소를 바꾸는 문제 번호 변경과 사용자 삭제도 전체 작업을 되돌리는 복구 지점이 없다.

  6. D4-F06 · 설정 데이터 소유권 집중

    중간

    기능별 화면과 저장 처리는 분리됐지만 16개 옵션의 기본값·정규화는 Settings에 집중되어 있다. 기능 변경 때 소유 모듈과 중앙 저장소를 함께 수정해야 한다.

  7. D4-F07 · 소유 모듈을 우회한 직접 조회

    중간

    Ranking·Submissions·Contests가 사용자 테이블을 직접 읽고 LearningDashboard가 문제 메타데이터를 직접 읽는다. 읽기 계약이 없어 스키마 변경 영향이 여러 모듈로 퍼진다.

  8. D4-F08 · 민감 파일의 공개 업로드 경로 사용

    높음

    AI 지침·변경 이력과 오류 로그가 웹에서 공개될 수 있는 업로드 루트 아래에 있다. Apache용 차단 파일만으로는 모든 서버 구성을 보호할 수 없다.

저장소 재정비 목표 구조

확정된 원칙을 실제 저장 구조로 옮기는 기준이다.

확정

  1. D4-R01 · 플랫폼 물리 테이블 이름 단일화

    WordPress 접두어와 oj_를 모두 제거한다. 논리명과 물리명을 같게 하되 예약어 충돌이 있는 groups는 learning_groups, 중복 사용자 원본인 users는 user_profiles로 바꾼다.

  2. D4-R02 · 스키마 등록과 데이터 소유 분리

    각 기능 모듈이 테이블 정의·버전·보존 정책과 정책 승인 버전을 등록하고 PlatformDb는 설치 순서, 상태 검사와 이전 실행만 조정한다. 개인정보에 영향을 주는 물리 명세는 목적·근거·기간·익명화·삭제·복구·책임자 정책표 승인 뒤 확정한다. JudgeDb는 외부 테이블을 만들거나 삭제하지 않는다.

  3. D4-R03 · wp_users.ID 단일 사용자 키 적용

    user_id는 로그인 아이디가 아니라 숫자 wp_users.ID를 뜻하며 user_profiles.user_id도 이를 기본키로 사용한다. 로그인 아이디·이메일·비밀번호·표시 이름·별명은 WordPress가 소유하고 user_profiles는 소속·생년·OJ 플랫폼 이용 상태 같은 전용 확장 정보만 소유한다. Judge 로그인 ID·비밀번호·이메일은 플랫폼 테이블과 사용자 메타에 남기지 않고 WordPress 계정이 없는 로그인 전환 절차에서만 일회성으로 읽는다.

  4. D4-R04 · 기능별 설정 계약

    공통 옵션 저장기는 단순 읽기·쓰기만 제공한다. 기본값·검증·정규화·변경 권한은 Auth·Submissions·Board·Blockly 등 각 기능 소유 모듈이 담당한다. AI 관련 설정은 Problems의 문제 메타데이터·문제 초안·테스트케이스 정책, AI Feedback의 제출 피드백 정책, Settings의 연결 프로필과 작업별 배정 정책으로 구분한다. 연결과 배정은 서로 다른 WordPress 옵션과 revision을 사용하고 플랫폼 테이블은 추가하지 않는다.

  5. D4-R05 · 소유 모듈의 읽기 서비스 사용

    사용자 프로필과 문제 메타데이터는 소유 모듈의 읽기 계약으로 제공한다. 문제 주제 검색은 D-008 목표 구조의 problem_topic_links와 WordPress 비공개 분류 oj_problem_topic를 읽는 Problems 소유 사전 서비스를 통해 제공하고 JSON 문자열 직접 검색을 금지한다. 새 표준 주제는 최고 관리자 전용 Policy를 통과한 명시적 생성 명령으로만 추가한다. 이전 도구처럼 여러 저장소를 바꾸는 기능만 명시적인 조정 서비스와 감사 기록을 사용한다.

  6. D4-R06 · 기능 OFF와 데이터 보존 분리

    기능을 끄면 읽기·쓰기는 차단하지만 테이블과 데이터는 유지한다. 비활성 기능의 테이블 누락은 전체 시스템 오류가 아니라 해당 기능 상태로 표시하고 삭제는 별도 백업·확인 작업에서만 허용한다.

  7. D4-R07 · 비공개 파일 저장소 도입

    AI 지침·변경 이력과 오류 로그는 공개 URL이 없는 서버 경로로 옮긴다. Blockly 자원과 게시판 첨부처럼 브라우저 제공이 필요한 파일만 WordPress 업로드에 둔다.

  8. D4-R08 · 추가·복사·검증·전환 순서 준수

    새 테이블 생성, 사전 복사, 해당 소유 모듈의 쓰기 동결·최종 차이 복사, 건수·키·고아 참조 검증, 모듈별 읽기·쓰기 원자 전환, 7일 관찰, 이전 구조 제거 순서로 진행한다. 다른 모듈은 자기 활성 스키마를 계속 사용하며 실패한 단계에서는 해당 모듈 버전을 올리지 않는다.

  9. D4-R09 · 서비스 담당 범위 데이터 분리

    수업은 classes.owner_user_id와 class_instructors, 대회는 contest_settings.owner_user_id와 contest_managers, 문제는 problem_ownerships와 problem_collaborators가 소유·담당 관계를 저장한다. 모든 사용자 참조는 숫자 wp_users.ID를 사용하고 AI 메타데이터·Judge 문제·대회 원본에 담당 관계를 섞지 않는다. 기존 문제와 대회의 담당자는 수정자나 Judge 로그인 문자열만으로 자동 확정하지 않고 후보 보고서와 관리자 승인을 거쳐 배정한다.

저장소 재정비 확정 결과

세 항목과 D4-R01~D4-R09를 모두 권장안대로 확정했다.

확정

  1. 1 · 그룹 테이블 이름

    groups는 DB 예약어 충돌 가능성이 있으므로 물리명을 learning_groups로 사용한다. 다른 그룹 관련 테이블은 group_managers, group_memberships를 유지한다.

  2. 2 · Judge 사용자 참조의 1차 저장 형식

    최신 확정: Judge DB는 처음부터 변경하지 않는 HUSTOJ 채점 엔진 경계다. 기본 채점 8개와 활성화한 custominput 선택 프로필의 이름·열·타입·키를 공식 스키마 그대로 유지하고 PlatformDb 설치·이전·정리 대상에 넣지 않는다. sim과 solution2는 사용하지 않으며 관련 설정을 각각 0으로 고정한다. 채점기가 직접 사용하지 않는 source_code_user도 사용자 요청과 제출 호환 계약에 따라 유지한다. 플랫폼 Controller·Service·권한·URL·플랫폼 테이블은 숫자 wp_users.ID를 사용하고, JudgeDb 제출 어댑터가 저장·조회 직전에 해당 WordPress 계정의 변경 불가 user_login을 사용해 기존 solution.user_id 문자열 계약을 지킨다. 별도 Judge ID 매핑 테이블, 보조 열, 이중 쓰기와 최종 타입 교체는 만들지 않는다.

  3. 3 · 현재 DB 검증 자료

    확인 가능한 SQL 파일은 2026-04-05의 contest·contest_problem 구조만 포함해 현재 테이블과 데이터 건수를 검증할 수 없다. 실제 이전 전에는 현재 운영 DB의 구조와 테이블별 건수 자료가 필요하다.

후속 기록:

세 확인 사항과 D4-R01~D4-R09를 승인했고 D-005와 D-006에서 구현 순서와 차단 조건을 확정했다. 이 문서 확정 시점의 목표 플랫폼 테이블은 담당 범위 테이블 3개를 포함한 40개였으며, 후속 C-27에서 제출 문맥·대회 문제 배점 2개를 승인해 현재 목표는 42개이고, 실제 이름 변경과 사용자 ID 전환은 운영 DB 기준 보고서와 백업·복구 시험 후에만 실행한다.
