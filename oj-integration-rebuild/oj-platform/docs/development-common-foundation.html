메뉴 기반 개발 설계 · 공통 기반

공통 기반 모듈 개발 설계

최종 목표는 사용자 서비스와 관리자 도구를 포함한 OJ Platform 전체를 새로 정비하는 것이다. 그 첫 단계로 모든 화면과 메뉴가 같은 권한, 설정, DB 연결, 경로, 작업 상태와 UI 시스템을 사용하도록 공통 기반을 완성한다.

작성일: 2026-07-22확정일: 2026-07-23인코딩: UTF-8 한글 원문상태: 사용자 확정 · 공통 기반 설계 동결근거: D-001·D-003·D-006·D-008·DS-02~DS-07
핵심 결정: 내부 클래스·어댑터 정리만으로 재정비를 완료하지 않는다. 공통 기반 뒤에는 각 메뉴를 사용자 화면·관리자 화면·문구·반응형 UX·권한·저장·작업·테스트까지 하나의 수직 단위로 새로 만든다. 공통 기반에서도 그 화면들이 공유할 UI 시스템을 함께 확정한다.
단일 진행 순서: 전체 설계와 승인은 DS-16까지 완료했다. 전체 설계·개발 순서에 따라 별도 재구축 작업 트리의 I-01 공통 UI·기반과 I-02 계정·셸까지 구현했다. 운영 설치·DB 쓰기·실데이터 이전은 I-09 승인 전까지 수행하지 않는다.
변경 금지: WordPress와 같은 식별 구조를 사용한다. user_id는 숫자 wp_users.ID이고 로그인 아이디는 문자열 wp_users.user_login이다. 플랫폼 테이블에는 WordPress 접두어와 oj_를 붙이지 않는다. Judge DB는 별도 연결을 유지하며 PlatformDb 분리는 별도 물리 DB 신설이 아니라 플랫폼 데이터 책임의 모듈 분리다.

전체 재정비 범위

공통 기반과 이후 메뉴 개발이 같은 최종 목표를 바라보도록 범위를 고정한다.

제품 전체
층재정비 대상완료 기준
사용자 서비스로그인, 홈, 문제, 제출, 학습, 커뮤니티, 내 정보의 화면·탐색·상태·모바일 경험학습자와 강사가 기술 설명 없이 핵심 작업을 완료하고 역할별 접근이 자연스럽게 이어짐
관리자 도구7개 주 메뉴와 58개 Registry 항목의 목록·상세·편집·설정·위험 작업·Jobs 화면업무 중심 문구, 일관된 조작 방식, 대상별 권한과 직접 주소 차단 검증
UI 시스템색상, 글꼴, 간격, 아이콘, 버튼, 입력, 표, 상태, 대화상자, 빈 화면, 알림, 반응형 패턴공통 컴포넌트와 화면 유형별 시각 기준을 데스크톱·모바일에서 승인
기능·코드Controller, Service, Repository, Provider, Adapter, Jobs와 모듈 의존성기능 소유권과 의존 방향이 분명하고 화면 코드와 업무 코드가 분리됨
데이터무접두어 플랫폼 테이블, WordPress 숫자 user ID, Judge 경계, 이전·복구승인된 스키마·고아 0건·복구 가능·기능별 소유권 검증
완료로 인정하지 않는 상태: 내부 클래스 이동, 어댑터 추가, DB 스키마 작성 또는 문서 작성만 끝나고 실제 사용자·관리자 화면이 기존 상태로 남아 있으면 해당 메뉴 재정비는 완료가 아니다.

직접 의존과 실패 영향 범위를 기준으로 한 순서이며 UI 시스템을 병행한다.

UI 작업은 후순위가 아니다: Permission부터 공통 컴포넌트와 관리자 화면을 함께 검증하고, AccessRouter까지 안정화되면 로그인·홈·공개 셸·관리자 셸을 첫 완성 화면으로 만든다. 내부 계약만 만든 채 다음 모듈로 넘어가지 않는다.

4 · JudgeDb연결 설정과 운영/Judge 테스트 DB 분리연결·테이블 매핑·기능별 준비 검사업무 모듈의 Judge 어댑터 기반
5 · Jobs CorePlatformDb·Settings 안정화작업·항목·사건·단계와 상태 전이·재시도·취소·임대메타데이터·이전·일괄 작업 실행 기반

병행 · UI SystemD-007·D-009의 사용자·관리자 UX 기준공통 토큰·컴포넌트·화면 유형·반응형·접근성 기준모든 메뉴의 실제 사용자·관리자 화면
Jobs 분할: 이 단계에서는 Jobs Core만 완성한다. 화면·POST·AJAX를 연결하는 Job_Http_Adapter는 Auth·PublicUi·AdminConsole이 준비된 뒤 조립한다. Core가 Permission·AccessRouter·AdminConsole을 역참조하지 않는다.

모든 메뉴가 사용하는 공통 계약

후속 메뉴 단계는 아래 계약만 사용하고 기반 내부 클래스를 우회하지 않는다.

필수 계약
계약등록자소비자검사 규칙
Capability·Context RulePermission과 기능 모듈 ProviderRouter, Service, 메뉴 조립기기능 상태 → 로그인 → 전역 권한 또는 대상 관계 → 행 범위
Setting Definition설정 값을 소유한 모듈Settings Repository·관리 화면키 중복, 타입, 기본값, 비밀값, 권한, nonce

Judge ReadinessJudgeDb와 업무 어댑터Problems·Submissions·Contests기본 MySQL 채점 8개는 항상 함께 검사하고 custominput은 선택 프로필 활성화 때 추가 검사한다. OJ_SIM_ENABLE=0과 OJ_TURBO_MODE=0을 강제한다.

Write Freeze GuardPlatformDb 운영 계약Service·Repository·Job Handler대상 소유 모듈의 전환 중 쓰기 차단, 읽기·검증만 허용
UI Component·Screen PatternPublicUi·AdminConsole 공통 UI 소유자모든 메뉴 View·Renderer한글 문구·반응형·접근성·상태·위험 작업 표현과 화면 유형
  1. Controller·Renderer·메뉴 Provider는 $wpdb나 Judge SQL을 직접 실행하지 않는다.
  2. 다른 모듈의 데이터는 Query Service 또는 Read Provider로만 읽는다.
  3. WordPress DB와 Judge DB를 하나의 트랜잭션으로 가정하지 않는다.
  4. 기능이 꺼지면 신규 읽기·쓰기는 차단하지만 데이터와 스키마를 자동 삭제하지 않는다.
  5. Container는 조립 단계에서만 사용하고 실행 클래스는 생성자 의존을 사용한다.

WordPress 표준 사용자 식별 계약

로그인 아이디와 내부 관계 키를 WordPress와 같은 방식으로 구분한다.

사용자 재확정
경계사용 필드형식·의미구현 규칙
WordPress 계정wp_users.IDbigint unsigned 내부 사용자 키WordPress가 생성·소유한다. 플랫폼은 값을 변경하거나 로그인 아이디로 대체하지 않는다.
WordPress 로그인wp_users.user_loginvarchar(60) 로그인 아이디인증·로그인 입력과 기존 Judge 계정 전환 후보 확인에만 사용한다. 플랫폼 관계 키로 저장하지 않는다.
플랫폼 도메인user_id, *_user_idbigint unsigned, 항상 wp_users.ID 의미권한·프로필·수업·대회·그룹·문제 소유·작업·감사 관계를 같은 숫자 키로 저장한다.
현재 로그인 사용자get_current_user_id()현재 세션의 숫자 WordPress ID일반 요청은 세션에서 바로 받아 사용하므로 로그인 아이디를 다시 조회해 변환하지 않는다.
공개 경로·API{user_id}, user_id숫자 WordPress ID로그인 문자열을 받는 입력은 반드시 user_login으로 이름을 구분한다. 숫자로만 된 로그인 아이디도 user_id로 해석하지 않는다.
Judge 호환 경계기본 채점 8개와 custominput 선택 프로필HUSTOJ 문자열 로그인 계약과 플랫폼 숫자 사용자 키일반 코드는 숫자 ID를 사용하고 JudgeDb 어댑터가 WordPress user_login으로 경계 변환한다. sim과 solution2는 사용하지 않으며 HUSTOJ 스키마와 열 의미를 바꾸거나 보조 열·이중 쓰기·영구 Judge ID 매핑을 만들지 않는다.
  1. Permission_Service와 모든 맥락 권한 규칙은 숫자 user_id를 입력으로 받는다.
  2. user_login은 WordPress 계정 소유 값이며 user_profiles와 업무 테이블에 복제하지 않는다.
  3. 이전 /user_profile/{oj_user}와 문자열 사용자 필터는 목표 Router에 등록하거나 숫자 경로로 변환하지 않는다. 기존 문자열은 승인형 Migration 후보 보고서 안에서만 읽고 일반 요청은 WordPress 기본 처리 또는 404로 끝낸다.
  4. WordPress 계정이 없는 기존 Judge 사용자는 사용자 동의·재검증 뒤 WordPress 계정을 만들고, 이후 일반 기능에서는 새 숫자 user_id만 사용한다.
  5. 제출 Service는 숫자 WordPress ID를 받지만 JudgeDb 어댑터가 기존 solution.user_id에 해당 계정의 user_login을 기록한다. 현재 사용자는 로드된 WP_User, 보고서는 일괄 조회와 요청 캐시를 사용한다.

사후 공통 기반 변경 · C-28

기존 CF-1~CF-8 동결 뒤 추가된 외부 애드온 계약은 별도 변경 문서에서 설계·승인·구현한다.

dev.33·API 1.1 구현
기존 공통 기반보존C-28에서 추가 설계
Permissioncore capability·role·preset과 Authorization 계약애드온 capability namespace와 fail-closed 판정 Adapter
AccessRoutercore Route 152개, URL·권한·rewrite 계약별도 Addon Route Catalog, core 충돌 검사와 Composite Catalog
AdminConsolecore Menu 58개, MenuTree와 ConsoleShell검증된 Console Addon Menu 합성, 공개 anchor·현재 경로·자산 기여
PublicUipublic_menu 설정, 기본 Menu 19개, PublicMenuSettingsService와 PublicShellPublic Route/Menu 명시 기여, 별도 override 설정과 기존 메뉴 원문을 보존하는 합성
Kernel6단계 부팅, core Registry 검증·동결, Container 비공개Registry 동결 전 원자 등록 창과 별도 AcceptedAddonCatalog 동결
단일 변경 원본: 아키텍처와 결정은 C-28 범용 애드온 확장 API, 정확한 공개 signature와 구현 기록은 C28-API-V1-LOCK-01에서 관리한다. 현재 C28-I01~I06 코드와 검증 ZIP은 통과했으며 API 1.1 릴리스 증거가 clean production build와 G1 인수를 추적한다. 이 부록은 기존 공통 기반이 C-28을 놓치지 않게 하는 연결점이며 CF-Q01~Q05를 다시 해석하지 않는다.

확정 항목

CF-1부터 CF-6의 개별 상세 설계와 사용자 확인으로 아래 범위를 동결했다.

사용자 확정
  1. CF-Q01: 공통 기반 개발 순서를 Permission → Settings → PlatformDb → JudgeDb → Jobs Core → AccessRouter로 고정한다.
  2. CF-Q02: Jobs는 Core만 이 단계에서 완성하고 HTTP Adapter는 공통 화면 틀이 준비된 뒤 연결한다.
  3. CF-Q03: 42개 스키마의 실행 명세는 이 단계에서 완성하되 실제 업무 테이블 활성화는 메뉴 소유 모듈 파동별 승인으로 제한한다.
  4. CF-Q04: 공통 기반에서 기능별 최종 화면 전체를 만들지는 않지만, 공통 UI 시스템과 로그인·역할 관리 기준 화면을 실제 구현·검증한다.
  5. CF-Q05: 공통 기반 완료 뒤 로그인·계정과 사용자/관리자 셸을 첫 수직 기능으로 완성하고 이후 모든 메뉴를 UI·기능·DB·테스트 묶음으로 진행한다.
확정 완료: 사용자 식별은 WordPress 표준 구조로 유지한다. 숫자 user_id와 문자열 user_login을 합치지 않으며 이 항목은 CF-Q01~CF-Q05의 추가 확인 대상이 아니다.
진행 상태: DS-00~DS-16의 기능·UI·권한·데이터·통합 계약을 사용자 확정으로 동결했다. 별도 재구축 작업 트리에서 Permission → Settings → PlatformDb → JudgeDb → Jobs Core → AccessRouter 순서의 I-01과 계정·셸 R-04까지 구현·검사했으며 다음은 R-05 Problems다.
