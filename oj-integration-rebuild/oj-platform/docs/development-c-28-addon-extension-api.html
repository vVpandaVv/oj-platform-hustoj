C-28 · Post-freeze Platform Change

범용 애드온 확장 API

외부 애드온의 관리자 기능은 OJ Console에, 로그인 사용자 기능은 PublicUI에 네이티브로 통합하기 위한 플랫폼 제공자 측 변경 설계다. AI 평가 기능을 플랫폼 본체에 넣지 않고, 모든 지원 애드온이 사용할 수 있는 등록·권한 선언·학사 컨텍스트 판정·AI 작업 실행 계약만 플랫폼이 소유한다.

보완일 2026-08-10 요구사항 6건 반영 확장 API v1 상세 설계 승인 C28-API-V1-LOCK-01 정의 현재 oj-platform 2.0.0-dev.33 C28-I01~I06 구현 완료 AM-01·AM-02 계약 개정 반영
C28-I06 현재 상태: 제품 2.0.0-dev.33, Addon API 1.1.0, 공개 interface 8개·DTO 28개·권한 utility 1개(총 37개)를 구현했다. CG01·CG02·CG11·AJ08·LC01·RC01·RC02는 코드와 fixture로 닫았고 CG03은 학년 미제공, RC04는 역할 전용, RC05는 GET 전용으로 정합화했다. 47개 회귀 script, 91-file source fingerprint, upgrade·rollback과 검증 ZIP hash는 릴리스 증거서에 고정했으며 clean production build와 G1 소비자 인수가 남아 있다.
정확한 공개 계약: 구현자는 C28-API-V1-LOCK-01 Addon API v1 정확한 계약 및 구현 이관서의 namespace·interface·DTO·hook timing·오류·SemVer를 사용한다. 이 문서는 변경 배경과 아키텍처 원본이며 두 문서가 다르면 정확한 공개 signature는 계약 이관서를 우선한다.
C28-R01AI 평가 애드온은 별도 WordPress 관리자 메뉴가 아니라 OJ Console 내부 메뉴와 경로를 사용한다.
C28-R02플랫폼 코드 변경은 같은 작업의 HTML 개발 문서, 추적 ID와 검증 관문에 반드시 함께 반영한다.
C28-R03Console과 PublicUI 기여를 분리 선언하고, 활성 애드온이 명시한 사용자 메뉴만 PublicUI에 기본 등록한다.
C28-R04애드온 capability는 manifest로 선언하고 플랫폼의 기존 역할 권한 관리에서 명시적으로 배정한다. 사용자 직접 capability 배정은 v1 비범위다.
C28-R05사용자·학급·그룹·담당 관계는 플랫폼 원장을 사용하며 애드온에는 범위가 제한된 context authorization 계약만 제공한다.
C28-R06애드온 AI task type은 기존 운영 > AI 작업 배정에 합성하고 provider·비밀값·model routing은 플랫폼이 계속 소유한다.
현재 판정C28-I06 구현은 완료됐고 release candidate 검증이 진행 중이다. 애드온 구현은 이 공개 계약만 소비하며 플랫폼 파일을 수정하지 않는다.

용어와 자동 등록의 의미

Console 등록, PublicUI 등록과 실제 사용자 노출을 서로 다른 계약으로 구분한다.

C28-R03
용어의미자동 처리
OJ Console관리자·교사가 제작, 배포, 평가와 운영을 수행하는 플랫폼 관리 shellmanifest의 console_routes와 console_menus만 합성
PublicUI로그인한 학생·일반 사용자가 학습 기능을 사용하는 플랫폼 사용자 shellmanifest의 public_routes와 public_menus만 합성
별도 등록한 애드온 manifest 안에서 Console과 PublicUI 기여를 독립된 목록으로 선언하는 것두 번 설치하거나 플랫폼 파일을 두 번 수정한다는 의미가 아님
자동 등록활성 애드온의 호환 manifest가 승인되면 선언된 기여가 해당 요청의 Composite Catalog에 들어가는 것운영자가 Route나 메뉴를 수동으로 다시 만들 필요 없음
자동 노출default_enabled=true, 유효한 부모, 수량 제한과 사용자 접근 정책을 모두 통과한 Public 메뉴를 표시하는 것모든 사용자에게 무조건 보이는 동작이 아니며 권한 판정은 항상 마지막에 적용
핵심 구분: Console 메뉴를 PublicUI로 자동 복제하지 않는다. 애드온 활성화는 manifest에 각각 명시된 두 기여를 한 번에 등록할 뿐이며, 사용자 메뉴 표시 여부는 PublicUI 기본값·운영자 override·현재 사용자 접근 정책을 차례로 적용한다.

등록 생명주기

모든 활성 플러그인 파일이 로드된 뒤, core 계약 등록과 Registry 동결 사이에 한 번의 수집·검증 창을 둔다.

C28-D01 확정
1
애드온 callback 선언

애드온 root 파일은 로드 시 oj_platform_register_addons callback 하나만 등록한다. Runtime 준비 callback은 별도 action이 아니라 이 callback 안에서 builder->onReady(...)로 함께 등록한다(AM-01). 이 시점에 플랫폼 class를 생성하거나 Registry를 조회하지 않는다.

2
core 계약 등록

플랫폼은 plugins_loaded 우선순위 1에서 부팅하고 기존 Module의 register()를 완료한다. 이 단계의 core Registry는 기존 계약대로 유지한다.

3
등록 창 실행

Registry 동결 직전에 action oj_platform_register_addons을 한 번 발행하고 변경 가능한 내부 Registry 대신 AddonRegistrationGatewayV1 하나만 전달한다.

4
후보 manifest 수집

각 callback은 gateway.register(addon_id, builder) 안에서 manifest 전체를 작성한다. builder의 예외와 DTO 오류는 Gateway가 잡아 해당 애드온 후보만 rejected로 기록한다.

5
전체 집합 검증·원자 승인

후보를 애드온 ID와 기여 key로 정렬한 뒤 core 충돌, addon 간 충돌, 참조, 수량과 버전을 검증한다. core와 충돌한 애드온은 거부하고, 같은 key·path를 낸 애드온끼리는 순서에 관계없이 모두 거부한다.

6
동결·Runtime 연결

승인된 애드온별 기여 전체를 하나의 불변 Catalog로 commit하고 core Catalog와 읽기 전용으로 합성한다. Route, Console 메뉴와 PublicUI 메뉴는 이 결과만 읽는다.

7
애드온별 Runtime 준비 dispatch (AM-01)

Runtime Ready 뒤, accepted된 애드온마다 그 애드온이 onReady()로 등록한 callback을 이 애드온 전용 AddonRuntimeContextV1 하나와 함께 plain PHP 함수 호출로 최대 한 번 실행한다. WordPress action으로 방송하지 않으므로 다른 애드온이 이 호출을 가로채거나 남의 context를 받을 수 없다. 애드온은 snapshot·Context·AI 작업만 사용하며 임의 service 조회와 추가 등록은 할 수 없다. manifest가 승인되지 못한 애드온의 onReady는 호출되지 않는다. Context 생성·callback 예외는 격리하지만 이미 합성된 기여는 유지되고 같은 부팅에서 재시도하지 않으므로 소비자는 자체 Bridge ready를 별도로 검사한다.

C28-I06-LC01 구현: callback 예외 뒤에도 catalog·Route·Menu는 accepted 상태로 남고 같은 부팅에서 자동 재호출하지 않는다. 별도 내부 readiness는 pending|ready|failed|not_required를 기록하며 운영 상태에는 안전한 addon_runtime_callback_failed만 표시한다. 소비자는 여전히 자체 Bridge ready를 모든 진입점에서 fail closed한다.
예외 격리의 현실적 경계: 애드온은 모든 manifest 작성 작업을 gateway.register() builder 안에서 수행해야 한다. Gateway 밖에서 플러그인 callback 자체가 PHP 실행을 중단시키는 행위까지 플랫폼이 sandbox할 수는 없으므로 이는 API 위반이며, 플랫폼 Error Boundary는 core 부팅 복구와 안전한 상태 기록까지만 보장한다.
AM-01 (2026-08-11): 이전 설계의 oj_platform_loaded(AddonRuntimeGatewayV1 $gateway)는 모든 애드온 callback에 같은 전역 Gateway를 넘겨 forAddon()에 임의 addon ID를 넣으면 다른 애드온의 Runtime Context를 받을 수 있는 애드온 간 impersonation 결함을 갖고 있었다. 이 설계를 폐기하고 애드온별 직접 callback dispatch로 교체했다. 배경과 소비자 전환 절차는 계약 개정 기록과 onReady 전환 안내서에 있다.

관리자 메뉴 아이콘 표시 정책

기존 AddonConsoleMenuDefinitionV1의 선택 인자 icon 계약은 변경하지 않는다. 아이콘은 공통 메뉴 데이터에 보존하며, 1차 메뉴에서만 플랫폼 Lucide IconName에 등록된 이름을 사용한다. 미지정 애드온 메뉴 또는 미지원 이름은 puzzle로 표시한다. 기본 메뉴의 기존 아이콘은 유지한다.

현재 애드온 anchor 등록은 기본 1차 메뉴 아래의 2차 메뉴를 추가한다. 2차 메뉴는 icon 값이 있어도 텍스트만 표시하며, 애드온이 임의 SVG·이미지·이모지를 메뉴 이름에 붙이지 않는다. 펼침·접힘 화살표는 하위 항목이 있는 1차 메뉴의 오른쪽에만 표시한다. API 버전, 권한, anchor 및 Route 계약은 변경하지 않는다.

관리자 저장 피드백 검토

관리자 콘솔의 제출 → AI 피드백 → 피드백 기록은 사용자 아이디·수업 번호·문제 번호로 제출별 최신 저장 피드백을 필터링한다. 관리자 제출 상세에도 같은 저장 피드백을 연결한다. AI 피드백 관리 권한과 해당 제출의 전체 상세 열람 권한을 모두 적용하며, 결과 전용 열람자는 피드백을 볼 수 없다. 권한은 사용자 → 역할과 권한에서 설정한다.

저장된 피드백의 관리자 검토는 학습자 새 생성 정책·연구 전달 정책과 분리한다. 관리자 조회는 학습자에게 피드백을 전달한 사건으로 기록하지 않으며 재생성·코드 전송을 실행하지 않는다. 재채점 후에도 생성 당시 저장 내용임을 표시한다. 기존 Addon API의 권한·피드백 생성 계약은 변경하지 않는다.
