문제별 제출 코드 규칙

관리 입력, 사용자 안내와 서버 제출 판정이 같은 정책 객체를 사용한다.

기존 Judge 필드 사용
관리 필드Judge 원본표시·입력 계약서버 계약
제출 금지어problem.bann/ 구분과 기존 줄바꿈 구분을 허용. \/는 문자 /, \\는 문자 \를 뜻한다. 예: eval/exec/\/ → eval, exec, /. 빈 항목·중복은 제외하고 문제 상세·제출 화면과 서버 검사에 같은 목록 사용정규식이 아닌 대소문자 구분 부분 문자열로 사용자 원본 또는 서버 생성 Blockly 코드에서 검사. 금지어 중 하나라도 포함되면 제출 거부
제출 코드 앞에 붙일 코드problem.front관리자는 표식을 포함한 원문 편집. 줄 끝의 #hidden(뒤 공백·탭 허용)이 있는 줄은 문제 상세·제출 화면의 HTML에 포함하지 않음. 나머지는 읽기 전용 표시금지 검사 통과 뒤 #hidden 표식만 제거하고 해당 코드 줄은 유지하여 사용자 원본 앞에 한 번 결합
제출 코드 뒤에 붙일 코드problem.rear앞 코드와 같은 줄별 비공개 규칙 적용. 전부 비공개라면 코드 대신 비공개 상태만 표시. 사용자 답안이나 빈칸 템플릿에는 이 표식을 적용하지 않음금지 검사 통과 뒤 #hidden 표식만 제거하고 해당 코드 줄은 유지하여 사용자 원본 뒤에 한 번 결합. 채점 로그까지 비밀을 보장하는 기능은 아니므로 비밀값 저장에 사용하지 않음
코드 빈칸 완성problem.body + problem_metadata관리자가 완성 코드를 작성하고 영역을 선택해 한 줄·여러 줄 빈칸으로 지정. 학생은 형광색 빈칸만 클릭해 입력브라우저의 완성 소스를 버리고 최신 템플릿과 빈칸 ID별 답안으로 서버가 다시 구성
  1. Problems는 banned_fragments[], front_code, rear_code, 정책 버전을 가진 불변 Problem_Submission_Code_Policy를 제공하고 Submissions는 Judge problem을 직접 조회하지 않는다.
  2. 관리 UI는 한 줄 목록을 사용하지만 bann의 기존 저장 형식 변환과 리터럴 슬래시 처리는 Problem_Judge_Gateway 한 곳에서만 수행한다.
  3. 금지 목록은 문제에 허용된 모든 언어에 동일 적용한다. front 또는 rear가 하나라도 있으면 허용 언어는 정확히 하나여야 하며, 언어별로 다른 래퍼가 필요하면 문제를 분리한다.
  4. problem.body는 전체 코드 작성에서는 편집기에 처음 채우는 시작 코드이고, 빈칸 완성에서는 고정 코드와 내부 빈칸 토큰을 가진 템플릿이다. 어느 경우에도 자동 래퍼가 아니며 front·rear와 역할을 섞지 않는다.
  5. problem_metadata.code_entry_mode는 full_code 또는 code_completion이고, 빈칸 완성일 때만 code_completion_schema와 code_completion_hash를 가진다. 스키마는 언어 키와 고유 빈칸 ID, 표시 문구, inline·block 형식, 최대 바이트를 보유한다.
  6. 빈칸 완성은 언어 하나만 허용하는 전용 작성 방식이다. 학생이 일반 코드나 Blockly로 전환할 수 없으며 관리자가 완성 코드의 영역을 선택해 빈칸으로 바꾸므로 내부 토큰을 직접 입력하게 하지 않는다.
  7. 저장 시 템플릿 토큰과 스키마가 일대일인지, ID가 중복되지 않는지, 빈칸이 1~30개인지, 언어가 하나인지 검사한다. 정규화한 LF 템플릿·정렬한 스키마·언어 키의 SHA-256을 템플릿 해시로 기록한다.
  8. 클라이언트 검사는 빠른 안내일 뿐이다. 서버는 제출 시 최신 정책을 다시 읽고 전체 코드·빈칸 완성·Blockly를 각각 복원한 뒤 같은 Validator와 Composer를 통과시킨다.
  9. 빈칸 제출 요청은 템플릿 해시와 빈칸 ID별 답안만 받는다. 해시 불일치, 알 수 없거나 중복된 ID, 필수 답안 누락, 형식·길이 위반은 현재 화면을 새로 불러오도록 안내하고 Judge 행을 만들지 않는다.
  10. 금지 코드는 학생이 입력한 범위와 그 경계에 걸친 일치만 차단한다. 고정 템플릿과 앞·뒤 코드는 관리자 신뢰 영역으로 분리하며, 서버는 최종 소스의 문자별 소유 범위를 추적해 빈칸 경계를 나눈 우회를 막는다.
  11. 금지 코드가 일치하면 solution과 소스 행을 만들지 않는다. 통과하면 LF 줄바꿈 경계를 보장해 front + 사용자 원본 + rear를 한 번만 구성한다.
저장 분리: DS-11은 빈칸을 서버에서 완성한 래퍼 없는 소스를 source_code_user, 실제 Judge가 컴파일할 앞·뒤 코드 결합 결과를 source_code에 저장한다. submission_events.metadata에는 작성 방식과 템플릿 해시만 기록하고 답안·템플릿 복제본은 저장하지 않는다. 새 플랫폼 테이블·경로·POST 액션·capability는 추가하지 않는다.
과거 제출: 템플릿을 수정해도 기존 source_code_user와 채점 결과는 바꾸지 않는다. 과거 제출은 완성 코드로만 확인하며, 빈칸 재입력은 최신 템플릿의 빈 화면에서 시작해 제출별 템플릿 스냅샷 증가를 막는다.

난이도JSON Schema 정수 minimum=1, maximum=5와 5단계 평가 기준을 함께 전달정수 1~5만 허용. 소수·문자·범위 밖 값은 보정하지 않고 실패1 매우 쉬움, 2 쉬움, 3 보통, 4 어려움, 5 매우 어려움
주제 지정2단계 사전에서 분야를 고른 뒤 정확히 맞는 활성 세부 주제 키를 선택 사항으로 최대 3개 지정하며, 하나 이상이면 첫 항목은 대표 주제주제 없음은 허용한다. 분야 자체 선택, 미등록·중복·4개 이상과 3단계 분류는 자동 보정하지 않고 거부자료구조 > 배열처럼 경로를 표시하되 problem_topic_links에는 선택한 세부 주제 키만 저장하고 미선택이면 행을 만들지 않음
주제 추가최고 관리자만 분야를 먼저 선택하고 영문 세부 주제 키·한글 이름·AI 별칭을 입력. 분야 추가도 최고 관리자 전용키 형식·키·이름·별칭 중복, 분야 존재와 정확히 2단계인지를 검사한다. 일반 문제 관리자·담당자·AI는 분야·세부 주제 생성 금지/oj-console/problems/topics에서 트리로 관리하고 문제 편집에는 분야별 세부 주제 선택기만 표시
AI 주제 선택·실패 확인selectable=true인 사전 항목의 key만 선택한다. 검증한 사전 스냅샷에서 출력 Schema의 enum을 만들며 Ollama 구조화 출력에 전달한다. 그 외 현재 연결은 동일 선택 규칙을 프롬프트로 전달하고 서버가 결과를 검증한다.상위 분야·표시 이름·미등록·비활성 키는 다른 주제로 치환하거나 초안에 저장하지 않는다. 주제가 없으면 빈 배열을 허용한다. 기존 큐 입력 해시·권한·수동 적용 절차는 유지한다.Jobs 결과의 주제 검증 상세에서 AI 반환 키, 등록 주제명, 거부 사유를 확인한다. 문제 원문·전체 AI 응답·비밀값은 공개하지 않는다. 이전 실패 기록에는 반환 키가 없으므로 업데이트 후 재생성한 결과부터 상세를 제공한다.
AI 신뢰도·응답 검증confidence는 유한한 0~1 JSON 숫자이며 누락·null·백분율은 허용하지 않는다. "0.8"처럼 숫자만 든 문자열은 같은 값의 숫자로 정규화한다.85를 1.0으로 바꾸던 범위 보정은 제거한다. 잘못된 척도를 100% 신뢰도로 저장할 수 없기 때문이다. 주제 검증·초안 검토·적용 절차와 Addon API 계약은 유지한다. BOM·코드 펜스만 정리하고 본문에서 임의의 JSON 조각을 추출하거나 잘린 응답을 복구해 저장하지 않는다.기존 Jobs 결과에 신뢰도 누락·자료형·범위 오류와 Ollama의 빈 답변·생각 과정만 반환·JSON 문법 오류·미완료·출력 한도 초과를 구분한다. 원문 응답과 생각 과정은 노출하지 않는다. Ollama 구조화 출력과 Chat API 규격을 기준으로 하며 실제 서버 응답을 확보하지 않은 오류는 원인을 단정하지 않는다.
생성 근거제목·본문·입출력·제한·예시·힌트와 허용된 통계 스냅샷입력 해시, 프롬프트·사전·평가기준·모델 버전 기록생성 방식, 시각, 충돌 상태 표시
수동 수정AI 입력과 별도 명령AI가 수동값을 덮어쓰지 않으며 비교 후 명시 적용수동·AI·통계 생성 출처 구분
1 · 대상 고정단건·선택·필터 전체

서버가 현재 권한과 필터로 문제 ID 목록과 입력 해시를 고정한다.

2 · Jobs 실행문제 1개 = 항목 1개

Worker가 현재 권한과 문제 버전을 다시 확인하고 AI를 호출한다.

3 · 검증·반영저장 또는 확인 필요

계약 통과 결과만 저장하고 변경·수동값 충돌은 비교 화면으로 보낸다.

저장 위치: 난이도와 생성 근거는 무접두어 problem_metadata, 문제와 세부 주제의 관계는 무접두어 problem_topic_links에 저장한다. 분야와 세부 주제 사전은 WordPress 비공개 분류 oj_problem_topic와 termmeta가 소유하며 새 플랫폼 테이블과 Judge problem 열은 추가하지 않는다.
2단계·버전 계약: 최상위 term은 문제에 직접 지정하지 않는 분야, 그 자식 term은 문제에 지정하는 세부 주제이며 손자 term은 허용하지 않는다. 최초 32개 세부 주제는 설치 시 topic-dictionary-v1 seed manifest로 멱등 등록한다. 실행 시에는 정렬한 분야·세부 주제 키·이름·별칭의 SHA-256을 43자 Base64URL로 표현한 td-v1:<digest> 형식(총 49바이트)을 현재 사전 버전으로 사용하고 AI 요청·Jobs 결과·problem_metadata.topic_dictionary_version에 기록한다. 이 형식은 varchar(50) 저장 계약을 넘지 않는다. 최고 관리자가 항목을 추가하면 이후 작업의 버전만 바뀌며 기존 문제 관계는 자동 재분류하지 않는다.
최고 관리자 전용: 주제 관리 메뉴 숨김만으로 보호하지 않는다. 직접 GET과 oj_problem_topic_create POST 모두 최고 관리자 Policy와 위험 작업 nonce를 다시 검사하며 oj_manage_problems, 문제 소유·협업 관계, manage_options 위임만으로는 새 주제를 만들 수 없다.

문제별 질문 연결

문제 상세의 학습 흐름은 이어 주되 게시판 원본을 중복 소유하지 않는다.

DS-14 연계
  1. 본문·예시·힌트 뒤에 최근 질문 최대 5개의 제목, 답변 상태, 댓글 수와 최근 갱신 시각만 표시한다.
  2. “질문하기”는 검증된 문제 문맥으로 /board/new, “전체 질문”은 같은 문맥의 /board, 항목은 게시글 상세로 이동한다.
  3. Problems는 Board 테이블을 직접 조회하지 않고 문제 ID, 숫자 사용자 ID와 최대 항목 수를 선택 Provider에 전달한다.
  4. Board 기능 OFF, 문제 질문 비활성, Provider 실패 또는 참여 중 평가 보호 상태에서는 질문 영역 전체를 숨긴다.
  5. 같은 평가 보호를 게시판 목록·검색·글 상세·댓글·첨부에 적용하고 관련 평가가 모두 끝난 뒤 다시 표시한다.
