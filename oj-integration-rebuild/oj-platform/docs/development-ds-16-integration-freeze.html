DS-16 · 설계 동결과 구현 인수 체크포인트

전체 연결·동결

DS-00~DS-15에서 확정한 사용자 경험, 권한, 경로, 모듈, 데이터와 운영 계약을 하나의 실행 구조로 연결한다. 현재 코드의 모양이 설계를 다시 바꾸지 않으며, 차이는 I-00~I-09에서 해소할 구현 격차로 관리한다.

현재 구현·인수 판정: R-11까지 정상 운영 모듈과 무접두어 스키마 42개를 구현했고 2026-08-10 현재 로컬 자동 검사 39개가 모두 종료 코드 0으로 통과했다. Ubuntu 24.04 LTS의 빈 WordPress·HUSTOJ 서버에서 실제 설치와 화면 검증을 시작해 설치 조정기, 정식 경로, 공통 UI 자산, 문제 저장, LaTeX, SPJ, 제출·대회 흐름의 결함을 발견하고 코드를 보강했다. 다만 수정본 재배포 뒤 최종 통과를 확인하지 않은 항목과 AI·메일·복구 미실시 항목이 있으므로 제품 전체를 실환경 인수 완료로 판정하지 않는다.

결정 우선순위

점검 때마다 이전 결정을 뒤집지 않도록 원본 순서를 고정한다.

변경 통제
  1. 사용자 확정 결정: 가장 최근에 명시적으로 확정한 요구와 DS-16 변경 기록이 최우선이다.
  2. DS-00~DS-15: 각 기능의 화면·권한·데이터·운영 상세 원본이다. DS-16은 내용을 복사하지 않고 연결 관계만 소유한다.
  3. D-001~D-009: 현재 구조의 근거와 목표 수량·소유권 기준이다. 상세 설계가 명확히 보강한 부분은 해당 DS 문서를 따른다.
  4. 현재 코드·DB: 이전 입력과 회귀 기준이다. 목표 설계를 자동으로 변경하는 근거로 사용하지 않는다.
  5. 변경 절차: 동결 뒤 변경은 근거, 영향받는 Route·권한·테이블·이전·테스트와 사용자 재확인을 한 변경 기록으로 남긴다.

SetupBootstrap 경계: Phase 0은 정상 모듈 DAG와 기능 컨트롤러 수에 포함하지 않는다. 설치 완료 상태에서는 클래스가 존재하더라도 화면·액션·자산 Hook을 등록하지 않으며, 신규 설치 실행은 PlatformDb·JudgeDb·Permission·Jobs의 공개 설치 계약에만 위임한다.
두 단계 모듈 수명주기: 모든 모듈은 먼저 타입이 정해진 정의만 Registry에 등록한다. 전체 등록이 끝나 중복·순환·누락 참조를 검사하고 Registry를 동결한 뒤에만 Router, 메뉴, POST/AJAX, Worker와 자산 훅을 연결한다.
의존 방향: Classes와 Contests는 Groups를 필수로 참조하지 않는다. Blockly는 제출 화면에서 블록 방식을 선택했을 때만 적재한다. Problems는 AI Feedback에 의존하지 않으며 AI 호출은 공통 AI Adapter와 Jobs를 통해서만 실행한다.

구현 격차 해소 현황

동결한 G-01~G-09를 삭제하거나 다시 정의하지 않고, 같은 기준으로 현재 구현 증거를 기록한다.
