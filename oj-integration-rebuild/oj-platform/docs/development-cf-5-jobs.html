등록·대상 고정·멱등성

같은 확인 요청이 중복 실행되지 않고 실행 중 대상이 늘어나지 않게 한다.

원자 등록
순서처리실패·충돌 처리
1 · 확인기능 화면이 범위·영향 수·실행 모드·덮어쓰기 정책을 보여 주고 nonce를 발급확인 전에는 작업 행을 만들지 않음
2 · 재검사POST에서 현재 권한·기능 상태·필터·대상 존재를 다시 검사실패하면 항목 0건으로 종료
3 · 스냅샷정렬된 대상 키와 각 대상의 버전·수정 시각·입력 해시를 생성Worker가 조건을 다시 검색하거나 새 대상을 추가하지 않음
4 · 멱등키작업 종류, Handler 정의 버전, 실행 모드, 접근 범위 해시, 정렬된 대상, 입력 버전·해시를 canonical JSON으로 만들고 SHA-256 계산AI는 task_type, 작업 배정 revision, 주·대체 프로필 키와 검사 fingerprint, 모델·프롬프트·출력 스키마와 해당 루브릭·사전 버전도 포함
5 · 원자 저장작업·항목·최초 사건을 한 PlatformDb 트랜잭션으로 저장고유키 충돌이면 새 작업을 만들지 않고 현재 조회 권한을 확인한 기존 작업으로 연결
6 · 실행 요청commit 뒤 서버 내부 비동기 POST로 Worker를 즉시 깨우고 작업 ID를 진행 화면에 전달연결 실패여도 작업·입력은 유지하고 1분 복구 예약이 다시 처리
  1. 자동·수동 재시도는 같은 작업과 항목을 갱신하고 사건을 추가한다. 새 작업을 만들지 않는다.
  2. Handler·입력·모델·사전 버전 또는 실행 모드가 달라지면 새 멱등키와 새 작업을 허용한다.
  3. AI 작업 등록 시 현재 작업 배정 revision과 주·대체 프로필 키·검사 fingerprint를 스냅샷으로 고정한다. 이후 배정 변경은 새 작업에만 적용하며, 실행 전 프로필 fingerprint가 달라졌거나 작업 허용·제출 코드 승인이 무효화되면 기존 작업을 다른 프로필로 자동 전환하지 않고 needs_attention으로 마감한다. 배정 revision은 AI 작업 배정 설정 전체의 버전이므로 같은 값 재저장이나 다른 작업 배정 저장으로도 바뀔 수 있다. 실패 항목 재시도는 원래 스냅샷을 유지하며, 설정 변경으로 중단된 경우에는 현재 설정으로 새 작업을 등록하도록 오류에 안내한다.
  4. 등록 스냅샷과 실행 직전 대상 버전이 다르면 저장하지 않고 항목을 needs_attention으로 마감한다. 문제·테스트케이스 초안은 생성 뒤 편집기 상태가 달라져도 자동 덮어쓰지 않고 필드·파일별 비교 화면만 제공한다.
  5. 외부 AI 호출이 끝난 뒤 업무 저장 직전에 대상 버전·입력 해시와 권한을 다시 읽는다. 호출 중 변경된 메타데이터·제출 피드백은 저장하지 않고, 문제·테스트케이스 결과는 오래된 입력으로 만든 초안임을 표시해 명시적 비교만 허용한다.
  6. 다른 사용자가 같은 작업을 먼저 등록했더라도 현재 조회 권한이 없으면 작업 ID·항목·결과를 노출하지 않고 중복 실행 중이라는 안전한 안내만 반환한다.

Worker·임대·운영 실행

2026-09-14 요청에 따라 예약 대기를 즉시 실행 신호와 완료 후 연속 처리로 변경했다.

동시성 핵심

실행 신호는 60초 유효한 일회용 토큰이며 서버에는 해시만 비자동로드 WordPress 옵션으로 보관한다. TLS 검증을 유지하고 리디렉션·쿠키·업무 입력 전달은 하지 않는다. 같은 큐의 실행 신호는 합치며 DB 오류로 진행하지 못한 작업은 즉시 반복 호출하지 않는다. 공개 Addon API는 변경하지 않는다.

  1. 작업 목록을 새 주 메뉴로 추가하지 않는다. 문제·사용자·이전 화면의 최근 작업 링크와 관리자 홈의 최근 작업에서 진행 화면으로 들어간다.
  2. 문제 작성 AI는 문제 편집기의 초안 영역, 테스트케이스 AI는 테스트데이터 도구, 제출 AI 피드백은 본인 제출 상세에서 상태를 표시한다. 일반 사용자 작업을 관리자 콘솔로 이동시키지 않는다.
  3. 문제·테스트케이스 AI 완료 결과는 자동 적용하지 않는다. 원본 이후 변경을 강조한 비교 화면과 “초안 적용” 또는 “검증 후 적용” 명령을 제공한다.
  4. 기본 화면은 요약·진행 막대·항목 표·주요 조치만 보여 주고 Worker ID·임대·예외 코드는 권한 있는 기술 상세에 둔다.
  5. 진행 중에는 2초 간격으로 조회하고 변화가 없으면 5초로 늦춘다. 탭이 숨겨지거나 최종 상태가 되면 자동 조회를 멈춘다.
  6. 모바일에서는 집계와 주요 조치를 먼저 표시하고 항목 표는 열 의미를 유지한 가로 스크롤을 허용한다.
  7. 완료·경고 문구는 URL에 넣지 않고 공통 Flash_Store의 일회성 메시지 코드만 사용한다.

AI 결과 저장 경계

AI 작업Jobs가 저장하는 값업무 저장소 반영충돌·권한 변화
문제 메타데이터대상·입력·계약 해시와 안전한 결과 코드Problems Handler가 난이도 1~5·표준 주제를 검증한 뒤 승인 정책에 따라 저장문제 수정 시각·해시가 달라지면 자동 저장 금지
문제 작성 초안암호화 초안의 payload_ref편집자가 비교 화면에서 적용한 뒤 기존 oj_problem_save로 저장현재 폼·기존 문제 변경 필드는 덮어쓰지 않고 비교 표시
테스트케이스 초안암호화 파일 초안의 payload_ref편집자가 검증 결과를 확인하고 problem_testcase_apply를 별도 승인원본 파일 해시가 달라지면 적용 금지
제출 AI 피드백제출·소스·문제·프롬프트·모델 해시와 안전한 결과 코드AI Feedback Handler가 성공 결과를 submission_ai_feedback에 저장상세 권한 회수·수행모드·제출 내용 변경 시 생성·열람 차단
제출 피드백 권한: oj_manage_ai_feedback는 정책·프롬프트와 강제 새로고침을 관리하는 권한이지 제출 소스 열람 권한이 아니다. 관리자도 대상 제출의 상세·코드 범위를 별도로 통과해야 하며, 수행모드에서는 그룹 밖 제출을 포함한 학습자 본인의 모든 제출 상세가 제한되므로 새 피드백 생성과 저장된 피드백 열람을 모두 막는다.

확정 항목

아래 여덟 항목은 2026-07-23 사용자 확인으로 동결했다.

사용자 확정
  1. DS06-Q01 · 범위·의존: Jobs Core는 PlatformDb·Settings에만 직접 의존하고 업무는 기능 Handler, 화면·POST·AJAX는 후속 Job_Http_Adapter가 소유한다.
  2. DS06-Q02 · 저장 구조: 기존 4개 무접두어 테이블을 유지하고 항목 스냅샷 열과 사건 행위자 표현을 D-008에 보강한다.
  3. DS06-Q03 · 등록·멱등성: 서버가 확정 시점의 대상과 버전을 고정하고 계약·접근 범위·입력 해시로 중복을 막으며 변경 충돌은 자동 덮어쓰지 않는다.
  4. DS06-Q04 · Worker·임대: 1분 예약 실행, 작업당 Coordinator 1개, 항목 원자 임대, 240초 Worker 예산과 5분 heartbeat 경고를 기본값으로 사용한다.
  5. DS06-Q05 · 상태·재시도·취소: 사용자 상태 7개를 유지하고 일시 오류만 기본 3회 지연 재시도하며 취소는 기존 임대가 정리된 뒤 확정한다.
  6. DS06-Q06 · 단계·복구: 저장 경계를 넘는 작업만 단계·체크포인트·검증·보상을 사용하고 문제 번호 변경을 첫 다중 저장소 적용 대상으로 한다.
  7. DS06-Q07 · 권한·민감 정보: 모든 진입점과 실행 직전에 현재 권한을 다시 검사하고 AI 키·비밀번호·원본 CSV·소스·전체 예외를 Jobs 이력에 저장하지 않으며 기존 보존 기간을 유지한다.
  8. DS06-Q08 · UI·최초 작업: 새 주 메뉴 없이 소유 기능에서 진행 상태를 보여 준다. 메타데이터·문제 작성·테스트케이스·제출 피드백의 모든 AI 호출과 CSV·이전·SPJ 컴파일·문제 번호 일괄 변경·퀴즈 게시 버전 재적용을 Jobs Handler로 연결하고, 문제·테스트케이스 결과는 자동 저장하지 않는 검토 초안으로 제공한다.
확정·구현: DS06-Q01~Q08과 D-008 Jobs 열 정의를 유지한다. Core, Auth CSV, Problems Handler와 기능별 현재 접근 정책을 구현했다. 취소·실패 재시도는 트랜잭션 상태 전이와 사건을 기록하며, 취소 확정 뒤 암호화 입력 폐기 실패는 상태를 되돌리지 않고 공통 오류 경계에 보고한다. 완료 모듈은 정의와 Handler를 양방향으로 검증하고, Submissions·Migration도 각 소유 단계에서 Handler와 접근 규칙을 함께 등록해야 한다. Handler·접근 정책 미등록 또는 계약 버전 불일치는 기본 거부한다.
