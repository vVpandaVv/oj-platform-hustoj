최고 관리자전역 문제 관리와 분야·세부 주제 사전 조회·추가확정 키 변경·3단계 분류·즉시 삭제·기존 문제 자동 재분류최고 관리자 전용 Policy · 위임 capability 없음
  1. 전역 관리자는 전체 문제, 담당자는 소유·활성 협업 문제만 목록에서 본다. 미배정 문제는 전역 문제 관리자만 본다.
  2. problem_ai_assist는 기본 비활성화한다. 기능을 켜고 해당 task_type의 AI 작업 배정이 준비된 경우에만 버튼과 실행을 함께 허용하며, oj_manage_problem_ai_assist는 문제 수정·테스트데이터 권한을 대신하지 않는다.
  3. oj_problem_topic_create는 최고 관리자 Policy와 위험 작업 nonce를 모두 통과해야 한다. 일반 문제 capability와 대상별 담당 관계로는 허용하지 않는다.
  4. 담당 관계가 해제되면 다음 요청과 대기 Job 실행 직전 검사부터 접근과 결과 노출을 차단한다.
  5. 목록의 일괄 작업은 화면에서 체크된 문제 또는 서버가 고정한 필터 대상만 사용한다.

현재 권한과 원본 버전이 같을 때만 AI 또는 유지보수 작업을 실행한다.

3 · 검토결과 비교·명시 적용

실패·충돌은 사유를 남기고 업무 원본을 바꾸지 않는다.

메타데이터 응답 재생성: 업무 검증에서 발견한 필수 필드 누락·형식 오류는 같은 항목의 기존 시도 한도(기본 총 3회) 안에서 5초 뒤 다시 실행 가능하게 큐에 넣는다. 단, Ollama에 native Schema를 보냈는데 최상위 필수 필드가 누락된 응답은 아래의 Provider 계약 오류로 즉시 중단한다. 한 번의 Worker 시도에서 Provider는 한 번만 호출하고, 반복 시도에는 검증된 출력 Schema에 완전한 객체를 요구하는 설명을 보강한다. 입력 스냅샷·해시와 problem-metadata-v1 계약은 유지한다. 한도 소진 시 problem.ai_contract_failed와 원래 오류 사유를 남겨 확인을 요청한다. 원문·프로필·권한 변경과 선택 불가 주제는 이 자동 재시도 대상이 아니며, 검증 전 응답은 초안이나 Jobs 결과에 저장하지 않는다.
Ollama 구조화 출력 검사: ProblemMetadataOutputContract 한 곳에서 생성한 Schema를 연결 후보 검사와 실제 생성 요청 모두 /api/chat의 format에 전달한다. 같은 Schema를 플랫폼 system 메시지에도 명시하며 애드온 지시와 사용자 데이터의 순서는 유지한다. Schema의 최상위 required 필드가 누락되면 schema_required_missing(Jobs 표시: problem.ai_provider_failed)으로 확인을 요청한다. 반복 재시도나 다른 Provider로 자동 전송하지 않고, 누락 필드명만 표시하며 응답 원문·미지의 키·인증정보는 노출하지 않는다. 필드의 형식·범위·주제 유효성은 기존 업무 검증을 계속 거친다. 서버의 Ollama 버전·모델 구조화 출력 지원 및 역방향 프록시의 format 전달 여부를 확인하고 연결 후보 검사를 다시 수행한다. 이는 서버 측 원인이 확인되었다는 의미가 아니며, 로컬 모의 응답 검증과 실제 서버 재검증을 구분한다. Ollama 공식 구조화 출력 문서
Gemma 4 서버 호환성: 구버전의 think=false 요청에서 format을 무시하는 상류 이슈 #15260는 Ollama 0.21.1에 수정되었다. 이후 사용자가 확인한 버전은 서버 0.34.2, CLI 0.20.5이다. CLI 버전 경고만으로 실제 서버가 구버전이라고 판단하지 않는다. 플러그인은 CLI를 실행하지 않고 HTTP API에 직접 요청하므로, 현재 누락 오류의 원인을 이 구버전 버그로 확정할 수 없다. 플랫폼에 설정된 실제 endpoint의 /api/version, 연결 후보 검사, 생성 요청과 응답을 대조해야 한다. 추론 모드 강제 활성화는 지연·출력 토큰 소모를 늘릴 수 있어 자동 우회하지 않는다.
본문 근거와 재분석: 메타데이터 분석은 문제 창작과 구분한다. 저장된 description/input/output/sample_input/sample_output/hint를 사실 근거로 삼고, 제목이나 문제 번호로 기억하는 다른 문제를 대신 설명하지 않는다. rationale은 한국어 500자 이내의 실제 요구사항 요약과 구체적인 본문·입출력 근거로 구성하며 없는 조건·공식·알고리즘을 추가하지 않는다. 텍스트로 확인할 수 없는 이미지·외부 자료 또는 모순은 한계로 밝히도록 지시한다. 잘못 저장된 DP 분류가 단순 Hello 출력 문제의 재분석을 오염시키지 않도록 current_metadata/accepted_count/submitted_count를 Provider 전송 사본에서 제외한다. 기존 큐 스냅샷과 해시는 변경하지 않아 원본·메타데이터 변경 충돌 검사를 유지한다. 분석은 미저장 편집 내용이 아닌 저장된 원문을 대상으로 한다. JSON 검증 통과나 모델이 반환한 높은 신뢰도는 내용의 정확성을 보증하지 않으며, 수정 적용 뒤 실제 모델 재생성과 초안 검토가 필요하다. 반환 네 필드·DB·공개 Addon API 계약은 변경하지 않는다.
본문 전달과 문맥 한도: Provider용 메타데이터 메시지는 선택 가능한 주제의 key → label 사전을 먼저, 실제 problem을 마지막에 배치한다. 주제 사전은 문제의 입력 데이터가 아님을 명시하며, 상위 분야 레코드와 중복 출력 Schema는 메시지에서 제외한다. 원문·예시를 자르거나 주제를 누락하지 않고 native Schema 및 큐 스냅샷은 유지한다. 설명·입력·출력·힌트에 텍스트 근거가 전혀 없으면 전송 전에 중단한다. Ollama 구조화 요청은 truncate=false와 shift=false를 보내 지원 서버에서 본문을 조용히 버리지 못하게 하며, 확인된 문맥 한도 오류는 자동 재시도 없이 num_ctx 설정 확인을 안내한다. 메모리 용량을 가정해 문맥 크기를 자동으로 올리지는 않는다. 기본 전체 사전과 Hello 테스트의 사용자 메시지는 11,438 → 3,313바이트이며 토큰 수나 실제 모델 판독량을 뜻하지 않는다. 실제 서버 로그·설정으로 입력 잘림 여부를 확인해야 하며 프록시가 두 옵션과 전체 messages를 보존하는지도 점검한다. 초안 보존: AI 문제·테스트데이터 초안은 암호화 Form Draft에 두고 취소·적용·폐기 또는 24시간 만료 때 제거한다. 비밀과 원문 전체를 Jobs 사건 로그에 기록하지 않는다.

SPJ 컴파일

  1. 문제 편집에서 특수 채점기 사용이 켜진 경우에만 spj.c, spj.cc, spj.cpp 중 선택한 한 소스를 컴파일할 수 있다.
  2. problem_spj_compile Job은 Bubblewrap의 분리된 네임스페이스에서 실행한다. /usr와 동적 라이브러리는 읽기 전용, 문제별 임시 폴더는 /build, 제한된 임시 공간은 /tmp로만 노출하고 네트워크와 capability를 제거한다.
  3. C는 gcc -std=c11, C++은 g++ -std=c++17을 기본 프로필로 하고 CPU 시간·메모리·출력 크기·전체 시간을 제한한다.
  4. problem_test_data.spj_sandbox_executable의 승인된 /usr 아래 bwrap과 컴파일러가 준비되지 않으면 작업 등록을 거부한다. 호스트 직접 컴파일로 우회하지 않는다.
  5. 성공한 새 바이너리의 형식·해시·실행 권한을 확인한 뒤에만 문제 폴더의 spj를 원자 교체한다. 실패하면 기존 동작 중인 spj를 그대로 둔다.
  6. 컴파일 로그는 민감 경로를 제거한 뒤 결과 참조로 보존하고 화면에서 성공·실패·컴파일러·시각을 확인한다. 실제 채점 인자 검증은 Judge Adapter가 SPJ 실행 계약을 제공할 때만 추가한다.
파일 원본: 확정된 입출력 파일과 SPJ 소스·바이너리는 문제 데이터 폴더의 루트가 소유한다. 테스트케이스 생성기와 검증 전 결과는 Jobs 임시 영역에서만 다루며 확정 파일만 루트에 반영한다. 플랫폼 DB에는 파일 본문을 복제하지 않고 Jobs에는 경로가 아닌 문제 번호·파일명·해시·크기·결과 코드만 기록한다.
