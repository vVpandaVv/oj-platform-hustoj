모듈·데이터베이스 소유권 재정비

무접두어 배치 제한

플랫폼 전용 테이블은 하나의 물리 WordPress DB에 OJ Platform 설치 하나만 소유한다. 초기 설치 전에 같은 이름의 테이블이 이미 있으면 자동 생성·채택·덮어쓰기를 중단하고 소유자·스키마·행 건수를 읽기 전용으로 검사한 뒤 사용자 승인을 받는다.

앞선 재정비 확정 기준

D-001, D-004, D-005, D-006과 D-007에서 승인해 다시 묻지 않는 계약이다.

재결정 불필요

무접두어 물리명

플랫폼 전용 테이블에는 WordPress 접두어와 oj_를 붙이지 않는다. WordPress 옵션·글 유형의 네임스페이스는 충돌 방지를 위해 유지한다.

사용자 원본

WordPress와 동일하게 숫자 wp_users.ID와 문자열 wp_users.user_login을 구분한다. 플랫폼 user_id는 전자만 의미한다. 로그인 아이디·이메일·비밀번호·표시 이름·별명은 WordPress가 소유하고, user_profiles에는 OJ 전용 소속·소개·생년·이용 상태만 둔다. Judge ID는 저장하지 않는다.

영구 매핑 제거

legacy_id_map을 최종 구조에 두지 않는다. 로그인 전환 중 필요한 Judge 정보는 사용자 확인 후 즉시 WordPress ID로 전환한다.

기능 독립성

Groups가 꺼져도 Classes와 Contests는 정상 동작한다. 비활성 기능은 읽기·쓰기를 막되 테이블과 데이터는 보존한다.

공통 AI 기반

Infrastructure/AI는 공급자 호출만 제공한다. Problems는 AI Feedback에 의존하지 않고, AI Feedback은 Problems·Submissions의 공개 읽기 계약만 단방향으로 사용한다.

안전한 이전

읽기 전용 보고서와 복구 시험 없이 자동 복사·이름 변경을 시작하지 않는다. 쓰기 동결 상태에서 최종 차이를 반영하고 원자적으로 전환한 뒤 7일간 관찰한다.

공통 AI와 업무 모듈의 경계

Infrastructure/AI의 Ai_Client_Interface는 공급자 통신을, Ai_Task_Router는 작업별 주·대체 연결 프로필 해석을 담당한다. OpenAI·MLX-LM·vLLM·SGLang·OpenAI 호환 AI Gateway는 공통 OpenAI 호환 Adapter와 Provider Profile을 사용하고, Gemini·Ollama만 전송 구조별 Adapter를 사용한다. 주소 분리·인증·응답 매핑의 단일 기준은 DS-15 AI Provider 통신 계약이다. Problems는 메타데이터·문제 작성·테스트케이스 프롬프트와 난이도 1~5·세부 주제·초안 검증·적용을 소유하고 AI Feedback은 제출 피드백 프롬프트·검증·저장을 소유한다. AI 호출은 각 기능 Handler가 task_type으로 Jobs에 등록해 WordPress Worker에서 실행하며 Judge 서버와 Judge DB는 호출에 참여하지 않는다. AI Feedback은 Problems·Submissions의 내부 Repository나 Service가 아니라 공개 읽기 Provider만 사용하며 역방향 의존은 금지한다.

Jobs 의존 경계

Jobs Core는 platform_db와 settings에만 직접 의존한다. Job_Http_Adapter는 permission, access_router, admin_console이 준비된 뒤 조립되어 D-002·D-003의 화면과 액션을 연결한다. 선택 기능은 Handler와 접근 정책을 Registry에 등록할 뿐 Jobs가 선택 기능을 역으로 참조하지 않는다.

Migration 잠금 조건

Migration은 사용자가 켜고 끄는 기능이 아니다. 사용자·DB 전환이 끝날 때까지 관리자에게만 노출되는 잠금 모듈로 유지한다. Judge 사용자 대체 인증은 전환 대상 전원 완료 또는 사용자가 승인한 전환 마감일 뒤 지원·복구 경로로 이관된 경우에만 닫을 수 있으며, 이 종료 검사와 D-008의 7일 관찰·제거 승인을 모두 통과한 뒤 코드와 등록을 함께 제거한다.

모듈과 기능 플래그 구분

현재 모듈 19개는 필수 기반 8개·사용자 선택 10개·전환 잠금 1개다. D-003의 기능 플래그 30개는 화면·권한·작업을 켜는 더 세분된 정책 키이므로 모듈 수와 일대일로 맞추지 않는다. Jobs는 공통 기반 모듈이다. 관리 작업 화면은 admin_console과 작업 소유 기능을 함께 확인하고, 제출 상세처럼 사용자 화면에 포함된 작업은 해당 공개 경로와 Handler 정책을 확인한다. 작업 종류별 Handler는 조회·관리 권한을 함께 등록하고 Migration 작업은 실행자 여부와 관계없이 oj_manage_migration을 요구한다.

모듈 간 데이터 접근 계약

한 테이블의 쓰기 경로를 하나로 제한하는 규칙이다.

필수 경계
  1. 쓰기 단일 소유: 테이블을 소유한 모듈의 Repository와 Service만 INSERT·UPDATE·DELETE를 수행한다.
  2. 읽기 계약: 다른 모듈은 소유 모듈의 Query Service 또는 Read Provider를 생성자 의존으로 받는다.
  3. 화면 코드 제한: Controller·Renderer·PublicUi·AdminConsole에서 $wpdb나 Judge SQL을 직접 실행하지 않는다.
  4. 선택 기능: Groups·AI·Blockly처럼 꺼질 수 있는 기능은 Optional Provider를 사용하고 없을 때의 기본 동작을 명시한다.
  5. 두 DB 작업: WordPress DB와 Judge DB를 한 트랜잭션으로 가정하지 않는다. Jobs 단계·멱등키·검증·보상으로 조정한다.
  6. 외부 Judge 소유: JudgeDb는 연결과 매핑을 제공할 뿐 업무상 쓰기 권한을 갖지 않는다. 각 기능 Repository가 허용된 명령만 수행한다.
  7. 문제 제출 코드 정책: Problems는 기존 Judge problem.bann·front·body·rear와 PlatformDb 빈칸 스키마·템플릿 해시를 소유하고 불변 Read Provider로 제공한다. Submissions는 이를 복제 저장하거나 직접 SQL하지 않고, 전체 코드·코드 빈칸 완성·Blockly 공통 Validator와 Composer에서만 소비한다.

전환 파동과 롤백 경계

기본 파동은 Auth 사용자 기반 → Problems → Submissions → Classes → Contests → Groups → AI Feedback 순서이며 Jobs는 신규 무접두어 테이블로 먼저 시작한다. 의존 소비자 검사가 실패하면 다음 파동으로 가지 않는다. 6단계 뒤 대상 새 테이블에 쓰기가 한 건이라도 발생하면 포인터만 되돌리지 않는다. 다시 해당 쓰기를 동결하고 새 구조의 차이를 기존 구조에 역반영해 검증하거나 승인된 복구 시점으로 관련 DB와 파일을 함께 복원한다. 단계별 Jobs 체크포인트와 사건 이력이 어느 경로를 사용했는지 증명해야 한다.

재정비 확정 결정

기존 다섯 항목, 서비스 담당 범위와 퀴즈 공유 버전 저장 방식을 확정했다.

7건 확정

  1. DB-Q01 · Jobs 모듈 구분

    확정: Jobs를 9번째 필수 기반 모듈로 추가한다. Jobs Core는 platform_db와 settings에만 직접 의존하고, Job_Http_Adapter는 permission·access_router·admin_console 준비 뒤 조립한다. 선택 기능은 Handler와 접근 정책을 등록하되 Jobs가 선택 기능에 역의존하지 않는다.

  2. DB-Q02 · 기능별 스키마 등록 형식

    확정: 각 모듈이 모듈 키·버전·테이블·선행 스키마·비파괴 변경·검사·보존 정책을 제공하고 PlatformDb는 등록·순서·버전 상태만 관리한다.

  3. DB-Q03 · 수업 공동 강사 테이블

    확정: classes.owner_user_id를 소유자로 두고 class_instructors에는 id, class_id, user_id, role, status, granted_by_user_id, granted_at, revoked_at, created_at, updated_at을 둔다. (class_id,user_id)는 고유키로 사용한다.

  4. DB-Q04 · 물리 외래키 적용 범위

    확정: 같은 모듈의 안정된 플랫폼 테이블 관계에는 외래키를 사용한다. WordPress·Judge 테이블 참조와 선택 모듈 간 관계에는 물리 외래키를 두지 않고 인덱스·Service 검증·고아 검사로 관리한다.

  5. DB-Q05 · AI 피드백 테이블 이름

    확정·보완: 제출별 AI 피드백을 저장하는 ai_assist를 용도가 분명한 submission_ai_feedback으로 변경한다. 공통 AI 연결 프로필과 작업별 배정은 플랫폼 테이블이 아니라 각각 독립된 WordPress 옵션과 소유 설정 계약으로 유지한다.

  6. DB-Q06 · 서비스 수업·대회·문제 담당 범위

    확정: 수업은 classes.owner_user_id·class_instructors, 대회는 contest_settings.owner_user_id·contest_managers, 문제는 problem_ownerships·problem_collaborators를 사용한다. 대회 담당 역할은 공동 운영자·시험 감독자·결과 검토자, 문제 담당 역할은 공동 편집자·테스트데이터 담당자로 제한한다. 기존 담당자는 자동 추정하지 않고 검증·승인 뒤 배정한다.

  7. DB-Q07 · 퀴즈 공유 게시 버전

    확정: 응시자별 문항·선택지·채점 기준 스냅샷을 저장하지 않는다. 게시할 때만 불변 quiz_revisions와 그 문항·선택지를 만들고 모든 시도는 해당 버전 ID를 참조한다. 게시 버전 보호를 해제해 일괄 재적용할 때도 기존 버전·시도·결과를 수정하지 않고 안정된 질문·선택지 키를 검증한 대체 시도 또는 재채점 결과를 부모 시도와 연결해 같은 5개 테이블에 저장한다. 응시 시작은 요약 1행, 제출은 답안 항목만 일괄 저장하며 참조 버전은 캐시 가능한 읽기 원본으로 사용한다.
