DS-02 · 공통 기반 CF-1

Permission 모듈 상세 설계

WordPress 역할·capability와 수업·대회·문제·그룹의 대상별 담당 관계를 하나의 권한 판정 계약으로 연결하고, 관리자가 이를 이해하고 운영할 수 있는 “역할과 권한” 화면을 새로 만든다. 메뉴, 직접 주소, 명령, Jobs와 조회 범위가 실제 사용자 경험에서 같은 결과를 내는 것이 목표다.

작성일: 2026-07-22확정일: 2026-07-22상태: 사용자 확정 · DS-02 설계 동결사용자 키: 숫자 wp_users.ID근거: D-001·D-003·D-006·D-008·DS-01
핵심: 현재 capability 60개·WordPress 역할 15개·preset 9개를 기준선으로 보존하고, 가입 승인을 사용자 수정에서 분리하기 위해 oj_approve_user_registrations, oj_registration_approver 역할과 registration_approver preset을 각각 하나 추가한다. 목표는 capability 61개·역할 16개·preset 10개다.
전체 순서에서의 위치: 이 문서는 전체 설계·개발 순서의 DS-02이며, 확정된 DS-01 공통 UI 시스템을 역할 화면에 적용했다. DS-02 확정 뒤에는 구현하지 않고 DS-03 CF-2 Settings 상세 설계로 이동한다.
구현 상태: 별도 재구축 작업 트리에서 61개 capability·16개 역할·10개 preset과 대상 보호 Policy를 구현했다. 운영 역할을 자동 변경하거나 운영 DB에 적용하지 않았으며 실제 적용은 별도 설치·이전 승인 절차를 따른다.

현재 핵심 위험: 알 수 없는 capability가 기본 global로 취급되고, can()이 scope와 무관하게 모든 Context Rule을 순회한다. 목표 구현은 등록되지 않은 키와 허용되지 않은 맥락 조합을 관리자 포함 전부 거부한다.

책임과 금지 경계

Permission이 판정 규칙을 조정하되 기능 데이터의 소유권은 가져오지 않는다.

단일 책임
구분Permission 소유기능 모듈 소유
전역 권한capability 정의 검증, WordPress 역할 설치, 관리자 우회자기 기능 capability의 업무 의미와 사용 위치
대상별 권한Context Rule Registry, 공통 판정 순서, 중복 방지소유자·담당자 관계 조회와 역할별 허용 작업
목록 범위Area Access Provider 계약과 결과 조정허용 대상 ID 조회·페이지 범위 제한 SQL
메뉴·경로판정 API만 제공AdminConsole은 메뉴, AccessRouter는 직접 주소, 기능 Service는 업무 재검사
기능 상태소유하지 않음Feature Guard가 Permission 호출 전에 기능 ON/OFF 판정
감사역할 동기화 차이와 실행 결과담당자 부여·해제와 업무 명령의 감사 기록
  1. Permission은 Classes·Contests·Problems·Groups Repository를 직접 참조하지 않는다.
  2. 선택 모듈은 활성화된 경우에만 자기 규칙을 등록하며, 꺼져도 Permission 부팅은 성공한다.
  3. 메뉴 노출은 편의 기능이고 보안 경계가 아니다. Router와 Service가 같은 요청을 다시 판정한다.
  4. 플랫폼 사용자 입력은 숫자 user_id = wp_users.ID만 사용한다. 로그인 아이디는 권한 관계 키가 아니다.
  5. Permission은 별도 플랫폼 테이블을 만들지 않는다. WordPress 역할 API와 소유 모듈의 관계 테이블을 사용한다.

권한 판정 순서

하나의 요청이 허용되는 순서를 고정해 호출 위치마다 결과가 달라지지 않게 한다.

기본 거부
1입력 검증
2등록 키 확인
3관리자 판정
4전역 capability
5Context Rule
6허용 또는 거부
순서검사실패 처리
1 · 입력user_id > 0, capability 형식, 필요한 target ID와 operation 확인즉시 거부
2 · Registrycapability가 등록되어 있고 요청 context type이 정의와 일치하는지 확인관리자도 거부하고 기술 로그에 등록 오류 기록
3 · 관리자super admin 또는 manage_options 보유자 확인등록된 OJ capability에 한해서만 우회 허용
4 · 전역global·global_or_context·creation 범위에서 WordPress capability 확인맥락 허용 범위가 있으면 다음 단계로 진행
5 · 맥락정확히 하나의 Rule이 현재 소유·담당 관계와 operation을 조회규칙 없음·중복·비활성 관계·범위 밖 작업은 거부
6 · 결과명시적으로 허용된 경우만 true그 밖의 모든 경우 false
호출 순서: 화면과 작업은 기능 상태 → 로그인 → Permission → 대상 존재·업무 상태 → 행 범위 순으로 검사한다. Permission은 기능 플래그나 대상의 게시·마감 상태를 대신 판정하지 않는다.
최고 관리자 전용 Policy: console.problems.topics와 oj_problem_topic_create는 위임 가능한 capability 판정에 들어가기 전에 super_admin_only를 검사한다. 따라서 oj_manage_problems, 문제 소유·협업 범위 또는 manage_options만으로는 통과하지 못하며 WordPress 최고 관리자만 접근한다.
설치 전 권한 예외: 플랫폼 역할과 61개 capability가 아직 설치되지 않은 상태에서는 SetupBootstrap 화면·단일 액션만 WordPress 내장 manage_options로 보호한다. 이 예외는 정상 Permission Registry에 capability를 추가하지 않으며 설치 완료 뒤 Hook 등록 0개가 된다. 역할 생성과 현재 관리자에게 플랫폼 최고 관리자 역할을 부여하는 작업은 설치 계획에서 별도로 확인받는다.

캐시: WordPress 사용자 객체와 같은 요청 안의 동일 판정만 요청 범위에서 캐시한다. 영구 캐시는 사용하지 않으며 역할·담당 관계 변경 서비스는 해당 요청 캐시를 즉시 무효화한다.

그룹 위임 운영자 보강 확정: 위임 운영자도 oj_bulk_register_group_members와 oj_reset_group_member_password를 자기 그룹 Context에서 사용할 수 있다. 일괄 등록은 생성·연결 결과를 항목별로 남기고, 비밀번호 초기화는 구성원 목록의 행 또는 선택 항목에서 최대 100명까지 제공한다.
비밀번호 초기화 경계: 대상은 같은 그룹의 승인된 일반 구성원이어야 하며 소유자·활성 위임 운영자·전역 계정 관리자·행위자 본인은 제외한다. 이메일은 필수가 아니다. Auth Service가 무작위 임시 비밀번호를 성공 화면에 한 번만 제공하고 기존 세션을 폐기한 뒤 다음 로그인에서 새 비밀번호를 정하게 한다. 실행 직전 각 대상의 구성원·운영자·계정 역할을 다시 확인하고 그룹, 행위자, 대상, 시각과 안전한 결과 코드만 감사 사건으로 남긴다.
그룹 평가 모드 확정: 그룹 소유자와 활성 위임 운영자는 oj_edit_groups와 operation=change_evaluation_mode를 통과한 자기 그룹에서 일반 모드와 수행 모드를 전환한다. 수행 모드의 일반 구성원은 제출 목록에서 문제, 제출 시각, 채점 결과만 확인하며 상세 링크와 코드 동작을 제공하지 않는다.
전환 UI: 그룹 운영 설정에 일반 모드 / 수행 모드 2개 항목의 분할 선택 컨트롤을 둔다. 수행 모드 선택 시 “제출은 계속 가능하고 일반 구성원의 제출 결과 상세·코드만 제한됩니다”라는 영향을 확인한 뒤 즉시 적용하며, 변경 사용자와 시각을 기록한다.
제출 동작 유지: 수행 모드는 문제 풀이, 코드·블록 제출, 채점 요청, 채점 상태 갱신과 제출 결과 목록을 제한하지 않는다. 제한 대상은 제출 결과 상세 페이지와 그 페이지가 사용하는 코드·오류·테스트·성능 상세·AI 피드백 생성·조회뿐이다.
우회 방지 범위: 화면에서 링크만 숨기지 않는다. 문제·수업·대회·그룹과 전역 제출 목록에서 여는 모든 제출 결과 상세 URL, 상세 AJAX·REST, 상세 내보내기와 AI 피드백 Jobs 등록·상태·결과 조회가 같은 가시성 정책을 사용한다. 브라우저 상세 요청은 제출 목록으로 돌려보내고 제한 안내를 표시하며 API는 상세 데이터 없이 403을 반환한다. 현재 제출에 신뢰할 수 있는 그룹 귀속값이 없으므로 활성 수행 모드 그룹의 일반 구성원인 동안에는 본인 제출 전체를 result_only로 제한하고, 여러 활성 그룹 중 하나라도 수행 모드이면 제한을 유지한다. 그룹을 일반 모드로 바꾸거나 구성원 관계를 종료하면 다음 요청부터 복원한다.
운영자 예외: 전역 제출 관리자는 전체 조회를 유지한다. 그룹 소유자와 활성 위임 운영자는 자신이 관리하는 그룹의 활성 구성원 제출만 전체 조회할 수 있다. 대상 사용자가 다른 수행 모드 그룹에도 속해 있고 조회자가 그 그룹을 관리하지 않으면 더 제한적인 결과만 정책을 적용한다.
파괴 작업: 사용자 영구 삭제, 제출 영구 삭제, 문제 영구 삭제, 문제 번호 변경, XML 일괄 작업, 데이터 이전과 시스템 변경은 대상 관계로 허용하지 않고 전역 고위험 권한과 별도 확인 절차를 요구한다.

DS-02 확정 결과

권한 범위와 학습 운영 방식을 2026-07-22 사용자 확인으로 동결했다.

4건 확정
  1. DS02-Q01 · 대상별 역할 · 확정: 위 권한표대로 소유자는 담당자를 지정하고, 공동 강사·공동 운영자·편집자는 자기 업무만 수행하며 소유권과 담당자 변경은 하지 못하게 한다. 그룹 위임 운영자는 자기 그룹의 승인된 일반 구성원에 한해 일괄 등록과 단건·선택 일괄 비밀번호 초기화를 수행하고 일반·수행 모드를 전환한다. 활성 수행 모드 그룹의 일반 구성원은 그룹 안팎에서 생성한 본인의 모든 제출에서 결과 목록만 확인하고 결과 상세·코드는 조회하지 못한다. 제출·채점은 계속 허용한다.
  2. DS02-Q02 · 보관과 영구 삭제 · 확정: 수업·대회·그룹·문제 소유자는 자기 대상을 보관할 수 있지만 영구 삭제와 문제 번호·XML 일괄 작업은 전역 고위험 권한으로 제한한다.
  3. DS02-Q03 · 역할 업그레이드 · 확정: 자동 업그레이드는 누락 권한 추가만 수행하고, 권한 제거는 차이 미리보기·명시적 승인·snapshot 이후에만 실행한다.
  4. DS02-Q04 · WordPress 범위 · 확정: 우선 현재 사이트의 역할만 관리하고, 멀티사이트 네트워크 전체 역할 동기화는 이번 CF-1 범위에서 제외한다.
확정·구현: DS02-Q01~Q04, 수행 모드의 전체 본인 제출 상세 제한과 가입 승인 전용 capability·역할 분리를 유지한다. 61 capability·16 역할·10 preset의 재구축 코드는 R-03~R-04에서 구현·검사했으며 운영 역할과 DB는 변경하지 않았다.
