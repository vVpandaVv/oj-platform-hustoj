제출 상세 설계

학습자에게는 문제 풀이부터 채점 결과 확인까지 단순한 흐름을 제공하고, 강사에게는 담당 범위 안의 제출 조회·재채점·감사를 제공한다. 제출 원본과 채점 결과는 HUSTOJ 테이블을 유지하며 플랫폼은 접근 정책과 처리 이력만 소유한다.

작성일: 2026-07-23기능 확정일: 2026-07-23시안 확장: 2026-07-24 · 직접 화면 12개최종 확정일: 2026-07-26상태: 사용자 확정 · 기능·UI 설계 동결선행 설계: DS-00~DS-10 확정실행: I-00 뒤 I-04근거: D-002·D-003·D-005·D-008·DS-02·DS-03·DS-04·DS-05·DS-06·DS-07·DS-09·DS-10·DS-16
전체 순서에서의 위치: 이 문서는 전체 설계·개발 순서의 DS-11 단일 원본이다. 일반 코드 제출, 코드 빈칸 완성, Blockly 편집기·블록 제출의 화면·권한·생성·저장·채점 연동과 DS11-Q01~Q08을 사용자 확정으로 동결했다. 실제 코드는 I-00 보호 환경을 통과한 뒤 I-04에서 구현한다.

사용자·관리자 직접 화면 12개는 두 시안으로 보고 Blockly 편집기는 이 문서의 다음 절에서 확인한다.

수량: 사용자 5개와 관리자 7개, 총 12개 직접 GET 화면을 유지한다. /submit/{problem_id} 안에서 전체 코드·Blockly 상태와 코드 빈칸 완성 상태를 문제 정책에 따라 배타적으로 렌더링하므로 Blockly와 빈칸 편집기를 별도 GET 화면으로 계산하지 않는다.
공통 화면 구조: 사용자 결과 상세와 관리자 제출 상세는 같은 결과 요약·코드·오류·메타데이터 구성과 공통 CSS를 사용한다. 문제 번호·제목·제한과 문제 정책이 허용한 작성 방식은 /submit/{problem_id} 사용자 화면이 한 번만 출력한다. 전체 코드 문제만 Ace 코드·Blockly 선택을 표시하고, 빈칸 완성 문제는 전용 공통 구성요소만 표시한다. Ace는 플러그인 내부 자산·계정 테마·언어 모드·원본 textarea 동기화 계약 하나를 사용하며 Blockly와 빈칸 편집기도 화면별 마크업·검증 로직을 복제하지 않는다.
DS-12 경계: 수업·그룹·대회의 실시간 제출 6개와 보관 제출 3개는 DS-12 화면 시안이 소유한다. DS-11은 해당 화면에 Query·Policy Projection만 제공한다.

핵심 사용 흐름

학습자는 작성과 결과 확인에 집중하고 관리 작업은 별도 화면으로 분리한다.

7개 흐름
학습자문제 → 풀이하기 → 코드 제출

문제 상세의 풀이하기 버튼으로 전용 제출 화면에 진입한다.

학습자형광색 빈칸 선택 → 코드 입력 → 제출

빈칸 완성 문제는 고정 코드를 수정하거나 일반 코드·Blockly로 전환하지 않고 필수 빈칸만 작성한다.

학습자블록 모드 선택 → 작성 → 제출

블록 모드를 고른 시점에만 Blockly를 불러오며 제출 언어는 Python 3으로 자동 고정된다.

학습자제출 → 채점 중 → 결과

현재 상세 화면에서만 상태를 갱신하고 완료되면 허용된 결과를 표시한다.

수행모드 학습자제출 → 결과만 확인

제출은 계속 가능하지만 상세·코드·컴파일·런타임·AI 피드백은 열리지 않는다.

담당 강사범위 선택 → 제출 검토 → 재채점

자신에게 할당된 수업·그룹·대회·문제의 제출만 처리한다.

시스템 관리자설정 → 진단 → 감사

언어와 Blockly 자산을 관리하고 민감 작업 이력을 확인한다.

용어 기준: 화면과 메뉴는 모두 “제출”을 사용한다. Judge 기본키와 DB 열 이름은 HUSTOJ 호환 때문에 solution_id를 유지하지만 사용자에게 “솔루션”이라는 용어를 노출하지 않는다.

제출 가시성 정책

한 번의 판정이 화면·AJAX·파일·Jobs에 동일하게 적용되어야 한다.

확정 계약 유지
판정허용금지Repository 동작
full목록 결과, 상세 요약, 소스, 컴파일·런타임 정보, 허용된 AI 피드백담당 범위 밖 데이터판정 완료 뒤 필요한 상세 테이블만 조회

  • 학습자의 /submissions와 문제별 제출 화면은 본인 제출만 표시한다.
  • 강사·그룹 위임 운영자·대회 담당자는 각 모듈이 제공한 검증된 담당 범위 안에서만 다른 사용자의 제출을 볼 수 있다.
  • 그룹 일반 사용자가 하나 이상의 활성 수행모드 그룹에 속하면 그룹 안팎에서 제출한 본인의 모든 제출이 result_only가 된다.
  • 수행모드는 제출 요청을 차단하지 않는다. 제한 대상은 결과 상세·코드·오류 정보·AI 피드백 조회다.
  • Groups는 선택적 정책 Provider만 등록한다. Groups가 꺼지면 Submissions 기본 정책으로 돌아가며 수업과 대회는 정상 동작한다.
  • 화면 버튼을 숨기는 것만으로 끝내지 않고 직접 URL, AJAX, 파일 응답, AI Jobs 입력에서도 같은 정책을 다시 판정한다.
정보 노출 방지: result_only 또는 denied에서는 먼저 소스·컴파일·런타임 행을 읽은 뒤 버리는 구현을 금지한다. 권한 Projection을 정한 다음 필요한 열만 읽는다.

제출 명령과 Judge 공개 순서

MyISAM 가능성을 고려해 데이터베이스 트랜잭션이 없어도 불완전 제출이 채점되지 않게 한다.

보상 처리 필수
단계검증·저장실패 처리감사 이벤트
1. 요청·소스 검증nonce, 요청 멱등 키, 숫자 WordPress 사용자 ID, 문제·수업·대회 접근, 제출 모드, 간격·제출 가능 상태를 검사한다. 코드 모드는 사용자 원본, 블록 모드는 검증된 작업공간에서 서버가 다시 만든 Python 3, 빈칸 모드는 최신 problem.body와 검증한 ID별 답안으로 서버가 다시 만든 완성 코드를 원본으로 삼는다. 2. 준비 행 생성solution을 Judge가 가져가지 않는 result=2 상태로 생성하고 solution_id 확보생성 실패 시 종료submission_prepare_started

  • 플랫폼 내부에서는 숫자 WordPress 사용자 ID를 사용한다. Judge solution.user_id가 문자열을 요구하는 경계에서 이미 읽은 WP_User.user_login만 전달한다.
  • 제출 요청 중 Judge users를 조회하거나 Judge ID를 다시 매핑하지 않는다. Judge 사용자 참조는 로그인 마이그레이션의 예외 절차에서만 허용한다.
  • 컨테스트 문제 번호는 Contests가 검증해 전달한 contest_id·num 문맥만 기록한다. Submissions가 contest·contest_problem 정책을 복제하지 않는다.
  • 브라우저가 보낸 금지 목록·앞 코드·뒤 코드와 이미 결합된 소스는 신뢰하지 않는다. 전체 코드는 원본 소스, Blockly는 작업공간, 빈칸 완성은 템플릿 해시와 ID별 답안만 입력으로 받으며 서버가 최신 문제 정책으로 다시 만든다.
  • 금지 검사는 사용자 원본 또는 서버 생성 Blockly 코드에만 수행한다. 권한 있는 문제 편집자가 저장한 앞·뒤 코드는 신뢰 경계 안의 코드로 보고 별도 구문·크기 검사를 통과한 값만 결합한다.
  • 앞 코드·원본·뒤 코드 사이에는 필요한 경우 정확히 하나의 LF를 넣어 토큰이 맞붙지 않게 하며 빈 필드는 건너뛴다. 클라이언트 미리보기와 서버 Composer가 각각 다른 결합 규칙을 만들지 않는다.
  • 소스 원문·Blockly 작업공간 JSON·컴파일 오류는 submission_events.metadata에 저장하지 않는다.

블록 선택로컬 고정 Blockly 12.5.1과 Python 3 생성기를 지연 로딩하고 현재 제출에 Python 3 자동 허용CDN 대체·외부 JS·문제 언어 설정 변경 금지
블록 제출submission_mode=blockly, 작업공간 버전·크기·프로필·허용 블록을 검증하고 서버가 Python을 재생성한 뒤 코드 제출과 같은 금지 코드 Validator·앞·뒤 코드 Composer를 적용source_code에는 앞·뒤 코드가 결합된 최종 Python, source_code_user에는 결합 전 생성 코드와 압축 blockly-json-v1
완료·로그아웃현재 탭 초안 제거localStorage 영구 저장과 제출별 자동 스냅샷 금지
  • Blockly 모듈은 엔진 버전, 블록 Registry, Python 생성기, 입문·표준·확장 프로필과 로컬 자산 상태를 소유한다.
  • 전역 설정은 기능 활성과 기본 프로필만 선택하며 수업·그룹·대회는 더 넓은 프로필을 선택할 수 없다.
  • 클라이언트 미리보기 코드와 표시 주석은 신뢰하지 않고 서버 Registry와 생성기로 결과를 다시 만든다.
  • 문제 상세·전체 코드·빈칸 완성·Blockly 제출은 같은 금지 코드와 앞·뒤 코드를 표시한다. Blockly iframe의 생성 코드와 빈칸 화면의 완성 코드는 즉시 안내용이며 제출 판정의 원본이 아니다.
  • 빈칸 완성과 Blockly는 같은 문제에서 동시에 선택하지 않는다. 빈칸 완성은 문제 템플릿 언어 하나로 고정하고 Blockly는 전체 코드 작성 문제에서 허용한 경우에만 표시한다.
  • 별도 Blockly 테이블은 만들지 않으며 학습자 작업공간은 현재 탭과 제출된 source_code_user 한 곳에만 둔다.

  • solution.result 0~17의 번호·문구·처리 상태가 HUSTOJ 결과 코드 표와 일치하며 모든 모듈이 단일 Judge_Result_Catalog를 사용한다.
  • Ace 코어·공식 테마·지원 언어 모드는 플러그인 배포 ZIP 안에 있고 외부 CDN을 요청하지 않는다. 코드 모드가 아닌 페이지에서는 Ace를 불러오지 않으며 실패 시 이름 있는 원본 textarea로 제출할 수 있다.
  • 관리자가 막은 언어는 계정 설정의 기본 제출 언어와 제출 화면 양쪽에서 보이지 않고 직접 조작한 저장·제출 요청도 거부된다. 저장된 기본 언어가 나중에 차단되면 현재 허용 언어로 폴백한다.
  • Blockly 자산은 블록 모드 선택 전 네트워크·스크립트 실행 기록에 나타나지 않는다.
  • 직접 Python 제출이 금지된 문제에서도 정상 작업공간을 사용한 블록 제출은 Python 3으로 채점되고, 작업공간 없이 submission_mode=blockly만 위조한 요청과 직접 Python 코드는 거부된다.
  • 수행모드에서 그룹 밖에서 만든 본인 제출도 상세·코드·오류·AI 피드백이 차단된다.
  • Groups 모듈을 꺼도 일반 제출, 수업 제출, 대회 제출이 정상 동작한다.
