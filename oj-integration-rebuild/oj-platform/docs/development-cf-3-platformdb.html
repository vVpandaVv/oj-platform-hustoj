DS-04 · 공통 기반 CF-3

PlatformDb 상세 설계

플랫폼 데이터의 물리 이름·소유권·버전·활성 위치를 한 기반에서 관리하되, 각 기능이 자기 스키마와 데이터 수명주기를 소유하도록 재정비한다. 운영 자료는 자동 채택하지 않고 검증·승인·복구 관문을 통과한 모듈만 전환한다.

작성일: 2026-07-22확정일: 2026-07-23상태: 사용자 확정 · 설계 동결Judge 스키마 보존: 사용자 확정선행 설계: DS-00~DS-03 확정근거: D-004·D-005·D-006·D-008·DS-03
전체 순서에서의 위치: 이 문서는 전체 설계·개발 순서의 DS-04다. 42개 무접두어 Schema Registry와 신규 설치 파동을 재구축 코드에 구현했고 R-04에서 Auth 7개 생성 정의를 연결했다. 운영 스키마 생성·이전은 아직 실행하지 않았다.

현재 상태 검사의 테이블 존재 확인열·인덱스·엔진·문자셋·소유 충돌·활성 맵 불일치를 발견하지 못한다.Registry fingerprint와 실제 information_schema를 비교하는 명시적 진단을 제공한다.
자동 채택 금지: 목표 이름의 테이블이 이미 존재해도 OJ Platform 자료라고 추정하지 않는다. 구조·소유 표식·기존 옵션·건수 보고서를 확인하고 사용자 승인을 받은 경우에만 복구 또는 이전 대상으로 등록한다.

실행 가능한 스키마 Registry

문자열 DDL이 아니라 구조화 정의를 등록하고 부팅 뒤 봉인한다.

모듈별 등록
정의필수 속성검증
모듈 정의module_key, schema_version, 선행 모듈·최소 버전, 정책 승인 버전알 수 없는 모듈·순환 의존·버전 역행 차단
테이블 정의논리명·물리명·소유 모듈·설명·수명주기·엔진·문자셋 정책물리명 중복, 접두어, 예약어, 64자 초과 차단
열 정의이름·타입·길이·unsigned·NULL·기본값·자동 증가·민감도타입별 불가능한 기본값과 암묵적 변환 차단

외래키·CHECK대상·열·삭제/갱신 동작·허용값 또는 범위같은 소유 모듈의 안정 관계와 DB 기능 지원 여부 확인
업그레이드 단계단계 키·from/to 버전·사전 조건·변경·사후 조건·되돌림 가능 여부중간 버전 누락·중복 단계·파괴 변경 자동 실행 차단
  1. 각 기능 모듈은 자기 테이블 정의만 등록하고 다른 모듈 정의를 수정하지 않는다.
  2. PlatformDb는 전체 정의의 충돌·의존 순서·DB 지원 기능을 검사한 뒤 Registry를 봉인한다.
  3. 실행 계획은 봉인된 Registry 버전과 실제 DB fingerprint를 함께 기록해 실행 중 정의 변경을 막는다.
  4. 모듈이 비활성화되어도 스키마 정의와 기존 데이터는 유지하고 새 업무 쓰기만 기능 상태로 차단한다.

42개 정의가 같은 데이터 의미와 DB 동작을 사용하게 한다.

  1. 전환 전에는 기존 접두어 테이블을 가리키는 legacy 맵을 유지하고 목표 구조는 준비 상태로만 둔다.
  2. 소유 모듈 쓰기 동결·최종 복사·관계 검증을 통과한 뒤 그 모듈 항목 하나만 교환한다.
  3. 활성 맵은 요청 시작에 한 번 읽고 revision별 메모리 캐시를 사용하므로 사용자·제출마다 별도 ID 또는 테이블 조회를 추가하지 않는다.
  4. 새 구조에 쓰기가 발생한 뒤에는 포인터만 되돌리지 않고 차이 역반영 검증 또는 승인된 백업 복원을 수행한다.

일반 요청과 구조 변경을 분리하고 DDL의 비트랜잭션 특성을 드러낸다.

  3. 기능을 켤 때 필요한 스키마가 없으면 DS-03 기능 사전 검사가 켜기를 차단하고 준비 작업으로 안내한다.

  5. MySQL 계열 DDL은 암묵적 커밋이 있으므로 전체 트랜잭션 성공을 주장하지 않고 단계 체크포인트와 사후 조건으로 복구한다.

사용자 확정 결과

아래 여섯 항목을 2026-07-23 확정하고 DS-04를 동결했다.

6건 확정
  1. DS04-Q01 · DB 배치 · 확정: PlatformDb는 WordPress DB 연결 안의 무접두어 42개 테이블이며, 이름 충돌을 막기 위해 물리 DB 하나당 OJ Platform 설치 하나만 허용한다.
  2. DS04-Q02 · 수량·소유 · 확정: D-008의 8개 소유 영역·42개 테이블을 유지하고 공통 기반에서는 Jobs 4개만 먼저 준비하며 나머지는 기능 파동에서 활성화한다.
  3. DS04-Q03 · Registry·물리 규칙 · 확정: 각 기능이 구조화 스키마를 등록하고 PlatformDb가 충돌·의존·InnoDB·utf8mb4·CHECK·인덱스·FK 규칙을 검증한다.
  4. DS04-Q04 · 충돌 정책 · 확정: 동명 테이블은 자동 채택·변경·이름 변경하지 않고 설치 ID·소유 표식·구조·건수 보고서와 사용자 승인으로만 등록한다.
  5. DS04-Q05 · 실행·복구 · 확정: 일반 요청의 자동 DDL을 제거하고 계획·승인·잠금·단계 실행·사후 검증을 사용하며 파괴 변경과 데이터 이전은 Migration Jobs로 분리한다.
  6. DS04-Q06 · 활성 스키마 맵 · 확정: 설치 버전과 활성 버전을 분리하고 소유 모듈별 원자 전환·7일 관찰·새 쓰기 전후의 서로 다른 복구 절차를 적용한다.
고정 경계: HUSTOJ 기본 채점 8개와 활성화한 custominput 선택 프로필의 물리 스키마를 유지하고 사용자 식별 변환을 JudgeDb 어댑터에만 둔다. sim과 solution2는 사용하지 않고 관련 설정을 0으로 고정하며, source_code_user는 별도 제출 호환 계약으로 유지한다.
후속 승인 변경 · DS05-Q05: 제출 게시 전 요청을 영구 선점할 수 있도록 Submissions 소유의 기존 submission_events 정의에 nullable request_key varchar(64)와 고유키를 추가했다. 42개 테이블 수·소유권·활성화 순서는 바뀌지 않으며 D-008의 속성 사전을 Registry 입력 원본으로 사용한다.
후속 승인 변경 · DS15-Q10: 신규 설치는 WordPress 관리자 전용 일시 마법사에서 실행한다. PlatformDb의 기존 4+38 순서와 충돌 정책을 그대로 사용하며 활성화 Hook DDL, 자동 DROP과 Migration 호출은 추가하지 않는다. Judge 확장 열은 마법사 뒤 JudgeDb 연결 적용 단계가 별도로 소유한다.
후속 승인 변경 · R-07/R-11: 대회별 문제 배점을 정규화한 contest_problem_settings와 제출 당시 수업·그룹 문맥을 고정한 submission_contexts를 각 소유 모듈에 추가했다. 총계는 42개, 신규 설치는 Jobs 4개와 소유 모듈 38개 파동이며 HUSTOJ 스키마에는 열·테이블을 추가하지 않는다.
확정·구현: DS04-Q01~Q06과 Judge 고정 경계를 설계 기준으로 유지한다. Registry·설치 계획·충돌 판정 코드는 구현했으며 운영 DB DDL과 데이터 이전은 I-09 승인 전까지 실행하지 않는다.
