OJ Platform 재정비 기준 · D-005

사용자 흐름·코드 구조 재정비

이 문서는 사용자 작업이 끝까지 완료되는 흐름을 기준으로 컨트롤러, 장기 작업, 복구, 상태와 문구를 재정비하기 위한 실행안이다. 기능 추가보다 실패 후 복구, 진행 상태, 이해 가능한 용어와 변경 영향 축소를 우선한다.

조사일: 2026-07-19 기준: D-004 저장소 재정비 설계 확정 · 전환 대기 상태 문서 인코딩: UTF-8 상태: 재정비 설계 확정 · 구현 대기
8핵심 사용자 작업
28컨트롤러 파일
131,000줄 초과 컨트롤러
2,698직접 화면 출력 구문
4현재 자동 검사 파일
핵심 결론: 주요 기능의 시작 화면과 처리 코드는 대부분 존재하지만, 오래 걸리는 작업의 진행·재시도·취소와 실제 사용자 흐름 자동 검증이 부족하다. 화면 출력, 요청 해석과 업무 처리가 대형 컨트롤러에 함께 있어 작은 UI 변경도 기능 전체를 건드리기 쉽다.

재정비 기준이 되는 핵심 사용자 작업 8개

현재 코드 경로는 확인했지만 WordPress·Judge 통합 환경의 완료 검증은 별도다.

통합 검증 필요
  1. 방문자·기존 사용자

    가입과 로그인

    첫 접근 → 로그인 화면 → 로그인 또는 가입·동의·법정대리인 확인 → 자동 승인 또는 수동 승인 대기 → WordPress 인증·필요한 기존 계정 전환 → 메인 홈

    현재 위험
    기존 Judge 사용자를 확인 없이 자동 가져오는 코드가 남아 있다.

  2. 학습자

    문제 풀이와 제출

    문제 탐색 → 문제 상세 → 제출 방식 선택 → 코드 또는 Blockly 제출 → 채점 상태 확인 → 결과·AI 피드백 확인

    현재 상태
    권한은 WordPress ID를 사용하지만 제출 소유자와 풀이 상태는 OJ 로그인 ID를 사용하므로 아직 단일화되지 않았다.

  3. 학습자·참가자

    수업·그룹·대회 참여

    목록 탐색 → 상세 확인 → 가입·참가 → 문제 풀이 → 제출 현황·진행률·순위 확인

    현재 위험
    세 기능이 사용자 ID와 제출 조회를 서로 다른 방식으로 조합한다.

  4. 강사·그룹 관리자

    학습 공간 운영

    수업·그룹 생성 → 문제·구성원 연결 → 승인·권한 위임 → 진행률·제출 보고서 확인 → 보관

    현재 상태
    기능은 갖춰졌지만 화면별 용어와 작업 위치가 많아 반복 운영 부담이 크다.

  5. 문제 관리자

    문제와 메타데이터 관리

    문제 목록 → 등록·수정 → 테스트데이터 → 단건·선택·전체 메타데이터 생성 → 퀴즈·문제집 연결

    현재 위험
    AI 일괄 생성이 한 HTTP 요청에서 순차 실행되어 중단 복구와 진행 확인이 없다.

  6. 제출 관리자

    제출 운영

    제출 필터 → 상세·코드 확인 → 재채점 또는 삭제 → 사건 기록 확인

    현재 위험
    Judge 변경과 플랫폼 사건 기록은 서로 다른 저장소라 하나의 원자 작업이 아니다.

  7. 사용자 관리자

    사용자 일괄 등록·전환

    CSV 입력 → 사전 검증 → 차단 행 수정 → 실행 → 결과 확인 또는 기존 사용자 전환

    현재 위험
    미리보기와 결과가 10분짜리 임시 데이터라 긴 검토나 재접속에 약하다.

  8. 시스템 관리자

    설정·점검·이전

    기능 설정 → DB 연결 점검 → 사전 검사 → 이전 실행 → 결과·정리 보고서 확인

    현재 위험
    설정과 기술 운영 절차는 분리 중이지만 공통 작업 상태와 복구 계약이 없다.

사용자 체계 재정비: Judge 계정 전환

자동 가져오기를 금지하고 사용자가 직접 확인한 한 번의 전환 절차로 제한한다.

D5-R05 확정
확정 원칙: 로그인 중 기존 계정 후보를 발견해도 데이터를 변경하지 않는다. 사용자 본인 검증, 충돌 검사와 옮길 정보 확인을 모두 통과한 뒤 명시적인 전환 요청에서만 실행한다.
완료 상태 분리: “전환 기능 구현 완료”는 동의·검증·중단·재개 흐름이 준비된 상태이고, “전체 데이터 전환 완료”는 미전환 사용자 처리 정책과 기존 참조 제거까지 승인된 상태다. 전자를 통과하면 다음 재정비 단계로 이동할 수 있지만 후자는 D-006의 최종 정리 관문에서 닫는다.
확인 정보 저장 금지: 사용자 확인을 기다리는 동안 Judge ID·로그인 아이디·비밀번호·비밀번호 해시는 서버 transient, Jobs 또는 별도 매핑에 저장하지 않는다. 확인 화면은 만료 시각·nonce·표시 정보 해시와 무작위 jti만 담은 서명 토큰을 사용하고, 최종 전환 요청에서 로그인 아이디와 기존 비밀번호를 다시 입력받아 Judge 원본을 재조회한다. 최종 요청은 jti 해시·세션 해시·만료 시각만 담은 WordPress option을 고유 이름으로 원자 생성해 토큰을 한 번만 선점한다. 이미 존재하는 option은 재전송·동시 요청으로 보고 거부하며 만료 뒤 정리한다. 이 option에도 Judge 정보는 기록하지 않는다. WordPress 계정을 만든 뒤 재개 작업에는 숫자 wp_users.ID와 단계 상태만 기록한다.
단계검증 내용차단 조건
1 · 후보 확인이메일 자동 연결을 사용하지 않고 입력한 로그인 아이디와 Judge users.user_id가 정확히 같은 한 행만 조회한다.누락, 중복, 비활성 또는 탈퇴 계정
2 · 본인 확인전환 화면에서 기존 Judge 비밀번호를 다시 입력받아 원본 해시와 검증한다.비밀번호 불일치 또는 검증 불가
3 · 충돌 검사WordPress 로그인·이메일 중복, 기존 user_profiles, 다른 WordPress 사용자와의 연결 여부를 확인한다.다른 사용자가 동일 정보를 소유하거나 이미 전환됨
4 · 사용자 확인WordPress 소유 항목인 로그인 아이디·이메일·표시 이름과 OJ 프로필 항목인 소속·생년 정보를 구분해 마스킹해 보여주고 사용자가 전환을 선택한다. 관리용 학생 이름은 신규 계정 생성 시 표시 이름으로 초기화하며 별도 사용자 입력을 받지 않는다.사용자 취소 또는 확인 만료
5 · 실행 직전 확인원본을 다시 읽어 비밀번호, 계정 상태와 후보 정보가 확인 화면 이후 바뀌지 않았는지 검사하고 서명 토큰의 jti를 원자적으로 한 번만 선점한다.원본 변경, nonce 실패, 토큰 만료·재사용 또는 동시 실행
6 · 전환 실행로그인·이메일·비밀번호·표시 이름·별명은 WordPress에, 소속·생년·플랫폼 이용 상태는 user_profiles에 저장하고 이후에는 wp_users.ID만 사용한다. Judge 비밀번호와 별도 Judge ID 연결 정보는 저장하지 않는다.일부 저장 실패 시 새로 만든 대상 데이터를 되돌림
7 · 사후 검증WordPress 로그인, 프로필 1:1 연결, 역할, 제출 이력 접근과 중복 실행 방지를 확인한다.완료 조건 하나라도 불일치하면 전환 실패로 기록
상태데이터 처리일반 기능완료 조건
미전환기존 Judge·플랫폼 기록을 읽기 전용으로 보존하고 자동 계정 생성·삭제를 하지 않는다.승인된 전환 마감일 전에는 WordPress 계정이 없을 때만 동의 전환을 제안하고, 그 밖에는 Migration 전용 감사 보고서에서만 확인한다.사용자가 전환을 완료하거나 승인된 마감일 뒤 지원·복구 경로로 이관할 때까지 유지
전환 중WordPress 계정을 만든 뒤 작업에는 숫자 wp_users.ID와 단계 상태만 저장한다. 이전 조회 값은 같은 계정의 user_login에서 다시 얻는다.모든 참조 전환과 검증이 끝날 때까지 로그인 세션을 만들지 않는다.플랫폼·Judge 참조 건수 일치, 고아 참조 0건, 재실행 가능
개인 전환 완료user_profiles·참여·권한·보고서는 숫자 WordPress ID를 사용하고 Judge 제출 원본은 기존 solution.user_id의 WordPress user_login 문자열을 유지한다.WordPress 인증과 숫자 user_id를 사용하며 JudgeDb 어댑터 경계에서만 user_login으로 변환한다.Judge ID 매핑·비밀번호·별도 로그인 ID 저장 0건, HUSTOJ 스키마 변경 0건
전체 정리 완료전환 대상 사용자 전원 완료 또는 사용자가 승인한 전환 마감일·미전환 원본 보존 정책 적용Judge 대체 인증과 로그인 전환 조회를 닫고 이후 시도는 지원·복구 경로로 안내대체 인증 종료 자동 검사, D-008 관찰·Judge 호환·제거 승인 관문 통과
대체 절차: 기존 비밀번호를 확인할 수 없으면 자동 연결하지 않는다. 검증된 이메일 인증 또는 관리자의 별도 본인 확인 절차를 사용하며, 비밀번호 원문과 Judge 비밀번호 해시는 어느 단계에서도 대상 저장소에 복사하지 않는다.

학습 참여 구조 재정비: 수업·그룹·대회

참여 신청부터 제출, 진행률과 순위까지 같은 사용자를 일관되게 판정하는지 확인했다.

현재 혼합 구조
확정 목표: 수업 등록, 그룹 소속, 대회 참가, 권한과 플랫폼 보고서의 사용자 키는 wp_users.ID 하나로 통일한다. Judge 제출 원본은 HUSTOJ 호환을 위해 solution.user_id에 WordPress user_login을 유지하고, 일반 참여 코드는 숫자 ID만 사용한 뒤 JudgeDb 어댑터 경계에서만 일괄 변환한다.
위험현재 동작사용자에게 나타나는 문제확정 해결 방향
1 · 참여 기준 불일치그룹 참여와 권한은 wp_user_id로 찾지만 그룹 보고서는 저장된 oj_user_id로 제출을 찾는다. 수업 등록과 대회 참가는 oj_user_id를 기준으로 찾는다.같은 계정이 한 화면에서는 참여자로 보이고 다른 화면에서는 미참여자로 판정될 수 있다.모든 참여 조회와 권한 판정을 정수 WordPress ID로 변경한다.
2 · 연결값 노후화와 소유권 이동기존 그룹 참여 행을 갱신할 때 oj_user_id는 수정하지 않는다. 반대로 수업·대회는 같은 OJ ID 행을 찾으면 연결된 WordPress ID를 새 값으로 바꿀 수 있다.그룹 보고서가 예전 계정 제출을 보여주거나 수업·대회 참여와 IP 제한이 다른 WordPress 계정으로 넘어갈 수 있다.OJ 연결값 갱신을 없애고 참여 행의 유일한 사용자 키를 WordPress ID로 고정한다.
3 · 중복과 고아 참여 행group_memberships, class_enrollments, contest_participants에는 대상과 사용자를 묶는 복합 고유키가 없고 참조 무결성도 DB가 보장하지 않는다.동시 참여 요청이나 일부 삭제 후 중복·고아 행이 남아 참여자 수가 부풀고 최신 행에 따라 상태가 달라질 수 있다.각 테이블에 대상 ID와 WordPress 사용자 ID 복합 고유키를 두고 이전 전에 중복·고아 데이터를 차단한다.
4 · 참여 판정과 제출 저장 분리참여 정보는 플랫폼 DB에서 확인하고 제출은 Judge DB에 별도로 저장한다. 두 저장소를 하나의 트랜잭션으로 묶지 못한다.참여 취소, 수업 종료 또는 대회 상태 변경과 제출이 겹치면 판정과 실제 저장 결과가 잠시 어긋날 수 있다.제출 직전 상태를 재검증하고 중복 실행 방지 키, 사후 검증과 실패 보상 기록을 적용한다.
5 · 그룹 기능 OFF의 부분 차단공개·비공개 수업과 대회는 그룹 없이 동작한다. 다만 그룹 제한 수업·대회는 그룹 서비스가 없으면 새 사용자의 접근과 참여가 차단되고 기존 등록자·참가자는 일부 접근을 유지할 수 있다.그룹 기능을 끈 뒤 특정 수업·대회가 새 사용자에게 사라지지만 기존 참여자는 계속 보이는 불일치가 생긴다.기능을 끄기 전에 그룹 제한 항목을 찾아 공개 또는 비공개로 변경하게 한다. 확정 기본값은 비공개이며 기존 직접 등록자·참가자는 유지하고 자동 공개는 하지 않는다.
6 · 제출·진행률·순위 누락그룹 보고서와 대회 순위는 solution.user_id 문자열을 사용하고, 수업 진행률도 같은 제출 값을 기준으로 묶는다.플랫폼의 숫자 사용자 ID를 Judge 문자열 열에 직접 적용하면 제출이 누락되거나 judge_client 호환이 깨질 수 있다.HUSTOJ 테이블에는 열을 추가·교체하지 않는다. Controller·Service는 숫자 WordPress ID를 사용하고 JudgeDb 어댑터가 현재 WP_User 또는 일괄 사용자 조회에서 얻은 변경 불가 user_login으로 solution.user_id를 저장·필터한다. 보고서 결과는 요청 단위 일괄 사전으로 숫자 ID에 연결하며 영구 Judge ID 매핑을 만들지 않는다.
확정 운영 정책: 그룹 기능을 꺼도 공개·비공개 수업과 대회의 조회, 직접 참여, 제출과 보고서는 정상 동작해야 한다. 그룹 제한 항목이 남아 있으면 기능 끄기를 중단한다. 관리자가 공개 또는 비공개로 변경한 뒤 다시 실행하며 기본값은 비공개로 한다. 기존 직접 등록자·참가자는 유지하고 자동 공개 전환은 하지 않는다.

학습 공간 운영 재정비

강사가 수업을 준비하고 학습자를 운영하며 결과를 확인한 뒤 보관하는 전 과정을 기준으로 조사했다.

운영 계약 확정
확정 개념 구분: 그룹은 여러 수업에서 재사용할 수 있는 구성원·관리자 묶음이고, 수업은 일정, 접근 방식, 문제, 직접 참가자와 학습 결과를 소유하는 실제 학습 공간이다. 수업은 그룹 없이 완전하게 운영할 수 있어야 하며 그룹은 접근 대상을 빠르게 연결하는 선택 기능으로만 사용한다.
1 · 수업 개설

기본 정보와 담당자

이름, 설명, 운영 기간, 공개 상태를 정하고 개설자를 수업 소유자로 기록한다.

2 · 접근 설정

공개·비공개·그룹

공개 참여, 비밀번호 참여 또는 선택한 그룹 구성원만 참여하는 방식을 정한다.

3 · 운영자 구성

소유자와 공동 강사

소유자는 수업 전체를 책임지고 공동 강사는 구성원, 문제와 보고서를 운영한다.

4 · 학습자 등록

직접 등록과 참여 신청

사용자 검색, 초대, 직접 등록 또는 참여 신청으로 학습자를 추가하고 상태 이력을 남긴다.

5 · 문제 구성

검색·선택·순서

문제 제목과 주제로 검색해 추가하고 풀이 순서와 공개 여부를 화면에서 조정한다.

6 · 학습 진행

풀이와 제출 연결

학습자는 수업 안에서 문제를 풀고 제출에는 수업 ID와 WordPress 사용자 ID가 함께 기록된다.

7 · 현황 확인

개인 진도와 전체 보고서

학습자는 자신의 결과를 보고 강사는 미시도자를 포함한 전체 진도와 제출을 확인한다.

8 · 종료와 보관

기록 유지와 복원

수업을 보관해 신규 참여와 제출을 닫되 구성원, 문제, 제출과 보고서는 유지하고 필요하면 복원한다.

운영 영역현재 코드운영 문제정리 목표
1 · 소유권그룹은 소유자와 위임 관리자를 구분하지만 수업은 생성자를 저장하고도 수정·구성원·보고서 권한을 전역 권한으로만 판정한다.강사에게 자기 수업만 맡기기 어렵고 전역 권한을 주면 다른 강사의 수업까지 관리할 수 있다.수업 소유자와 공동 강사를 두고 수업별 권한 범위를 적용한다.
2 · 구성원그룹은 신청, 승인, 거절, 직접·일괄 추가, 탈퇴와 삭제가 있지만 수업 참가자 화면은 조회 전용이다.잘못 등록된 학습자 처리, 강사의 직접 등록, 학습자의 수업 나가기와 재등록 절차가 없다.직접 등록, 초대, 제외, 본인 나가기와 재등록을 제공하고 참가 상태 이력을 유지한다.
3 · 대상 선택수업에 그룹과 문제를 연결할 때 숫자 ID를 여러 줄 텍스트로 입력한다.강사가 ID를 미리 알아야 하고 잘못된 대상이나 문제 순서를 눈으로 검증하기 어렵다.이름·제목 검색, 선택 목록, 순서 이동과 삭제가 가능한 선택 UI로 바꾼다.
4 · 저장 일관성수업 본체, 그룹 연결과 문제 연결을 각각 저장하며 연결 저장의 실패 결과를 확인하지 않고 성공으로 반환한다.저장 완료 문구가 보여도 그룹이나 문제가 일부 빠진 수업이 만들어질 수 있다.한 작업 서비스가 전체를 검증하고 같은 플랫폼 DB 트랜잭션에서 모두 성공하거나 모두 되돌린다.
5 · 보고서 범위등록 학습자는 수업 전체 제출·진행률 화면에 접근할 수 있고 내보내기 버튼 판정과 실제 처리 권한도 서로 다르다.다른 학습자의 제출 이력이 과도하게 노출되고 보이는 버튼이 실행 단계에서 거절될 수 있다.학습자는 자신의 진도만, 수업 운영자는 전체 현황과 내보내기를 사용하도록 분리한다.
6 · 미시도자수업 진행률은 제출 기록에서 사용자 행을 만들기 때문에 한 번도 제출하지 않은 등록자는 빠진다.강사가 도움이 필요한 미시도자를 전체 진도에서 확인할 수 없다.활성 참가자 명단을 기준으로 행을 만들고 제출이 없으면 0%로 표시한다.
7 · 계정 보안그룹 소유자와 위임 관리자가 승인 구성원의 플랫폼 비밀번호와 WordPress 비밀번호를 직접 지정할 수 있다.대상 계정의 역할과 그룹 관계를 충분히 제한하지 않으면 학습 공간 운영 권한이 사이트 계정 통제로 확대된다.소유자와 위임 운영자는 같은 그룹의 승인된 일반 구성원에게만 구성원 목록에서 단건·선택 일괄 초기화를 요청한다. 기존 비밀번호 열람·영구 비밀번호 직접 지정은 금지하고 이메일 비의존 임시 비밀번호를 한 번 제공한 뒤 본인이 새 비밀번호를 정하게 한다.
8 · 보관·복원그룹은 보관과 전역 관리자 복원을 지원하지만 수업은 보관 후 보고서 조회만 가능하고 복원 동작이 없다.실수로 보관한 수업을 정상 운영 상태로 되돌릴 수 없고 기능 간 규칙이 다르다.수업과 그룹에 동일한 보관·복원 원칙과 감사 기록을 적용한다.
9 · 그룹 수행 모드evaluation_mode의 default·exam 값을 저장·표시하지만 제출 상세·코드 권한에는 적용하지 않는다. 본인 제출은 항상 상세와 코드를 열 수 있다.그룹 화면에서 상세 링크를 숨겨도 직접 URL이나 다른 제출 목록으로 우회할 수 있다.소유자·위임 운영자가 일반·수행 모드를 전환한다. 활성 수행 모드 그룹의 일반 구성원은 그룹 안팎에서 생성한 본인의 모든 제출에서 풀이·제출·채점·결과 목록은 정상 사용하고, 결과 상세 페이지와 코드·오류·테스트·성능 상세·AI 피드백 조회만 모든 진입점에서 제한한다.
10 · 사용자 식별구성원은 WordPress ID와 OJ ID를 함께 저장하고 보고서는 Judge 제출의 문자열 사용자 ID를 다시 조합한다.등록, 제출과 보고서가 서로 다른 사용자를 가리키거나 결과가 누락될 수 있다.참가, 제출과 보고서 모두 wp_users.ID만 사용한다.

점수표시판정 기준
1매우 쉬움기본 입출력이나 한 가지 기초 연산으로 풀 수 있고 풀이가 바로 드러나며 예외 처리가 적다.
2쉬움한 가지 기초 알고리즘·자료구조 또는 짧은 변환이 필요하고 일부 경계 조건을 다룬다.
3보통표준 알고리즘을 응용하거나 두 가지 기초 개념을 결합하며 구현량과 경계 조건이 중간 수준이다.
4어려움고급 알고리즘·자료구조 또는 쉽게 드러나지 않는 관찰이 필요하고 증명·최적화·복잡한 예외 중 하나 이상이 중요하다.
5매우 어려움여러 고급 개념, 새로운 관찰 또는 엄밀한 증명이 필요하고 최적화와 구현 복잡도가 모두 높다.
공통 판정 규칙: 정답률은 보조 근거일 뿐 단독 기준으로 사용하지 않는다. 필요한 개념, 추론 깊이, 구현량, 시간·공간 최적화와 경계 조건을 함께 평가하며 AI 생성·관리자 수정·통계 보정은 같은 루브릭 버전을 사용한다. 버전이 바뀌어도 기존 점수는 자동 재분류하지 않는다.
AI 생성 계약: 프롬프트를 만들 때부터 difficulty-rubric-v1의 다섯 단계 설명과 작업 시작 시점의 활성 주제 사전 스냅샷을 전달한다. 최초 사전은 D-008 topic-dictionary-v1의 32개 seed이며 이후 최고 관리자가 추가한 활성 주제를 함께 포함한다. 응답 스키마는 difficulty_score를 정수 열거형 1·2·3·4·5로, topic_keys를 0~3개의 허용된 표준 키 배열로 제한하며 값이 있으면 첫 키를 대표 주제로 사용한다. AI는 주제를 만들 수 없고 사전에 없는 값을 제안해도 자동 등록하지 않는다. 작업 배정 revision, 선택된 연결 프로필 키·fingerprint, 모델, 프롬프트·루브릭·정렬된 사전 내용의 결정적 해시를 결과와 작업 계약에 기록한다. 소수·범위 밖 점수나 미등록·중복·4개 이상 주제는 보정하지 않고 실패 또는 확인 필요로 처리하며, 정확히 맞는 세부 주제가 없을 때의 빈 배열은 정상값으로 허용한다.

D5-F03 · 장기 작업의 동기 실행 해결안

화면 요청이 끝날 때까지 모든 항목을 처리하지 않고, 영구 작업을 등록한 뒤 독립 작업자가 항목별로 실행하게 한다.

해결안 확정
코드에서 확인한 원인: 문제 메타데이터 선택·필터 전체 생성은 generate_many()가 문제마다 최대 180초인 AI 요청을 순차 호출하며 컨트롤러는 실행 시간 제한을 해제한다. 제출 AI 피드백도 현재 컨트롤러 요청 안에서 AI 호출과 저장을 실행한다. 통합 전 플러그인의 문제 작성 AI는 동기 요청 또는 30분 transient를 사용하고 테스트케이스 AI에는 생성기 파일 직접 쓰기 경로가 있으나, 현재 통합 Problems 모듈에는 두 기능이 빠져 있다. CSV 사용자 등록과 기존 Judge 사용자 검사는 모든 행을 한 화면 요청에서 반복한다. 현재 재채점은 단건이므로 장기 작업 대상이 아니며, 향후 대량 재채점만 공통 실행기를 사용한다.

실행 안전 계약

기준적용 규칙
작업 실행웹 요청은 작업만 등록한다. WordPress 예약 실행을 기본 연결로 제공하고 운영 환경에서는 서버 cron이 wp-cron.php를 정기 호출하도록 상태 검사를 제공한다.
대상 고정등록 확인 시 서버가 필터와 권한을 다시 검증하고 정확한 대상 키를 background_job_items에 저장한다. Worker는 존재와 권한만 재검증하며 새로 조건에 맞은 대상을 추가하지 않는다.
중복 방지작업 종류, Handler 정의 버전, 실행 모드, 정렬한 대상 키, 대상 입력 버전·해시를 중복 방지 키에 포함한다. AI 작업은 배정 revision, 주·대체 프로필 키와 등록 당시 fingerprint, 모델, 프롬프트·난이도 루브릭·주제 사전 버전도 포함한다. 같은 계약 버전과 입력은 완료 항목을 다시 저장하지 않고, 버전이나 실행 모드가 다르면 새 작업으로 등록한다.
변경 충돌등록 때 기록한 대상 버전·수정 시각·입력 해시를 실행 직전과 외부 호출 뒤 업무 저장 직전에 다시 비교한다. 달라지면 메타데이터·제출 피드백은 저장하지 않고, 문제·테스트케이스 결과는 오래된 입력 초안으로만 비교한다. 관리자 작성값과 원본 파일은 명시적 적용 없이 변경하지 않는다.
재시도네트워크 시간 초과, AI 제공자 일시 오류와 잠금 충돌만 제한 횟수로 지연 재시도한다. 자동·수동 재시도는 등록 때 고정한 배정 revision과 프로필 fingerprint를 그대로 사용하고 같은 작업과 항목 행의 상태·실행 가능 시각·임대만 원자적으로 갱신한다. 프로필 fingerprint가 달라졌다면 다른 모델로 조용히 전환하지 않고 확인 필요로 마감한다. 입력·Handler·배정·모델·사전 버전이 바뀐 실행은 새 멱등키의 새 작업으로 등록한다. 잘못된 입력, 권한 거부와 존재하지 않는 대상은 즉시 최종 실패로 기록한다.
취소background_jobs.cancel_requested_at과 cancel_requested_by_user_id를 조건부 갱신해 한 번만 요청한다. 항목 점유 트랜잭션은 취소 요청이 있는 작업을 제외한다. 이미 임대한 모든 항목이 결과를 확정할 때까지 기다리고 미점유 항목을 취소로 마감한 뒤 부모 작업을 cancelled로 확정한다. 그 전까지 사용자 상태는 진행 중을 유지하고 “취소 요청됨”을 부가 표시한다.
권한등록·조회·취소·재시도와 실행 직전에 현재 Handler 권한, 사용자 존재와 기능 상태를 다시 확인한다. 생성자 일치는 자기 작업 범위를 제한할 뿐 권한을 대신하지 않는다. 권한이 회수되면 새 점유를 막고 이미 임대한 항목이 정리된 뒤 확인 필요로 마감한다.
민감 정보AI 키는 작업 데이터에 저장하지 않고 실행 시 비밀 저장소에서 읽는다. CSV 비밀번호와 문제·테스트케이스 AI 입력·초안은 WordPress DB 밖의 비밀값에서 파생한 키로 인증 암호화한 Form_Draft_Store 값에 보관하고, 작업 항목에는 고유한 무작위 payload_ref만 둔다. 소유 작업·항목을 확인한 Worker와 적용 Controller만 읽으며 목적에 따라 실행 또는 적용·폐기·취소·24시간 만료 때 암호문과 참조를 제거한다. 제출 소스·원본 프롬프트·테스트케이스 내용은 Jobs 표·사건·내보내기에 저장하지 않는다. 참조가 없거나 만료됐거나 암호화 키 변경으로 읽을 수 없으면 자동 재생성·재시도하지 않고 비밀값을 포함하지 않은 사유 코드와 함께 확인 필요로 마감한다.
상태 문구대기, 진행 중, 확인 필요, 일부 완료, 완료, 실패, 취소를 공통 사용자 상태로 사용한다. 재시도 대기는 “대기”, 충돌·보상 실패·중단된 작업은 “확인 필요”로 표시하고 내부 예외명은 관리자 기술 상세에서만 제공한다.
부모 상태 집계: 시작 전은 queued, 실행 가능한 항목이나 임대가 있으면 running이다. 자동 실행이 남지 않았고 미해결 항목·단계가 하나라도 있으면 needs_attention이다. 취소 요청 뒤에는 신규 점유를 막고 모든 기존 임대를 정리한 다음 미점유 항목을 취소해 cancelled로 마감한다. 그 밖의 종료 작업은 전부 성공이면 completed, 전부 실패면 failed, 성공과 실패가 섞이면 partial이다. “재개 가능”, “복구 중”, “기록 동기화 필요”는 상태가 아니라 상세 문구로만 표시한다.
확정 계약: AI 메타데이터·문제 작성 초안·테스트케이스 초안·제출 피드백은 단건부터 모두 작업으로 등록한다. 문제·테스트케이스 초안은 자동 반영하지 않고 편집자의 비교·검증·적용을 거친다. 신규 사용자 CSV 실행과 플랫폼 데이터 이전도 공통 실행기를 사용한다. 현재 단건 재채점과 집합 쿼리 한 번으로 끝나는 공개 상태 변경은 즉시 처리하며, 제거된 기존 Judge 사용자 일괄 가져오기는 재도입하지 않는다.

D5-F05 · 다중 저장소 부분 완료 해결안

같은 저장소의 변경은 로컬 트랜잭션으로 묶고, 서로 다른 DB와 파일의 변경은 재실행 가능한 단계와 보상 작업으로 조정한다.

해결안 확정
핵심 판정: 서로 다른 두 DB 연결에 각각 START TRANSACTION을 실행해도 하나의 원자적 트랜잭션이 되지 않는다. 한 연결의 COMMIT 후 다른 연결이 실패하면 앞선 완료를 ROLLBACK할 수 없으므로 저장소별 완료 지점, 사후 검증과 보상 절차가 필요하다.

    AI 메타데이터, 사용자 일괄 등록, 데이터 이전과 대량 재채점을 공통 작업 실행기로 처리한다. 대상 항목별 상태, 진행률, 재시도, 취소와 결과 내려받기를 제공한다.

  3. D5-R03 · 영구 작업 내역

    확정

    장기 작업의 실행자, 기능, 대상 조건, 진행 수, 실패 사유와 시간을 영구 저장한다. transient는 일회성 화면 알림에만 사용한다.

  4. D5-R04 · 재실행 가능한 단계 계약

    확정

    여러 DB와 파일을 다루는 작업은 작은 단계, 완료 지점, 중복 실행 방지 키와 보상 작업을 기록한다. 중단 후 마지막 미완료 단계부터 다시 실행할 수 있어야 한다.

  5. D5-R05 · 로그인 전환 확인과 검증

    확정

    Judge 계정 후보 발견만으로 자동 전환하지 않는다. 정확한 로그인 ID 후보, 기존 비밀번호, 대상 충돌, 원본 변경과 사후 상태를 검증하고 사용자가 전환을 명시적으로 선택한 경우에만 한 번 실행한다.

  6. D5-R06 · 문제 관리자 화면부터 컨트롤러 분리

    확정

    문제 목록, 편집, 메타데이터, 퀴즈, 문제집, XML과 테스트데이터를 각각 화면 컨트롤러와 작업 서비스로 분리한다. 공통 문제 Repository는 유지한다.

  7. D5-R07 · 명시적 생성자 의존

    확정

    Container는 Core 부팅과 모듈 생명주기 조립에서만 사용한다. 실행 클래스는 필요한 타입을 생성자로 받고 선택 기능은 기능별 확장 레지스트리와 좁은 Provider 인터페이스로 연결한다.

  8. D5-R08 · 공통 상태·문구 체계

    확정

    대기, 진행 중, 확인 필요, 일부 완료, 완료, 실패, 취소 상태와 사용자 행동 문구를 공통으로 정의한다. 내부 클래스명, DB명, 마이그레이션 코드 같은 개발 용어는 상세 기술 정보에서만 보여준다.

  9. D5-R09 · 핵심 흐름 통합 테스트

    확정

    가입·전환, 문제 제출, 메타데이터 일괄 작업, 수업·그룹·대회 참여, 관리자 파괴 작업과 DB 이전을 권한별·실패별로 자동 검증한다.
