전체 설계·개발 순서

먼저 사용자·관리자 경험과 모든 모듈의 상세 설계를 완성하고 사용자 승인을 받아 기준을 고정한다. 그 뒤에는 메뉴별로 UI·기능·권한·DB·테스트를 한 묶음으로 구현한다. 내부 클래스만 먼저 끝내거나 화면을 마지막에 몰아서 만드는 방식은 사용하지 않는다.

완전 재구축 원칙

현재 코드를 고쳐 쓰는 것이 아니라 실행 트리를 비우고 설계 계약에서 다시 만든다.

C-23~C-27 실행안
권장 작업 방식: 현재 main은 I-00 기준점과 복구 원본으로 고정하고, 별도 Git 재구축 브랜치·작업 트리(worktree)에서 작업한다. I-00 산출물을 승인한 뒤 재구축 작업 트리의 oj-platform에서는 docs와 I-00 개발 증거 도구만 보존하고 기존 config·languages·modules·resources·src·templates·tests·플러그인 진입 파일·README를 제거한 다음 새 구조를 생성한다. 운영 WordPress에는 완성 전 재구축 브랜치를 설치하지 않는다.
원칙허용금지검증
기존 코드 취급Git 이력, I-00 manifest, 화면·동작 기준, 복구용 배포본기존 클래스 상속·호출·복사, 기존 Service를 새 Container에 등록새 runtime에서 구 namespace 파일 경로 참조 0개
데이터 이전Migration의 읽기 전용 Legacy Reader와 명시적 적용 Job업무 모듈의 이전 테이블 직접 조회, 자동 가져오기, 이중 쓰기I-09 뒤 Reader·Migration 코드 0개
호환 처리승인된 데이터 변환 보고서와 오류 안내이전 Route·Action·테이블 이름의 런타임 호환 분기호환 Route 0개, 이전 식별자 변환 0개
단계 통합완성된 수직 단위만 단계 브랜치에 병합임시 Controller, 비어 있는 Service, 화면 없는 내부 API를 다음 단계로 넘김UI·권한·데이터·테스트 관문 동시 통과
롤백기준 commit·DB·파일 백업으로 기존 배포본 전체 복원새 코드 안에 옛 코드를 남겨 롤백 수단으로 사용I-09 운영 교체 전 복구 리허설과 소요 시간 기록
빅뱅 운영 교체가 아니다: 새 코드 트리는 처음부터 깨끗하게 만들되 운영 교체는 I-09 검증 뒤 한 번만 수행한다. 개발 중 안정성은 옛 코드를 새 코드에 섞어서 얻지 않고, 고정된 운영 기준점과 분리된 시험 환경으로 확보한다.

목표 코드 구조

의존 방향을 폴더와 자동 검사로 고정해 새 코드가 다시 뒤섞이지 않게 한다.

|-- src/
|   |-- Kernel/                      # 부팅, SetupBootstrap, DAG, Container 조립, Registry 동결

|-- modules/{Module}/

|   |-- Contract/                    # 다른 모듈에 공개하는 Interface·DTO
|   |-- Domain/                      # 해당 모듈의 규칙·값 객체
|   |-- Application/                 # Command·Query·Policy·Use Case
