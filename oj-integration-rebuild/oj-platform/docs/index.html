OJ Platform 재정비

OJ Platform 재정비 기준 문서

이 문서 묶음은 기존 OJ Platform의 디자인, 코드, 데이터베이스와 기능 경계를 일관된 사용자 서비스 구조로 재정비하기 위한 단일 기준입니다. 조사 결과와 현재 구현은 재정비 결정을 뒷받침하는 근거로만 사용합니다.

재정비 범위

목표: 디자인 통일, 코드 책임 정리, 데이터베이스 소유권 정리, 기능 분리 명확화와 사용자 중심 용어·화면을 하나의 순서로 구현합니다.

범위 밖: 재정비와 관계없는 신규 기능 확장, 임시 운영 안내, 개발자용 홍보 문구는 이 문서에 추가하지 않습니다.

정식 버전 승인 · 2026-09-11: 검토·보완된 재구축 플랫폼을 2.0.0 정식 버전으로 승인했습니다. 승인 근거와 배포 조건은 C-29 정식 버전 승인 기록에서 확인합니다. 공개 Addon API 1.1.0은 유지하며, 특정 서버의 설치·업데이트 완료와 정식판 승인은 구분합니다.

2026-08-10 검증 이력: D-001~D-009와 DS-00~DS-16의 재정비 설계, I-00·R-01~R-11 구현과 단계 커밋을 유지합니다. 당시 정상 운영 계약은 GET 152개, 고유 액션 128개, 관리자 메뉴 58개, 권한 61개, 역할 16개, 기능 30개, 무접두어 플랫폼 테이블 42개였습니다. PHP 파일 1,096개와 구조·계약·단위·통합·E2E 자동 검사 39개에서 실패 0건을 확인했습니다. 당시 실제 서버 인수는 신규 설치 조건부 통과, 정식 경로·UI·Judge 쓰기·SPJ·제출·학습 공간은 수정본 재검증, AI·메일·복구는 미실시로 기록했습니다. 상세 판정은 DS-16 실환경 인수 현황을 단일 원본으로 사용합니다.

사후 변경 C-28: OJ Console·PublicUI 등록, capability 선언·역할 배정, 플랫폼 학습 Context authorization, 기존 AI 작업 배정과 공개 실행 gateway, 문서 동시 갱신 규칙을 C28-R01~R06·D01~D11에 반영했다. C28-API-V1-LOCK-01의 Addon API 1.1.0과 C28-I01~I06 Runtime 구현은 dev.33에서 코드·검증 ZIP 관문을 통과했다. 기존 DS-16과 core 수량은 유지하며 릴리스 증거의 clean production package와 애드온 G1 인수가 남아 있다.

변경 금지 기준: WordPress와 동일하게 숫자 내부 키와 문자열 로그인 아이디를 구분합니다. 플랫폼의 user_id는 wp_users.ID이며 로그인 아이디는 wp_users.user_login입니다. 무접두어 테이블, 제출 용어, 선택 모듈 독립성, AI 분리, 난이도 1~5와 안전한 이전을 포함한 전체 고정 결정은 D-006의 “변경 금지 기준”을 단일 원본으로 사용합니다.

개발 설계

전체 설계·개발 순서

전체 상세 설계는 완료했습니다. 기존 runtime을 새 코드에 남기지 않는 C-23, 신규 설치와 기존 데이터 이전을 분리하는 C-24, 플러그인 개발과 운영 배포 실행을 나누는 C-25, 테스트 환경 설정 누락을 보강한 C-26, 실행 필수 스키마를 정합화한 C-27과 R-00~R-11 완전 재구축 계획, 각 단계의 생성·검사·제거 관문을 이 문서에서 관리합니다. SEQ-Q04까지 사용자 확정했으며 I-00과 R-01~R-11 구현·자동 검사를 완료했습니다. 실제 WordPress·Judge DB 통합과 사용자 시각 확인은 최종 인수·배포 전 누적 관문으로 유지합니다.

C-28 범용 애드온 확장 API 변경 설계

DS-16 동결 이후 외부 애드온의 관리자 기능은 OJ Console에, 로그인 사용자 기능은 PublicUI에 연결하고 선언 capability·학습 Context·AI task를 플랫폼 운영 체계에 합성하기 위한 사후 변경 통제다. C28-D01~D11과 Addon API v1 정확한 계약 및 구현 이관서를 정본으로 삼아 C28-I01~I06을 dev.33·Addon API 1.1로 구현했다. AM-01은 옛 oj_platform_loaded/AddonRuntimeGatewayV1을 애드온별 onReady() 직접 dispatch로 교체했고, AM-02는 학생 learning Context·exact roster·task instruction을 additive로 추가했다. 공개 symbol 37개와 47개 회귀 script, 검증 ZIP은 통과했으며 릴리스 증거서에 upgrade·rollback·fingerprint를 기록했다. 남은 작업은 clean production package와 AI 평가 애드온 G1 인수다.

I-00 보호 기준선 실행 보고서

재구축 전 Git 기준점, 별도 worktree, 현재 코드·Route·Action·권한·메뉴·옵션·테이블 manifest와 복구 도구를 기록합니다. 개발 보호 기준선 통과로 별도 worktree의 R-01 코드 재구축을 허용하며, 실제 WordPress·Judge DB 백업과 격리 복원은 I-09 운영 교체 전 배포 승인 절차로 분리합니다.

DS-00 목적·범위·기준선

학습용 프로그래밍 채점 서비스의 목적, 사용자, 포함·제외 기능, 현재 코드 수치, 목표 수치와 변경 금지 계약을 짧게 묶은 상세 설계 진입 기준입니다.

DS-01 공통 사용자·관리자 UI 시스템

로그인·사용자 홈·관리자 대시보드·역할 관리에서 시작해 모든 기능 화면이 공유할 셸, 시각 토큰, 컴포넌트, 상태·문구, 반응형·접근성 기준과 단계별 전환 방법을 정의합니다.

공통 기반 모듈 개발 설계

최종 목표는 사용자 UI와 관리자 UI를 포함한 플랫폼 전체 재설계입니다. 첫 단계로 Permission, Settings, PlatformDb, JudgeDb, Jobs Core, AccessRouter와 공통 UI 시스템의 순서·소유권·계약·구현 관문을 정리합니다. 이후 각 메뉴를 화면·기능·DB·권한·테스트가 결합된 수직 단위로 완성하며 새로운 D 번호를 추가하지 않습니다.

DS-02 CF-1 Permission 상세 설계

사용자 확정 뒤 가입 승인 권한 분리를 보강한 설계입니다. 기존 60개 capability·15개 역할을 보존하고 승인 전용 capability·역할·preset을 하나씩 추가해 목표 61개·16개·10개로 구성합니다. 학습 운영 담당 범위, 수행 모드, Registry와 역할 관리 화면·테스트 관문을 구체화합니다.

DS-03 CF-2 Settings 상세 설계

사용자 확정으로 동결된 설계입니다. 공통 설정 기반, 기능별 설정 소유권, 기존 WordPress 옵션의 호환 저장, 비밀값 보호, 기능 전환 사전 검토와 운영자 설정 화면 계약을 정의합니다.

DS-04 CF-3 PlatformDb 상세 설계

사용자 확정으로 동결된 설계입니다. 무접두어 플랫폼 테이블 42개의 소유권, 실행 가능한 스키마 Registry, 동명 테이블 충돌 차단, 모듈별 활성 스키마 맵과 설치·업그레이드·복구 계약을 정의합니다.

DS-05 CF-4 JudgeDb 상세 설계

사용자 확정으로 동결된 설계입니다. 외부 HUSTOJ 데이터베이스 연결, 지원 테이블 프로필, 문제·제출·대회 Gateway, WordPress 사용자 식별 변환, 부분 실패 복구와 운영 상태 화면을 정의합니다.

DS-06 CF-5 Jobs 상세 설계

사용자 확정·설계 동결 상태입니다. 장기·다중 저장소 작업의 원자 등록, AI 작업, 4개 영구 테이블, Worker 임대, 7개 상태, 재시도·취소·복구와 진행 화면을 정의합니다.

DS-07 CF-6 AccessRouter 상세 설계

사용자 확정된 실행 계약에 DS-10 퀴즈 화면 분리·호환 경로 제거·최고 관리자 주제 관리, DS-14 보호 첨부 파일 응답과 DS-15 AI 작업 배정 화면을 동기화한 상태입니다. 152개 GET 경로의 타입 정의, 중복 검사, URL 생성, 로그인·기능·대상 권한 판정, WordPress rewrite와 기존 페이지 충돌 검사를 정의합니다.

DS-08 계정·사용자 상세 설계

기능 설계와 UI 시안 3종을 사용자 확정으로 동결했습니다. WordPress 사용자 원본, 로그인·가입·기존 Judge 계정 전환, 프로필·설정·약관·법정대리인 동의와 사용자 관리 화면을 정의합니다.

DS-09 홈·대시보드·셸 상세 설계

DS-10 문제 상세 설계

기능 설계와 시각 시안 5종을 사용자 확정으로 동결했습니다. 큰 단일 문서를 페이지·권한·데이터 계약, 문제 콘텐츠, 퀴즈, 관리 도구·구현으로 분리했습니다. 전체 화면 시안 5종에서 사용자 10개와 관리자 13개 화면의 구현 기준을 확인할 수 있습니다.

DS-11 제출 상세 설계

사용자 제출 화면 5개와 관리자 화면 7개, HUSTOJ 원본 보존, 수행모드, 재채점·무효 처리·복원, Blockly 편집기 시안과 입문·표준·확장 도구상자, 8개 블록 범주, Python 생성·저장 규칙을 한 문서에서 정의합니다. 제출 화면 시안과 Blockly 편집기를 같은 설계 원본에서 검토할 수 있습니다.

DS-12 학습 공간 상세 설계

기능 설계와 UI 시안 7종을 사용자 확정으로 동결했습니다. 직접 경로 47개와 학습 공간 플랫폼 테이블 14개를 사용하며 수업 → 대회·평가 → 그룹 순서의 참여·담당자·문제·제출·진도·보고서, 수행 모드와 Groups OFF 독립성을 정의합니다.

DS-16 전체 연결·동결

기존 상세 문서를 반복하지 않고 부팅 순서, 모듈 의존 계약, 페이지·권한·코드·테이블 추적, 주요 업무 흐름과 검증 관문을 하나의 기준으로 연결합니다. DS16-Q01~Q06의 동결을 유지하면서 LIVE-01~LIVE-09를 실제 서버 인수 원장으로 추가했습니다. 신규 설치·정식 경로·공통 UI·Judge 문제·Jobs·SPJ·제출·학습 공간·AI·메일·복구를 같은 판정 규칙으로 관리하며, 수정 반영과 서버 재검증을 구분합니다.

재정비 문서 작성 기준

  • 앞으로 사용자 검토용 정리문서는 독립 HTML 파일로 작성한다.
  • 한글은 UTF-8 원문으로 기록하고 유니코드 이스케이프 표현을 사용하지 않는다.
  • 확인된 사실과 제안·확정·보류 결정을 시각적으로 구분한다.
  • 점검은 D-006의 변경 금지 기준을 우선하며, 다른 결론은 자동 반영하지 않고 불일치로 기록한 뒤 사용자 승인을 받아 변경한다.
  • 플랫폼 코드·config·테스트·공개 계약을 변경할 때 같은 변경 집합에서 관련 HTML 개발 문서, 추적 ID, 계약 수량과 검증 관문을 함께 갱신한다. 문서와 코드가 다르면 완료로 처리하지 않는다.
  • 데스크톱, 모바일과 인쇄 화면에서 같은 내용을 명확하게 읽을 수 있어야 한다.
  • 외부 서비스 없이 파일을 직접 열어도 핵심 내용과 상호작용이 동작해야 한다.
