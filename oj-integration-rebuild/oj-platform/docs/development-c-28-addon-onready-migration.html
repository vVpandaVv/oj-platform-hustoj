C-28 · Addon API v1 · Amendment AM-01

onReady 전환 안내서

이 문서는 Addon API v1을 사용해 이미 개발 중인 외부 애드온이 oj_platform_loaded / AddonRuntimeGatewayV1::forAddon() 기반 코드를 새 AddonManifestBuilderV1::onReady(callable $callback) 기반 코드로 옮기기 위한 실무 절차서다. 배경 설계와 정확한 signature는 각각 C-28 변경 설계와 API v1 계약 이관서의 계약 개정 기록(AM-01)이 정본이며, 이 문서는 두 문서와 다르면 항상 그 두 문서를 따른다.

개정 ID AM-01 개정일 2026-08-11 AM-01 당시 Addon API 1.0.0 현재 Addon API 1.1.0 필수 조치: Runtime 통합 코드 수정
한 줄 요약: Runtime 준비 알림을 받던 add_action('oj_platform_loaded', ...) 블록을 지우고, 그 안의 로직을 register() builder 안에서 $addon->onReady(...)로 옮긴다. Console/Public Route·Menu·Capability·AI Task 선언 코드는 전혀 바꿀 필요가 없다.
현재 적용 상태: AM-01의 전환 방식은 Addon API 1.1.0에서도 그대로다. 2.0.0-dev.33은 callback 결과를 pending|ready|failed|not_required로 별도 진단하며, 이 문서의 1.0.0 표기는 AM-01 발생 당시의 호환 이력이다.

왜 바뀌었는가

기계적인 rename이 아니라 실제 보안 결함을 고친 변경이다 — 이유를 알아야 전환 코드를 제대로 옮길 수 있다.

보안 수정

oj_platform_loaded는 등록된 모든 애드온의 callback에 같은 전역 AddonRuntimeGatewayV1 인스턴스 하나를 방송했다. 이 Gateway의 유일한 메서드는 forAddon(string $addonId)였고, 인자로 어떤 문자열을 넘기든(자기 자신이 아닌 다른 승인된 addon ID를 넘겨도) 그 addon의 AddonRuntimeContextV1을 그대로 돌려줬다.

결과적으로 가능했던 일: 애드온 A가 $gateway->forAddon('addon-b')를 호출하면 addon-b가 등록한 적 없는 접근권한으로 addon-b의 학사 Context 조회·인가(AddonContextGatewayV1)와 AI Task 실행(AddonAiTaskGatewayV1)을 그대로 수행할 수 있었다. 이는 특정 애드온의 코드 품질 문제가 아니라 API 자체의 설계 결함이었다 — 정직하게 작성된 addon-b도 이 결함으로부터 스스로를 지킬 방법이 없었다.

AM-01은 "ID로 조회하면 아무 addon의 context나 나온다"는 구조를 근본적으로 없앴다. 이제 context는 조회되는 것이 아니라, 등록 시점에 그 애드온이 직접 넘긴 callable에 플랫폼이 그 애드온만을 위해 만든 인스턴스를 인자로 넘겨 호출하는 방식으로만 전달된다. 다른 애드온의 callable을 알 방법이 없으므로 impersonation 경로 자체가 사라진다.

reflection 기준으로 정확히 무엇이 없어지고 무엇이 생겼는지.

전환 절차

기존 통합 코드 기준으로 지우고 옮기는 두 단계다.

실무 diff
  1. use CodingPanda\OjPlatform\AddonApi\V1\AddonRuntimeGatewayV1; import를 use CodingPanda\OjPlatform\AddonApi\V1\AddonRuntimeContextV1;로 바꾼다.
  2. add_action('oj_platform_loaded', function (AddonRuntimeGatewayV1 $gateway) { ... }) 블록 전체를 지운다.
  3. 그 안에서 $gateway->forAddon('내-addon-id')로 얻은 $runtime을 사용하던 로직을 그대로 떼어내, register() builder 안 $addon->onReady(function (AddonRuntimeContextV1 $runtime) { ... })의 body로 옮긴다. forAddon() 호출 자체(과거엔 반드시 자기 자신의 ID를 넘겨야 했던 부분)는 그냥 없앤다 — 플랫폼이 이미 이 애드온의 context만 넘겨준다.

이전 (AM-01 이전, 더 이상 동작하지 않음)

use CodingPanda\OjPlatform\AddonApi\V1\AddonManifestBuilderV1;
use CodingPanda\OjPlatform\AddonApi\V1\AddonRegistrationGatewayV1;
use CodingPanda\OjPlatform\AddonApi\V1\AddonRuntimeGatewayV1;

add_action('oj_platform_register_addons', static function (
    AddonRegistrationGatewayV1 $gateway
): void {
    $gateway->register('my-addon', static function (
        AddonManifestBuilderV1 $addon
    ): void {
        $addon->manifest(/* ... */);
        // capability(), consolePage(), publicPage(),
        // consoleMenu(), publicMenu(), assetBundle(), aiTask()
    });
}, 10, 1);

add_action('oj_platform_loaded', static function (
    AddonRuntimeGatewayV1 $gateway
): void {
    $runtime = $gateway->forAddon('my-addon');
    if ($runtime->snapshot()->status() === 'accepted') {
        MyAddonRuntimeBridge::connect($runtime);
    }
}, 10, 1);

이후 (AM-01, 현재 계약)

use CodingPanda\OjPlatform\AddonApi\V1\AddonManifestBuilderV1;
use CodingPanda\OjPlatform\AddonApi\V1\AddonRegistrationGatewayV1;
use CodingPanda\OjPlatform\AddonApi\V1\AddonRuntimeContextV1;

add_action('oj_platform_register_addons', static function (
    AddonRegistrationGatewayV1 $gateway
): void {
    $gateway->register('my-addon', static function (
        AddonManifestBuilderV1 $addon
    ): void {
        $addon->manifest(/* ... */);
        // capability(), consolePage(), publicPage(),
        // consoleMenu(), publicMenu(), assetBundle(), aiTask()
        // — 위 선언 코드는 전혀 바꾸지 않는다.

        $addon->onReady(static function (
            AddonRuntimeContextV1 $runtime
        ): void {
            if ($runtime->snapshot()->status() === 'accepted') {
                MyAddonRuntimeBridge::connect($runtime);
            }
        });
    });
}, 10, 1);
Context·AI Task 사용 코드는 그대로: MyAddonRuntimeBridge::connect($runtime) 내부에서 $runtime->contexts()->listTeachingContexts(...), $runtime->aiTasks()->execute(...) 등을 호출하는 코드는 한 글자도 바꿀 필요가 없다. $runtime의 타입과 제공 메서드가 이전과 동일하기 때문이다.

동작이 실제로 달라지는 부분

이름만 바뀐 게 아니라 관찰 가능한 동작이 달라지는 지점 — 놓치면 조용히 깨진다.

주의
상황이전(AM-01 이전)이후(AM-01)
manifest가 rejected/incompatible/disabled인 경우forAddon()이 여전히 context를 반환하고, snapshot()->status()와 code()로 애드온 스스로 실패 사유를 읽을 수 있었다.onReady callback이 전혀 호출되지 않는다. 애드온 코드 안에서는 자신이 왜 거부됐는지 알 방법이 없다 — 실패 사유는 플랫폼 운영자용 상태 화면에만 나타난다.
다른 애드온의 context 조회forAddon('다른-addon-id')로 가능했다(결함).불가능하다 — 애초에 ID로 조회하는 API가 없다.

onReady()를 아예 호출하지 않으면해당 없음(과거엔 두 번째 action을 구독하지 않으면 그냥 Runtime을 못 받았다).manifest는 정상 승인되고 Route·Menu·Capability·AI Task는 모두 정상 동작하지만, Context/AI Task Runtime 접근만 조용히 없는 상태가 된다 — 오류나 경고는 없다(안전한 기본값).
자기 진단이 필요하다면: "내 manifest가 왜 거부됐는지"를 애드온 코드 스스로 알아야 하는 요구가 있다면, 이는 AM-01 이전에도 다른 애드온을 impersonate할 수 있었던 것과 같은 API 표면(임의 ID로 조회 가능한 Runtime facade)을 다시 여는 방향이므로 현재 계약에는 없다. 필요하다면 플랫폼 운영자 대상 애드온 상태 화면(운영 콘솔)에서 확인하도록 안내하거나, 이 요구를 계약 개정 기록에 새 논의로 등록해 별도 안전한 self-diagnostics 계약을 검토해야 한다.

자주 하는 실수

전환 중 실제로 부딪히기 쉬운 지점.

체크
  • onReady()를 두 번 호출: 같은 register() builder 안에서 onReady()를 두 번 부르면 LogicException이 발생하고 그 애드온의 등록 후보 전체가 거부된다. builder 하나당 정확히 0회 또는 1회만 호출한다.
  • onReady()를 register() 바깥에서 호출: onReady()는 AddonManifestBuilderV1의 메서드이므로 register()의 두 번째 인자로 넘긴 클로저 안, manifest()를 호출하는 것과 같은 위치에서만 호출할 수 있다. 별도 action이나 별도 시점에서 부를 수 있는 메서드가 아니다.
  • callback 안에서 status() 분기를 지우고 무조건 연결: 현재 구현에서는 onReady가 호출되는 시점의 manifest 상태가 항상 accepted이므로 if ($runtime->snapshot()->status() === 'accepted') 검사는 사실상 항상 참이다. 그래도 이 검사를 지우지 말 것을 권한다 — 향후 계약이 바뀌어도(예: 조건부 승인 상태 추가) 방어적으로 동작한다.
  • 옛 import를 지우지 않고 남겨두기: use ...AddonRuntimeGatewayV1;가 남아있으면 그 interface가 삭제됐기 때문에 클래스 로드 시점에 Fatal error: Interface ... not found가 난다. 죽은 add_action('oj_platform_loaded', ...) 블록과 함께 반드시 지운다.
  • Runtime 연결 로직을 manifest() 호출보다 먼저 두기: onReady()는 반드시 같은 builder 안에서 manifest()가 호출된 뒤에 등록해도 상관없지만(둘은 순서 의존이 없다), manifest() 자체를 호출하지 않고 onReady()만 호출하면 그 애드온 후보는 addon_manifest_invalid로 거부된다.

전환 체크리스트

전환이 끝났다고 보기 전에 확인한다.

완료 확인
  • AddonRuntimeGatewayV1을 import하거나 참조하는 코드가 0건이다(grep -r AddonRuntimeGatewayV1로 확인).
  • add_action('oj_platform_loaded', ...) 호출이 0건이다.
  • Runtime 연결 로직이 register() builder 안, $addon->onReady(...) callback 내부로 옮겨져 있다.
  • 이전에 forAddon('내-addon-id')로 넘기던 자기 자신의 addon ID 문자열이 코드에서 사라졌다(더 이상 필요 없음).
  • 플랫폼 활성화 상태에서 실제로 onReady callback이 호출되어 Runtime 연결이 이루어지는지 로그나 상태 화면으로 확인했다(예: 임시 로그 한 줄을 넣어 한 번 부팅해 본다).
  • manifest를 일부러 깨뜨려(예: requiresPlatform을 불가능한 범위로) 등록을 거부시켜 본 뒤, 이 경우 onReady callback이 호출되지 않는다는 것과 Runtime 연결 코드가 예외 없이 조용히 스킵된다는 것을 확인했다.

FAQ

전환 중 자주 나오는 질문.

Addon API 버전이 왜 그대로 1.0.0인가? major bump 아닌가?

공개 interface 삭제·action 삭제는 계약의 SemVer 규칙상 major에 해당한다. 다만 이 변경 시점에 Addon API가 아직 C28-I06 공식 릴리스 전이었고 실제 배포된 소비자가 없었기 때문에, 병행 지원 없이 즉시 교체하는 예외를 사용자 승인으로 적용했다. 자세한 판정은 계약 개정 기록 AM-01을 참고한다. API가 정식 릴리스된 뒤에 이런 변경이 다시 필요하다면 이 예외는 적용되지 않는다.

onReady를 여러 개 등록해서 여러 시점에 콜백을 받을 수 있는가?

아니다. builder당 onReady()는 최대 1회만 등록할 수 있고, 플랫폼도 callback을 최대 한 번만 호출한다. accepted 뒤 Runtime Context 생성과 callback 진입이 정상일 때 한 번 전달되며 실패 뒤 같은 부팅 재시도는 없다. 여러 하위 시스템에 연결해야 한다면 하나의 onReady callback 안에서 원자적으로 연결한다.

onReady callback 안에서 예외가 나면 어떻게 되는가?

C28-I06-LC01: 플랫폼이 이 예외를 잡아 진단 채널로 보고하고 부팅을 계속한다. core 부팅이나 다른 애드온에는 영향이 없지만 이미 합성된 이 애드온 Route·Menu와 accepted catalog 상태도 자동 철회되지 않고 callback을 같은 부팅에서 재시도하지 않는다. 애드온은 catalog accepted와 자체 Bridge ready를 분리하고 모든 handler·REST·Job에서 unavailable 상태를 fail-closed해야 한다. 재호출·상태 공개가 필요하면 별도 플랫폼 승인·SemVer·격리 fixture 뒤 변경한다.

기존 addon-api-profile.html/addon-lifecycle.html 문서도 고쳐야 하는가?

이 문서와 두 C-28 플랫폼 문서는 oj-platform 저장소 소유이며 플랫폼 제공자 쪽 계약을 기록한다. 애드온 저장소(예: oj-ai-dashboard) 쪽의 자체 소비자 문서(a-ds-02-addon-api-profile.html, a-ds-02-addon-lifecycle.html 등)는 그 저장소를 관리하는 쪽에서 이 안내서를 참고해 별도로 갱신해야 한다 — 이 문서가 대신 수정하지 않는다.
