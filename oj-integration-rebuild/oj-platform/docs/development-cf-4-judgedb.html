DS-05 · 공통 기반 CF-4

JudgeDb 상세 설계

외부 HUSTOJ 데이터베이스의 핵심 채점 구조를 유지하고 Problems 확장 열만 설치 경계에서 보강하며, 문제·제출·대회 기능이 승인된 명령만 실행하도록 연결·테이블·사용자 식별·부분 실패·운영 화면을 하나의 계약으로 고정한다.

작성일: 2026-07-23확정일: 2026-07-23전체 설계 확정일: 2026-07-26상태: 사용자 확정 · 설계 동결선행 설계: DS-00~DS-04 확정실행: I-00 뒤 I-01근거: D-004·D-005·D-006·D-008·DS-03·DS-04·DS-16
전체 순서에서의 위치: 이 문서는 전체 설계·개발 순서의 DS-05다. Judge 연결 Profile·TLS 판정·공통 MySQLi Connector와 전환 전용 읽기 Adapter를 재구축 코드에 구현했다. 운영 Judge 연결과 데이터는 변경하지 않았다.

기능별 Judge Gateway

JudgeDb는 연결과 실행 규칙을 제공하고 업무 명령은 소유 모듈이 정의한다.

단일 소유
소유 모듈·Gateway허용 테이블대표 명령소비 경계
Problems · Problem_Judge_Gatewayproblem의 원문·langmask·bann·front·body·rear, 제한된 solution 집계목록·상세·생성·편집·공개 상태·제출 코드 정책·참조 현황Judge 원문과 Problems의 problem_metadata 작성 방식·빈칸 스키마·해시를 조립한 불변 Problem_Submission_Code_Policy를 다른 모듈에 제공
Submissions · Submission_Judge_Gatewaysolution, source_code, source_code_user, compileinfo, runtimeinfo, 통계 열제출 게시·상태·상세·재채점·관리 삭제·오류 정보Problems Provider의 정책은 생성자 의존으로 받고 problem을 직접 조회하지 않는다. 권한이 확인된 제출 읽기 Provider는 AI·학습 현황에 제공
Contests · Contest_Judge_Gatewaycontest, contest_problem, 제한된 problem·solution 조회대회·문제 연결·제출 결과·순위 원본수업·그룹은 Contests Provider를 사용하고 직접 SQL 금지

Problems Jobs · Problem_Maintenance_Gatewaystatus와 승인된 문제 참조 테이블문제 번호 변경 사전 검사·단계별 DML·검증·보상DS-06 Jobs와 유지보수 잠금 안에서만 실행
JudgeDb 내부information_schema, 연결 상태fingerprint·권한·지연·설정 후보 검사업무 자료를 반환하지 않고 안전한 상태 코드만 제공
  1. Classes·Groups·Ranking·Learning Dashboard·AI Feedback은 JudgeDb 객체를 주입받지 않는다. Problems·Submissions·Contests가 공개한 읽기 Provider만 사용한다.
  2. Controller와 Renderer는 Gateway를 직접 호출하지 않고 해당 기능의 Application Service와 권한 정책을 거친다.
  3. 테이블 식별자는 봉인된 Profile Registry에서만 만들고 요청 값으로 테이블·열·정렬 SQL을 조립하지 않는다.
  4. DS-10~DS-12에서 업무 필드를 상세화할 수 있지만 위 테이블 소유와 금지 경계를 넓히려면 DS-05 변경 이력과 사용자 재확인이 필요하다.

일반 코드의 숫자 사용자 키를 유지하면서 HUSTOJ의 문자열 열을 안전하게 사용한다.

제출 게시 순서

순서처리실패 시
1PlatformDb에서 제출 요청 멱등키를 선점하고 사용자·문제·대회 권한을 재검사한다. Problems Provider의 최신 문제 정책으로 전체 코드, 서버 재구성 빈칸 코드 또는 서버 생성 Blockly 원본의 템플릿 해시·금지 문자열·허용 언어·크기를 검사하고 앞·뒤 코드를 LF 경계로 한 번 결합해 최종 크기를 검사중복이면 기존 결과 반환, 권한·템플릿·빈칸·금지 코드·정책 검증 실패면 Judge 쓰기 없음
2solution을 Judge가 가져가지 않는 준비 상태 result=2로 생성생성 실패로 종료
3source_code_user에는 앞·뒤 코드가 없는 전체 코드, 서버 재구성 빈칸 코드 또는 Blockly 복원 묶음을, source_code에는 실제 컴파일할 결합 코드를 같은 solution_id로 기록하고 다시 읽어 검증생성한 행을 보상 삭제, 삭제 실패는 확인 필요로 기록
4solution.result=0을 마지막에 갱신해 채점 대기열에 게시준비 상태로 격리하고 재조정 작업에서 게시 또는 정리
5문제·대회 제출 통계를 갱신하고 PlatformDb 사건에 solution_id 연결제출은 유지하고 파생 통계만 재계산 대상으로 기록
PlatformDb 속성 보강 확정: 1단계의 멱등키를 영구 선점하기 위해 기존 submission_events에 nullable request_key varchar(64)와 고유키를 추가하고 최초 요청 사건에만 사용한다. 테이블 수와 Submissions 소유권은 바꾸지 않으며 D-008 속성 사전과 DS-04 후속 승인 변경에 반영한다.
  1. 재채점: 단일 solution 행을 조건부 갱신하고 이미 대기·채점 중이면 충돌로 반환한다. 쓰기 결과가 불명확하면 같은 명령을 즉시 반복하지 않고 현재 행을 재조회한다.
  2. 대회 문제 교체: 기존 전체 삭제 뒤 재삽입하지 않는다. 검증한 차이를 추가·수정하고 제거 대상을 마지막에 처리하며, 대회 운영 잠금과 원본 스냅샷을 남긴다.
  3. 문제 번호 변경·영구 삭제: 일반 HTTP 요청에서 실행하지 않는다. DS-06 Jobs가 Judge·PlatformDb·파일을 단계별로 잠그고 건수·해시·보상을 기록한다.
  4. DDL: 일반 기능·번호 변경·Migration에서는 0건이다. 검증된 Judge 연결을 적용할 때만 없는 problem 확장 열의 ADD COLUMN을 허용한다.
진실의 기준: 제출 본문은 solution·최종 채점 코드인 source_code·래퍼 없는 전체 코드 또는 서버 재구성 빈칸 코드인 source_code_user 세 행과 최종 대기 상태가 기준이다. 문제별 금지·앞·뒤 코드는 Problems가 소유한 Judge problem, 빈칸 작성 방식·스키마·해시는 problem_metadata가 원본이며 Submissions에 복제하지 않는다. 제출 수·정답 수는 파생 통계이므로 불일치하면 제출을 삭제하지 않고 재계산한다.

사용자 확정 결과

아래 여덟 항목을 2026-07-23 확정하고 DS-05를 동결했다.

8건 확정
  1. DS05-Q01 · 외부 연결 · 확정: 운영 Judge DB는 별도 jol만 허용하고 same DB 모드와 Judge 테이블 접두사 설정을 제거한다.
  2. DS05-Q02 · 지원 프로필 · 확정: 기본 8개와 custominput 선택 1개를 지원한다. sim·solution2는 미사용, source_code_user·status는 별도 호환·도구 계약으로 둔다.
  3. DS05-Q03 · 기능별 Gateway · 확정: 범용 Judge DB·SQL API를 제거하고 Problems·Submissions·Contests·Auth Migration의 타입이 정해진 Gateway만 허용한다.
  4. DS05-Q04 · 사용자 호환 · 확정: 숫자 WordPress ID를 경계에서 user_login으로 변환하고 48자 초과·Judge collation 충돌은 자동 변환 없이 제출 전 차단·보고한다.
  5. DS05-Q05 · MyISAM 쓰기 · 확정: 트랜잭션을 가정하지 않고 제출은 준비 행·소스 검증·마지막 대기열 게시 순서로 처리한다. 기존 submission_events에 요청 멱등키 속성·고유키를 보강하고 다중 테이블 작업은 보상·재조정을 사용한다.
  6. DS05-Q06 · 사용자 원본 · 확정: 플러그인은 Judge users에 계정·프로필·비밀번호·상태를 쓰지 않고 기존 계정 전환 Reader만 제한적으로 유지한다.
  7. DS05-Q07 · 자격·보안 · 확정: 플러그인은 읽기·쓰기 자격을 별도로 설정할 수 있게 하되 표준 HUSTOJ의 단일 DB 계정을 양쪽에 동일하게 지정하는 구성을 허용한다. Judge 프로세스와의 계정 분리는 권장 보안 구성으로 두고, 원격 연결은 인증서 검증 TLS를 적용하며 운영 쓰기 시험은 금지한다.
  8. DS05-Q08 · 운영 화면 · 확정: 후보 연결을 검사한 뒤 명시적으로 적용하며 실패 시 기존 active 연결을 유지하고 상태 화면에는 안전한 결과·필요 조치만 표시한다.
확정·구현: DS05-Q01~Q08을 설계 기준으로 유지한다. 읽기·쓰기 계정은 분리 입력을 지원하되 같은 HUSTOJ 계정을 양쪽에 넣을 수 있으며, 운영 연결 검사는 설치 승인 단계에서만 수행한다.
