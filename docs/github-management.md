# GitHub 공개 및 버전 관리

이 문서는 현재 **HUSTOJ 기반 OJ Platform과 애드온의 개발 소스**를 공유하고, 이후 Judge0 기반 개발을 별도 저장소로 관리하기 위한 방침입니다. 현재 코드를 Judge0 전환 완료 상태로 표시하지 않습니다.

현재 공개 저장소는 [vVpandaVv/oj-platform-hustoj](https://github.com/vVpandaVv/oj-platform-hustoj)입니다. 사용자가 확정한 첫 공개 범위는 플랫폼과 모든 애드온의 개발 소스이며 교재·문제 콘텐츠는 포함하지 않습니다. 향후 Judge0 버전은 `oj-platform-judge0`라는 별도 저장소로 구분할 계획입니다. Judge0 저장소의 생성과 구현 완료를 의미하지 않습니다.

## 현재 HUSTOJ 기준선

현재 버전의 기준선은 플랫폼 **2.5.1** 소스입니다. 애드온의 버전은 각 메인 파일 헤더와 릴리스 킷 목록을 기준으로 확인합니다. 플랫폼 버전과 애드온 버전을 하나의 숫자로 일괄 변경하지 않습니다.

공개 기준선은 다음처럼 보존합니다.

1. 첫 공개 기준선 태그는 `hustoj-baseline-20261026`으로 관리합니다. 실제 커밋과 검증 결과는 공개 시 함께 기록합니다.
2. 기본 브랜치는 `main`, HUSTOJ 유지보수 브랜치는 `codex/hustoj-maintenance`로 구분합니다. 기준선 태그는 이동·삭제·덮어쓰기하지 않습니다.
3. 정식 패키지의 버전 태그는 공식 빌더의 규칙을 따릅니다. OJ Platform의 `oj-platform-v<버전>` 태그와 공개 기준선 태그는 역할이 다릅니다.
4. 수정한 릴리스는 새 버전·새 태그로 만듭니다. 과거 ZIP과 체크섬을 같은 이름으로 교체하지 않습니다.

커밋·태그·브랜치를 실제로 만들거나 원격에 반영할 때는 현재 변경과 대상 저장소를 확인합니다. 이 관리 문서는 그 작업을 자동 실행하는 스크립트가 아닙니다.

## 개발 이력과 공개 스냅샷

기존 작업 저장소에는 비공개 운영 기록이나 로컬 환경 자료가 섞여 있을 수 있습니다. 기존 Git 이력은 원래 작업 저장소에서 보존하고, 공개용은 **별도 내보내기 디렉터리의 검토된 스냅샷**으로 준비합니다.

- 파일 선택은 제외 목록만 믿지 않고, 공개할 소스 디렉터리·개발 도구·테스트·문서를 명시해 확인합니다.
- 공개용 첫 커밋에는 검토한 파일만 넣습니다. 기존 `.git` 디렉터리를 복사하거나, 비공개 저장소의 전체 이력을 `push --mirror`로 공개 저장소에 보내지 않습니다.
- 공개 스냅샷의 기준 버전·검토 일자·검증 결과를 기록합니다. 원래 비공개 이력을 공개 커밋과 동일한 이력으로 표현하지 않습니다.
- 필요한 편집기 원본·빌드 스크립트·고정 의존성 목록·라이선스 고지는 보존합니다. 의존성 캐시나 과거 생성물이 원본을 대신하지 않도록 합니다.
- 개발 소스 공개와 설치 ZIP 공개는 구분합니다. 설치 ZIP은 공식 릴리스 킷으로 생성한 결과만 사용합니다.

공개 후에는 검토한 변경을 작은 커밋으로 관리합니다. 비공개 작업 폴더의 파일을 일괄 동기화하거나 `git add .` 결과를 검토 없이 그대로 공개하지 않습니다.

실서버 구현 일지·계정별 검증·화면 캡처와 배포 인수 기록은 개발 소스와 분리합니다. AI Dashboard는 검토한 설계 문서만 포함하고 공개용 목차를 별도로 생성합니다. Code Lab은 실제 운영 인수 기록 대신 보류 상태의 예제 파일을 제공합니다. 공개 검토에서 제외 대상이 발견된 후보 Git 이력은 원격에 보내지 않고 격리하며, 수정된 공개 후보는 제외 자료를 포함한 부모 커밋 없이 새 이력으로 만듭니다.

현재 내보내기 도구는 `_release-kit/export-public-source.py`이며, 포함·제외 규칙은 `_release-kit/public-source.json`입니다. 기본 동작은 파일 목록과 용량을 확인하는 dry-run입니다. `--write`는 신규 또는 빈 출력 폴더만 허용하고 기존 파일을 덮어쓰거나 지우지 않습니다. 기본 공개용 로컬 저장소는 `.codex-work/github/oj-platform-hustoj`이며 원래 개발 저장소의 이력을 변경하지 않습니다. 이후 변경은 새 후보 폴더로 내보내고 공개 저장소와 diff를 검토한 뒤 반영합니다.

공개 후보에는 콘텐츠 대신 빈 `readcontents-content/catalog.json`과 범위 안내를 만듭니다. 공개 폴더에서 `release.cmd content`를 실행해 인덱스를 생성한 뒤 `release.cmd check`로 점검합니다. `SOURCE-SNAPSHOT.json`은 원래 개발 기준 커밋과 현재 작업 파일을 포함했다는 사실, 파일별 해시와 내보내기 범위를 기록합니다.

## 공개하지 않는 자료

다음 자료는 소스 공유 대상에서 제외합니다.

| 종류 | 예시 |
| --- | --- |
| 인증·운영 설정 | 실제 `.env`, `wp-config.php`, DB 접속값, API 토큰, SMTP 비밀번호, SSH 키, 인증서 개인키, 클라우드 자격 증명 |
| 데이터와 개인정보 | DB 덤프·백업, 학생·교사 명단, 실제 제출 코드·성적·연구 참여 기록, 업로드 자료, 비공개 문제·정답 데이터 |
| 운영 기록 | 디버그 로그, 실제 요청·응답 캡처, 세션·쿠키·실행 ticket, 서비스 진단 원본, 내부 주소나 개인 정보가 담긴 화면 캡처 |
| 로컬 산출물 | `node_modules`, 패키지 캐시, 임시 폴더, 과거 빌드·배포 묶음, 편집기 임시 파일 |

예제 설정은 실제 값과 분리하고, 문서용 가상 값임을 명확히 합니다. 테스트 fixture도 합성 자료인지 확인합니다. 공개 가능한 콘텐츠와 외부 자산은 재배포 권한·원래 고지·출처를 별도로 확인합니다.

경로 이름만으로 안전성을 판단하지 않습니다. 소스·문서·샘플·스크립트·그림의 내용과 Git에서 추적할 파일 목록을 함께 확인합니다. 공개 전에 비밀값 검색, UTF-8/BOM 검사, 큰 파일·생성물 확인, 변경 diff 검토를 수행합니다. 자동 검사가 모든 비밀값이나 권리 문제를 찾아준다고 표현하지 않습니다.

공개된 비밀값을 발견하면 해당 자격 증명을 먼저 폐기·교체하고, 공개 이력과 배포물에 남은 범위를 확인합니다. 최신 커밋에서 파일만 삭제한 것으로 노출이 해소되었다고 처리하지 않습니다.

## Judge0 기반 별도 저장소

Judge0 전환 저장소는 실제 전환 작업을 시작하고 공개할 기준 소스가 준비될 때 별도로 만듭니다. 현재 HUSTOJ 저장소를 이름만 바꾸어 전환 완료처럼 안내하지 않습니다.

전환 저장소에는 다음을 명시합니다.

- 출발한 HUSTOJ 기준선의 태그·버전과 유지한 구성 요소
- Judge0 실행 어댑터·워커·최종 판정·특수 채점의 실제 구현 범위
- 보존한 문제·제출 ID와 기존 DB 호환 범위, 별도 데이터 이전이 필요한 부분
- 사용자 입력 실행, PRIMM, 그림 채점, 대회 점수 등 기능별 호환성 검증 결과
- 설치·전환·복구 절차와 미지원·미검증 범위

HUSTOJ 쪽의 수정은 필요성과 호환성을 검토해 Judge0 저장소에 반영합니다. 두 저장소의 커밋을 무조건 병합하지 않으며, 보안 수정이나 공통 애드온 변경을 옮길 때는 원래 변경의 출처와 검증 결과를 기록합니다. HUSTOJ 기준선과 릴리스는 그대로 남깁니다.

## 릴리스와 설치 안내서

설치 ZIP과 설치 안내서는 저장소 루트의 `_release-kit\release.cmd`만 사용해 만듭니다. 세부 정책은 [릴리스 킷 설명](../_release-kit/README.md)을 따릅니다.

```powershell
.\_release-kit\release.cmd package
.\_release-kit\release.cmd docs
.\_release-kit\release.cmd check
```

한 번에 처리할 때는 `release.cmd all`을 사용합니다. 버전별 패키지는 `_releases/<플러그인>/<버전>/`에만 만들고 릴리스한 버전은 덮어쓰지 않습니다. 안내서 원본은 `_release-kit/guides/`이며 `_releases/latest/`는 생성물입니다.

GitHub Releases에 파일을 첨부하는 경우도 공식 킷에서 생성·검사한 파일과 체크섬을 사용합니다. GitHub의 자동 생성 Source code ZIP은 개발 소스이며 WordPress용 통합 설치 ZIP이 아닙니다. OJ Research처럼 현재 킷 목록에 없는 구성 요소는 공식 배포 경로를 먼저 정리한 뒤 설치 패키지를 추가합니다.

## 라이선스와 검증 기록

플랫폼 자체 코드의 [GPL-3.0-or-later 고지](../oj-integration-rebuild/oj-platform/LICENSE.txt), 애드온별 기존 라이선스, 외부 구성 요소의 원래 고지를 유지합니다. 저장소 공개를 이유로 다른 구성 요소의 라이선스를 일괄 변경하지 않습니다. 소유 코드의 표기가 빠진 곳과 콘텐츠 재배포 조건은 공개 범위를 정할 때 확인합니다.

공개 기준선에는 실제로 실행한 검사와 미실행 검사를 구분해 기록합니다. `release.cmd check`는 패키지 정책 검사이며, 모든 언어·채점 방식·동시 부하·운영 서버의 검증을 대신하지 않습니다. 실제 사용자 자료 대신 합성 fixture를 사용하고, 테스트를 통과했다는 설명에 대상 버전과 범위를 함께 적습니다.
