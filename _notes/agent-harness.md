# 플러그인 루트 에이전트 하네스

이 문서는 `wp-content/plugins` 루트 전체를 대상으로 하는 작업자용 표준 하네스다.
목적은 다음과 같다.

- 여러 작업자와 에이전트가 같은 기준으로 설계, 구현, 검수, 인수인계를 수행하게 한다.
- `OJ-BUILD-HARNESS.md`의 아키텍처 원칙을 실제 작업 절차로 변환한다.
- 인코딩, 설정, 채점엔진 연동, 모듈 분리, 검수 기준이 작업마다 흔들리지 않게 한다.

이 문서는 루트 `AGENT.md`, `OJ-BUILD-HARNESS.md`, 각 플러그인 내부 하네스보다 실행 절차에 더 가까운 운영 문서다.

## 1. 적용 범위

다음 작업은 모두 이 하네스를 따른다.

- `oj-*` 플러그인 신규 생성, 수정, 분리, 통합
- `hustoj-*` 레거시 분석 및 이전 작업
- 루트 문서, `_notes` 문서, 설치/배포 문서 수정
- 설정 화면, 운영 화면, 설치 도구, 감사 로그, 라이선스, 헬스체크 작업
- 채점엔진 연동 또는 제출 흐름 수정

## 2. 기준 문서 우선순위

작업 중 기준이 충돌하면 아래 순서대로 우선 적용한다.

1. 현재 사용자 요청
2. 루트 `AGENT.md`
3. `OJ-BUILD-HARNESS.md`
4. 이 문서 `_notes/agent-harness.md`
5. 각 플러그인 내부 문서와 README
6. 기존 구현 코드와 패턴

단, 인코딩과 저장 형식 규칙은 `AGENT.md`를 최우선으로 적용한다.

## 3. 비타협 작업 원칙

### 3.1 인코딩 원칙

- 모든 텍스트 파일은 반드시 `UTF-8 without BOM`으로 저장한다.
- `UTF-8 BOM`, `UTF-16`, `CP949/EUC-KR` 저장은 금지한다.
- 파일 콘텐츠를 읽어 올 때도 UTF-8을 명시한다. PowerShell에서는 `Get-Content -Encoding UTF8`을 기본으로 사용한다.
- 사용자 화면, 관리자 화면, 문서의 한글은 실제 UTF-8 한글 리터럴로 저장한다.
- `\uXXXX`, `\u{XXXX}` 형태의 한글 이스케이프는 남기지 않는다.
- PowerShell 저장 시 가능하면 `.NET UTF8Encoding(false)`를 사용한다.

### 3.2 아키텍처 원칙

- 모든 신규 기능은 단일 거대 플러그인이 아니라 `oj-*` 모듈 구조로 작성한다.
- 모듈 간 직접 결합보다 `contract`를 우선 사용한다.
- 외부 채점엔진 접근은 `oj-judge-adapter`를 통해서만 수행한다.
- `HUSTOJ` DB나 레거시 내부 테이블에 새 의존성을 추가하지 않는다.
- 아직 설치되지 않은 기능을 이유로 코어 테이블에 미래 컬럼을 미리 넣지 않는다.
- 채점엔진 코어 테이블은 최소화하고, 기능별 정보는 모듈 전용 테이블로 확장한다.

### 3.3 운영 원칙

- 설정 가능한 값은 모듈 자체 화면 또는 `OJ Setup`에서 도달 가능해야 한다.
- 중요한 상태 변경은 감사 로그를 남겨야 한다.
- 운영 상태는 `oj-ops`에서 확인 가능해야 한다.
- 상용 또는 제한 기능은 `oj-license` 게이트를 통과해야 한다.
- 배포에 필요한 환경 입력값은 하드코딩하지 않는다.

## 4. 에이전트 역할 정의

작업자는 하나 이상의 역할을 수행할 수 있지만, 결과물은 아래 책임을 모두 충족해야 한다.

### 4.1 설계 담당

- 요구사항을 기존 모듈 구조에 맞게 배치한다.
- 새로운 기능이 어떤 플러그인에 속하는지 결정한다.
- 의존성, 설치 순서, 계약 경계를 먼저 정리한다.

### 4.2 구현 담당

- 기존 패턴을 존중하면서 실제 코드, 테이블, 화면, 문서를 작성한다.
- 설정, 헬스체크, 감사 로그, 권한 체크를 빠뜨리지 않는다.
- 런타임에서 없는 모듈이 있어도 치명 오류가 나지 않게 처리한다.

### 4.3 검수 담당

- 문법 검사, 흐름 점검, 의존성 누락, 권한 누락, 설정 누락을 확인한다.
- 기존 계약을 우회하거나 직접 결합한 코드가 없는지 확인한다.
- 사용자에게 전달할 위험과 남은 환경 작업을 명확히 기록한다.

### 4.4 릴리스 담당

- 설치 순서와 초기 설정 순서를 정리한다.
- 환경별 입력값을 어디서 넣는지 명확히 남긴다.
- 운영 전 필수 점검 항목을 인계한다.

## 5. 표준 작업 순서

모든 작업은 가능하면 아래 순서를 따른다.

1. 요구사항을 현재 플러그인 구조에 배치한다.
2. 영향받는 모듈, 계약, 설정값, 관리자 화면을 확인한다.
3. 기존 패턴을 읽고 같은 구조로 구현 방향을 확정한다.
4. 필요한 경우 `plugin-package.php`, 설치기, 계약 등록, 설정 provider를 함께 설계한다.
5. 코드 수정 전에 변경 범위와 목적을 짧게 공유한다.
6. 파일을 수정하고, 필요한 문서와 설정 경로를 함께 갱신한다.
7. 변경 파일에 대해 문법 검사나 정적 확인을 수행한다.
8. 사용자가 실제로 해야 할 설정, 테스트, 운영 후속 조치를 정리한다.

## 6. 변경 유형별 필수 규칙

### 6.1 신규 플러그인 생성

- 루트 디렉터리명은 `oj-*` 규칙을 따른다.
- 반드시 다음 파일을 갖춘다.
  - 메인 플러그인 파일
  - `plugin-package.php`
  - `src/Core/Autoloader.php`
  - `src/Core/Plugin.php`
  - `README.md`
- 하드 의존성은 `plugin-package.php`에 명시한다.
- 활성화 훅과 설치기가 필요하면 함께 만든다.
- 가능한 경우 `OJ Setup`에 연결할 `setup_provider`를 제공한다.

### 6.2 DB/테이블 변경

- WordPress 쪽 테이블은 각 모듈 설치기에서 생성한다.
- 채점엔진 코어 테이블은 `oj-judge-adapter` 계약을 통해 접근한다.
- 없는 기능을 위해 코어 테이블에 컬럼을 선반영하지 않는다.
- 빈번히 조회되는 목록은 핫패스에 맞는 인덱스를 우선 고려한다.
- 모듈 전용 데이터는 모듈 테이블로 분리한다.

### 6.3 제출 흐름 변경

- 제출 생성은 `oj-problems` 서비스 계층에서 처리한다.
- 채점 요청은 `oj-judge-adapter`를 통해서만 전달한다.
- 반, 대회, 평가 같은 컨텍스트는 `submission_context_provider` 계약으로 연결한다.
- 요청자와 대상자, 컨텍스트 범위를 분리해 기록한다.
- 프론트 제출과 관리자 제출은 같은 서비스 규칙을 공유해야 한다.

### 6.4 설정 화면 추가

- 설정 항목은 모듈 내부 관리자 화면 또는 `OJ Setup`에서 접근 가능해야 한다.
- 여러 환경에서 바뀌는 값은 옵션 저장 구조로 두고 코드에 고정하지 않는다.
- 민감한 값은 표시 방식을 최소화하고, 저장 후 요약만 노출한다.
- 설정만 있고 검증 수단이 없으면 안 된다. 가능하면 연결 테스트나 상태 요약을 제공한다.

### 6.5 AI 기능 추가

- 모든 AI 호출은 `oj-ai-provider`를 경유한다.
- 공급자 종류, 모델, 타임아웃, 키 관리는 공통 provider 설정을 사용한다.
- AI 결과가 운영에 영향을 주면 감사 로그와 검토 상태를 함께 고려한다.
- 평가나 피드백은 대상 학생, 그룹, 계획 식별자를 추적 가능하게 남긴다.

### 6.6 게시판/UX 기능 추가

- 게시판은 `oj-board-addon`을 통해 제공한다.
- Blockly 제출은 `oj-blockly-submit`을 통해 제공한다.
- 라이선스 게이트가 필요한 경우 프론트와 관리자 모두 같은 정책을 적용한다.
- 프론트 shortcode는 로그인 상태, 빈 데이터, 오류 메시지까지 포함해 완료형으로 만든다.

## 7. 계약과 의존성 사용 규칙

- 모듈 간 공유 기능은 직접 클래스 호출보다 `oj_register_contract()`와 `oj_contract()`를 우선 사용한다.
- URL 생성은 URL registry를 우선 사용한다.
- 선택 기능은 soft dependency로 처리하고, 없는 경우 기능을 숨기거나 대체 메시지를 보여준다.
- 하드 의존성은 `plugin-package.php`와 활성화 가드에 함께 반영한다.
- 새 계약을 추가하면 다음을 같이 맞춘다.
  - 등록 위치
  - 소비 위치
  - 없는 경우의 fallback
  - 관련 문서

## 8. 감사 로그, 헬스체크, 라이선스 규칙

- 다음 작업은 감사 로그 대상으로 본다.
  - 설정 변경
  - 생성/삭제/동기화 작업
  - 대량 처리
  - 운영 상태 변경
- 다음 기능은 헬스체크 제공 여부를 검토한다.
  - 외부 DB 연결
  - 외부 API 연결
  - 라이선스 상태
  - 필수 설정 누락
- 상용 기능이나 제한 기능은 `oj_license_allows()` 기준을 통과해야 한다.
- 라이선스 게이트만 추가하고 관리자 설명이 없으면 안 된다. 설정 경로와 상태 요약이 함께 있어야 한다.

## 9. 프론트와 관리자 UI 규칙

- 프론트 shortcode는 단순 자리표시자가 아니라 실제 사용 가능한 흐름이어야 한다.
- 관리자 페이지는 최소한 목록, 생성 또는 저장, 상태 메시지까지 포함한다.
- 비어 있는 상태와 오류 상태를 화면에 명확히 표현한다.
- 코드 예외를 화면에 그대로 노출하지 않고 사용자용 메시지로 변환한다.
- 디자인보다도 설치 직후 사용성과 설정 가능성이 우선이다.

## 10. 문서화 규칙

- 구조가 바뀌면 `OJ-BUILD-HARNESS.md` 또는 관련 README를 갱신한다.
- 운영자가 실제로 입력해야 하는 값은 문서 또는 `OJ Setup`에 드러나야 한다.
- 새 모듈을 만들면 최소한 역할, 의존성, 설정 위치, 제공 shortcode를 README에 적는다.
- 작업 종료 보고에는 다음을 포함한다.
  - 무엇을 구현했는지
  - 어디를 수정했는지
  - 무엇을 검증했는지
  - 아직 실환경에서 해야 할 일이 무엇인지

## 11. 반복 오류 방지 체크리스트

### 11.1 저장 전

- 수정 파일이 텍스트 파일인지 확인한다.
- 한글이 포함되면 실제 한글 리터럴로 저장할 계획인지 먼저 확인한다.
- PowerShell 저장 시 `.NET UTF8Encoding(false)`를 사용한다.

### 11.2 저장 직후

- BOM 존재 여부를 확인한다.
- 파일을 다시 읽어 한글이 그대로 보이는지 확인한다.
- `\uXXXX`, `\u{XXXX}`가 남았는지 다시 검색한다.
- 인코딩 복원 중 문장 일부가 깨졌다면 즉시 중단하고 원인을 다시 좁힌다.

### 11.3 전수 수정 시

- 먼저 전체 스캔으로 `BOM`, `CP949 fallback`, `유니코드 이스케이프`, `깨진 문자`를 집계한다.
- 일괄 변환은 `vendor`, `node_modules`, `.min.js`, `.min.css`를 포함한 전체 범위에서 수행하되, 외부 자산은 변환 근거를 먼저 확인한다.
- 일괄 변환 후 다시 같은 스캔을 반복해 잔여 항목이 0인지 확인한다.

## 12. 금지 사항

다음 패턴은 금지한다.

- `HUSTOJ` DB에 새 기능을 직접 연결하는 것
- `oj-judge-adapter`를 우회해 채점엔진에 직접 붙는 것
- 설정 값을 소스코드 상수나 임시 문자열로 고정하는 것
- 설치되지 않은 미래 기능 때문에 코어 테이블을 과도하게 확장하는 것
- `contract`로 풀 수 있는 문제를 직접 클래스 참조로 박아 넣는 것
- 프론트 shortcode를 자리표시자 수준으로만 남기는 것
- 감사 로그나 권한 체크 없이 대량 상태 변경을 만드는 것
- 임시 복구 파일을 루트에 남겨두고 설명 없이 종료하는 것
- 문법 검사와 기본 검증 없이 구현 완료를 선언하는 것

## 13. Definition of Done

다음 조건을 만족해야 작업 완료로 본다.

- 요구사항이 어느 모듈 책임인지 명확하다.
- 필요한 코드, 설정, 문서, 관리자 경로가 함께 반영되었다.
- 하드 의존성과 soft dependency가 의도대로 정리되었다.
- 필요한 경우 감사 로그, 헬스체크, 라이선스 게이트가 포함되었다.
- 변경 파일에 대한 기본 검증이 수행되었다.
- 사용자가 실제로 해야 할 환경 설정이나 테스트가 정리되었다.

## 14. 인수인계 규칙

다음 작업자나 에이전트에게 넘길 때는 아래를 반드시 남긴다.

- 현재 구현 상태 요약
- 수정한 핵심 파일 경로
- 검증 결과
- 남은 환경 설정 값
- 아직 열려 있는 위험 또는 미완 테스트

## 15. 현재 OJ 프로젝트에 대한 해석

현재 이 워크스페이스에서 이 하네스는 다음처럼 해석한다.

- 구조 설계와 모듈 구현은 이미 상당 부분 완료된 상태다.
- 남은 핵심 일은 실환경 설정 입력, 활성화 검증, 통합 테스트, 운영 안정화다.
- 따라서 새 작업은 아키텍처를 다시 흔드는 것보다 기존 기준을 보강하는 방식으로 진행해야 한다.
- 새 기능도 가능하면 `OJ Setup`, `oj-ops`, `oj-license`, `oj-core contract` 체계 안에 편입해야 한다.
